# 优化方案（2026-08-13）

对应 `README.md` 里的 L-1…L-8。每项给「最优解 + 为什么不选其他 + 预期效果」。
优先级按「每天被多少人撞到 × 撞到时的代价」排。

---

## 1. L-1 性能：20.4 秒 → 预期 < 0.5 秒　【P0，改动最小，收益最大】

### 真正的成因（profile 实测，与初版报告的判断不同）

```
build_inspection_audit_workspace          20.6s / 20 次
└─ build_inspection_submitted_document_rows   17.2s
   └─ project_document_read_view              17.1s
      └─ deepcopy（745 万次）                  17.0s
         └─ InMemoryRepository.__init__        15.7s
            └─ runtime_initial_state → fresh_state()
               ├─ publish_standard_clause_release   10.6s
               └─ bind_project_node_clause_packages  8.0s
```

`project_document_read_view()` 里：

```python
view = InMemoryRepository()     # 172ms：重建整个 demo 种子、发布条款 release、绑定 69 节点
view.state = detached_state     # 下一行把上面造的东西整个丢掉
```

单次 242ms 里 **172ms（71%）是白做的**。而这个视图只依赖 `projectId`，却被
`audit-overview` 在 69 个节点的循环里各调一次。

### 最优解（两处，都是外科手术式改动）

**A. 构造游离视图时不播种。** 给 `InMemoryRepository` 加 `seed: bool = True`，
detached view 传 `False`；或用 `__new__` + 手动初始化。
→ 单次 242ms → 约 70ms。

**B. 把 read view 提到节点循环之外。** 它是**项目级**的，不随 nodeId 变化，
在 `audit-overview` 里构造一次传给所有节点投影。
→ 69 次调用 → 1 次。

合计：`69 × 242ms ≈ 16.7s` → `1 × 70ms ≈ 0.07s`。

**为什么不选缓存**：缓存是掩盖，且要处理失效；这里是纯粹的重复劳动，去掉即可，
没有一致性代价。

**为什么不选「分页后再算」**：`summary` 本来就要覆盖全部 69 个节点，切了分页
汇总数字就不准了。去掉浪费后全量算也只要毫秒级，不必牺牲正确性。

### 护栏
加一条性能回归测试：`audit-overview` 内 `InMemoryRepository()` 的构造次数必须 ≤ 1。
断言调用次数而不是耗时——耗时在 CI 上不稳定，次数是确定的。

## 2. L-2 载荷：单次加载省 4.5 MB　【P0，改动最小】

`businessPackSnapshot`（1.1 MB）内嵌在每个响应的 `data.project` 里：
`workbench/projects`（×9 = 6.6 MB）、`tree`、`workbench/context`、`audit-overview`。

### 最优解

1. 这四个端点改用**仓库里已有**的 `project_without_business_pack_snapshot()`
   （`routes.py:2404`，目前全库只用了 2 处）。
2. 响应保留 `businessPackSnapshotHash`；前端按 hash 缓存，只在 hash 变化时
   调一次独立端点取完整快照。

→ 项目列表 6.6 MB → 约 50 KB；工作台单次加载少传约 4.5 MB。

**为什么不选 gzip**：nginx 压缩能把体积压下去，但服务端序列化 1.1 MB × 4 的
CPU 和内存开销还在，前端解析也还在。不传才是最优。

### 护栏
契约测试：这些端点的响应体不得包含 `businessPackSnapshot` 键。

## 3. L-3 OCR 结构化：右侧看不懂　【P1，业务价值最高】

现状：`ocrReadiness.status = ready`、bbox 100%，但字段是
`OCR文本 / OCR文本2 … OCR文本5`、置信度全 `0.0`。

这是两个独立问题，要分开治：

### 3a. 抽取本身没做字段识别（后端）

**最优解**：以节点规则声明的必需字段为 schema，做一次结构化抽取
（`设计压力`、`材料牌号`、`证书编号`、`有效期`…），LLM 走已有的 `llm.remote` 队列。
抽不出的字段显式标 `missing`，不要用文本片段占位。

**为什么不选正则/模板**：69 个节点、63 种资料类型，模板维护不起；而规则里
已经声明了每个节点要什么字段，正好当 schema 用。

### 3b. 就绪度指标说了谎（后端，先做，成本极低）

`status = ready` 目前只校验「有文本 + 有坐标 + 产物完整」。加一条
**字段覆盖率**：规则要求的字段一个都没抽到时，状态不得为 `ready`，
应为 `incomplete` 并说明「未识别出业务字段」。

先做这条的理由：它不需要等抽取能力就位，却能立刻阻止「系统说就绪、监检打开
发现没法用」——本轮反复出现的正是这类「指标绿了、事情没成」。

### 3c. 右侧面板按业务语义分组（前端）

现在是平铺 10 条 `OCR文本N`。改成：

- **规则要求的字段**排在最前，抽到的显示值 + 置信度，没抽到的显示「未识别」并可
  一键人工补录（`fact-corrections` 接口已存在）；
- **其余识别内容**折叠进「原文片段」次级区域，默认收起；
- 置信度为 0 时不显示「0%」——那会被读成「完全不可信」。应显示「未提供置信度」，
  两者含义完全不同。

## 4. L-4 Office 预览：用 ONLYOFFICE　【P1】

你已确认「能预览就行，不用定位」，那 ONLYOFFICE Document Server 就是最优解。

- 镜像 `docker.m.daocloud.io/onlyoffice/documentserver:8.2` **实测可达**；
- 服务器余量：内存 30 G（已用 7 G）、磁盘 39 G 可用，跑得下（DS 约需 2–4 G 内存）；
- 集成方式：文档走 MinIO 预签名 URL 给 DS，前端嵌 DS 的 viewer；只读模式不需要
  回调保存，接入面很小。

**注意两点**（不影响决策，但要知道）：
1. 社区版是 AGPL v3。内部自用没问题；若将来对外提供 SaaS，需评估。
2. 走 DS 的 iframe 后，bbox 坐标数据仍然用不上——你说不需要定位，那这笔就是
   有意识地放弃，不是遗漏。

**更轻的备选**（若嫌 DS 重）：LibreOffice headless 转 PDF，复用现有 PDF 预览路径，
资源占用约为 DS 的十分之一；代价是保真度略低、不能在线编辑。

## 5. L-5 状态口径：新项目不该有 138 个红点　【P1】

「还没开始报送」被计为 `needs_attention`。

**最优解**：把 `needs_attention` 的判据收紧为「有人做了事但结果不对/不全」：

| 情形 | 现在 | 应为 |
|---|---|---|
| 项目未开工、无任何提交 | 需关注 | **未开始** |
| 已提交但缺必传项 | 需关注 | 需关注 ✓ |
| 已提交且被打回 | 需关注 | 需关注 ✓ |
| 超过约定时限未提交 | 未开始 | **需关注**（新增） |

判据从「有没有资料」改成「该做的事有没有进展」。这样 138 个红点会归零，
真正需要关注的浮上来。

## 6. L-6 AI 复核假成功　【P1】

接口返回 `code=0`、界面显示「已进入队列」，运行记录却是 `失败`。

**最优解分两层**：

1. **让失败可见**（立刻可做）：run 状态为失败时，界面显示失败原因与可重试入口，
   而不是停留在「完成后将更新」。
2. **把 LiteLLM 跑起来**：`ghcr.io` 不可达，各镜像源也没有 —— 用 pypi
   （该网络可达）自建镜像：`pip install "litellm[proxy]"` + 现有
   `config/litellm.yaml`。上游 DeepSeek 的 key 已在服务器凭证文件里。

## 建议的执行顺序

1. **L-1 + L-2**：改动最小、收益最大，且互不干扰，一起做一次部署即可
   （24 秒 → 亚秒级，单次加载少传 4.5 MB）。
2. **L-3b**（就绪度不说谎）+ **L-5**（状态口径）：都是判据修正，不依赖新能力，
   做完界面才开始讲真话。
3. **L-4** ONLYOFFICE：独立部署，不阻塞其他项。
4. **L-3c** 右侧面板重排：依赖 L-3b 的字段覆盖率信息。
5. **L-6** LiteLLM 自建镜像 + 失败可见。
6. **L-3a** 结构化抽取：工作量最大，且应在前面几项稳定后再动。
7. **L-7 / L-8** 随手清掉。
