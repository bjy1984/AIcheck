# 线上环境审计（2026-08-12）

环境：`http://39.108.65.148:8081`，最小可用栈（Postgres + Redis + API + nginx），
六个角色真实登录，全部通过公网 API 实测。**本轮只找问题，未改动线上代码。**

与前几轮的关键区别：这是第一次在**真实部署环境**上审计——此前所有「在线确认」
都是本地 uvicorn。部署差异本身就是一类风险源。

## O-1 · 施工方可读监检人工审查意见全文与 AI 判定理由 【P1】

施工方（contractor）的动作表里**没有任何 `review:*` 或 `ai:*` 权限**：

```
project:view, file:view, file:upload, file:bind, file:preview, file:download,
file:withdraw, submission:draft, submission:submit, rectification:submit,
todo:update, message:update
```

但实测可读：

| 端点 | inspection | contractor | ndt | owner | admin |
|---|---|---|---|---|---|
| 人工审查意见 | 可读 | **可读** | 403 | 403 | 可读 |
| AI 运行记录 | 可读 | **可读** | 403 | 403 | 可读 |
| 整改往返 | 可读 | 可读 | 可读 | 403 | 可读 |

施工方实际读到的内容：

```
监检人工结论：结论=满足要求  风险=低  审查人=张工
             「焊工资格证书真实有效，持证项目和项目焊接作业要求匹配。」

AI 判定理由：  「仅识别到证书编号 TS6J-2024-03158；未识别到姓名、有效期、持证项目等
              支撑字段，不能判断证书与焊接作业要求是否匹配，需人工核对原件和外部
              查询截图。」
```

**这是 M-9 的同源遗漏**：上一轮修 M-9 时只把 `owner` 列进
`REVIEW_PROCESS_OBSERVER_ROLES`，`contractor` 没进去。当时的判断依据是「建设方是
observer」，但施工方同样没有审查过程的读权限——被审查方能看到审查方的完整判定
理由和内部结论，等于把「怎么判的」提前告诉了被判的一方。

**边界建议**：
- 整改往返**应当**对施工方开放——打回理由本就是要给他看的，这是业务闭环的一部分；
- 人工审查意见全文与 AI 判定理由**不应**开放。施工方需要知道的是「结论是什么、
  要补什么」，而不是「监检内部怎么推导的」。

修复方式与 M-9 一致：把 `contractor` 加入受限角色集合，但 `rectifications`
端点保持放行（它已经是施工方动作表 `rectification:submit` 的配套读取）。

## O-2 · 对象存储缺失时文档详情端点整体失败 【P2】

MinIO 未部署（最小栈），实测影响面：

| 端点 | 结果 |
|---|---|
| 文档详情 `/documents/{id}` | **50330 整体失败** |
| 预览地址 / 下载地址 / 原件 | 50330 失败（合理——本就需要存储） |
| 资料台账、节点包、节点树、工作台汇总、报告列表、归档包 | 正常 |

列表类端点正确降级，这部分设计是对的。但**文档详情整体失败值得商榷**：该端点同时
承载元数据（文件名、资料类型、归属节点、OCR 状态、版本列表）和存储签名地址，
后者不可用时前者也一并拿不到。

监检人员在存储故障期间连「这份资料是什么、挂在哪个节点」都看不到，而这些信息
完全不依赖对象存储。建议：元数据照常返回，签名地址字段置空并附 `storageUnavailable`
标记，由前端决定是否禁用预览/下载按钮。

**注**：审计过程中我一度误判 M-8 线上失效——因为详情端点返回空导致读数为 None。
实际台账视图里 `materialTypeName=焊工资格证`、`nodeId=24` 均正确落库，
**M-8 线上是生效的**。误判源于我的探测工具把非零 code 静默转成 None，
这个教训与 M-7（静默丢弃）同构。

## 本轮确认干净的防线

### 认证机制（8 项攻击面全部挡住）

| 攻击 | 结果 |
|---|---|
| 篡改 JWT `role` → admin（保留原签名） | 401 |
| `alg=none` 无签名令牌 | 401 |
| `dev-token-admin-admin` 后门 | 401 |
| `dev-token-inspection-inspection` | 401 |
| 持施工方令牌 + `X-Role: admin` 提权 | 403 |
| 空令牌 / `Bearer` / `abc.def.ghi` | 401 |

dev-token 后门在线上确实失效（`AICHECK_ALLOW_DEV_TOKENS` 未开），这是部署配置正确的
直接证据。

### 写路径授权（8 项越权全部拒绝）

施工方保存审查结论、施工方打回补正、建设方保存审查结论、NDT 打回补正、
**管理员代替业务角色审查**、FDE 保存审查结论、建设方上传资料、建设方触发 AI 复核
——全部 403。管理员不能代替业务角色写，这条尤其重要。

### 跨项目隔离（5 项全部拒绝）

施工方直接猜测越界项目 `P-2025-CQARCH-007` 的项目详情、资料台账、节点树、报告、
工作台汇总——全部「用户未获得该项目授权」。

### 跨单位数据隔离

NDT 只看到自家 2 份资料（华测检测），看不到施工方资料。施工方能看到 1 份 NDT 资料
——需业务确认是否为预期（可能是已提交进同一节点的共享证据）。
