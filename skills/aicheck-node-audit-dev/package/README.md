# aicheck-node-audit 安裝與使用

**最省事的裝法**：在 AIcheck 平台右上角帳號選單點「安裝節點審計 skill」，把複製到的那句話發給你電腦上的 AI 助手（Claude Code、Codex），它會自己下載、核對校驗值、安裝，最後打開網頁授權。下面是手動安裝的做法。

單節點輔助審計 skill：審一個工程節點，輸出是否通過、證據頁碼、不通過或暫不能判定的原因、最需要先做的事。輔助意見，不代替監檢人員的正式結論；同步到服務器要先預覽、用戶明確同意後才寫。

## 目錄
- `skills/aicheck-node-audit/`：skill 本體（`SKILL.md`、`references/`、`scripts/node_audit.py`）
- `backend/business_packs/engineering_inspection_v1/`：審計規則（skill 讀它建報告骨架）
- `rules/standards/`：skill 頁碼表（`references/standard-pages.md`）引用的 14 份標準原文。其餘標準庫沒有隨包帶，需要時用 `standards` / `standard-content` 命令經服務器查，或把 `AICHECK_REPO` 指向完整倉庫

## 安裝（3 步）
1. 解壓到任意目錄，下面稱為「包根目錄」。
2. 裝 PDF 庫和 YAML 庫（SKILL.md 默認用 `backend/.venv/bin/python`；讀審計規則要 PyYAML）：
   ```bash
   cd <包根目錄>
   python3 -m venv backend/.venv && backend/.venv/bin/pip install pymupdf pyyaml
   ```
3. 讓你的 agent 看到 skill，並**在包根目錄啟動 agent**（SKILL.md 里的命令都按包根目錄寫）：
   - Claude Code：`mkdir -p .claude/skills && ln -s ../../skills/aicheck-node-audit .claude/skills/aicheck-node-audit`
   - Codex：`mkdir -p .agents/skills && ln -s ../../skills/aicheck-node-audit .agents/skills/aicheck-node-audit`
   - 其他 agent：讓它先讀 `skills/aicheck-node-audit/SKILL.md` 再照做

**不需要在本機配任何 OCR 密鑰**：掃描件的 OCR 由 AIcheck 服務器做（服務器用它自己配好的 MinerU，MinerU 排隊超時會自動改用千問），skill 只用你的監檢登錄令牌。

自檢（不聯網）：`python3 skills/aicheck-node-audit/scripts/node_audit.py rules --node 24` 應返回 `"ok": true`。

## agent 需要的能力
能執行 shell 命令、讀文件就行，**不需要看圖能力**：掃描件上傳到服務器 OCR，agent 讀返回的逐頁文字（印章、簽名也在文字里，寫成 `[印章：…]`、`[簽名：…]`）。OCR 之後仍缺、讀不清的事實，skill 判證據不足或交人工確認，agent 不自己看圖。

## 用法
- 本地資料：對 agent 說「用 aicheck-node-audit 審計本地資料，節點 24，項目目錄 `<路徑>`」。資料都有文字層時不用登錄；有掃描件或圖片就要先按下面登錄（OCR 在服務器做）。第一次 OCR 前 agent 會問你是否同意把原件上傳到 AIcheck 服務器（服務器會留存上傳的原件，並交 MinerU、千問識別）；不同意就只審有文字層的文件，掃描件相關的檢查判證據不足。本地資料包不能同步。
- 服務器節點：先登錄。**推薦網頁授權**（不用開終端，口令只在瀏覽器裡輸）：對 agent 說「登錄 AIcheck」，它會運行
  ```bash
  AICHECK_BASE_URL=http://<服務器>:8081 AICHECK_ALLOW_HTTP=1 python3 skills/aicheck-node-audit/scripts/node_audit.py login --web
  ```
  瀏覽器會打開平台的授權頁：用監檢或管理員帳號登錄，核對頁面上寫的本機端口和 agent 說的一致，點「授權」，看到「授權成功」就好（5 分鐘內有效）。瀏覽器沒自動打開時，agent 會把鏈接發給你。授權碼只回調到 agent 所在那台電腦的 `127.0.0.1`，所以**你的瀏覽器要和 agent 在同一台電腦上**；agent 跑在遠程機器上時網頁授權收不到，改用下面的終端口令登錄。只有你自己剛讓 agent 登錄時才點授權，別人發來的授權鏈接不要點。
  也可以在**自己的終端**用口令登錄（口令不要發給 agent）：`… node_audit.py login --username <你的監檢帳號>`。
  登錄有效期 12 小時，過期後重新授權一次。帳號須是監檢（inspection）或管理員。再說「審計 `<工程ID>` 節點 `<N>`」。審完 agent 會先預覽同步內容再問你，你同意才寫。
- 資料包、頁圖、報告默認放 `~/.aicheck-node-audit/`，不在包目錄里。
- 審完 agent 會在回覆裡貼出**完整的逐項結果**（每項的結論、理由、事實和出處、下一步，以及缺的資料、風險、局限、讀了哪些文件），不只給路徑；同一份內容存在 `audit.md`。
- 結果圖（可選，要登錄）：審完對 agent 說「生成結果圖」，它會跑 `render`，把審計結果的摘要發給服務器，由服務器渲染成白底的圖存進資料包：內容少就一張 `audit.png`，內容多自動分頁成 `audit-1.png`、`audit-2.png`……（第 1 頁是總覽，後面每項檢查一張卡片）。生產服務器 2026-10-28 起已有這個接口；連到還沒更新的舊版服務器時 `render` 返回 `renderNotDeployed`，跳過即可，不影響審計。服務器不存摘要也不存圖。

## 注意
- 服務器節點的原件，平台已經用 MinerU（或千問兜底）識別過的，skill 直接取平台那份識別結果（輸出裡列在 `reused`）——平台審查讀的也是它——不再上傳、不再識別；平台用別的引擎識別的（如導入的測試工程）、還沒識別的，照舊上傳交 MinerU。要服務器 2026-11-04 之後的版本，連到舊服務器時自動照舊上傳。要重新識別就讓 agent 加 `--force`。
- 其餘掃描件、圖片會上傳到 AIcheck 服務器做 OCR。**服務器會永久留存上傳的原件**，不保證自動刪除，並交 MinerU、千問識別；本地測試資料上傳後也留在那里。你的 agent 的模型提供方只看到 OCR 文字（身份證號已脫敏）；證件號、許可證號經服務器發給公示平台查詢。脫敏按寬口徑：出生日期合法、首位 1–8 的 18 位號都遮（OCR 讀錯一位、號碼中間有空格的也遮），服務器返回的 JSON（工作區、證據鏈、審查運行）存進資料包時也已脫敏；緊挨著英文字母的號碼（如 `No110101…`）遮不到，這是已知局限。
- 服務器只在 MinerU 排隊超時時才改用千問；MinerU 已識別完但漏了某個值，不會再調千問，這類事實交人工確認。OCR 會認錯編號、代號裡的字母：MinerU 實測把 GTAW 讀成 CTAF、6G 讀成 60，千問會改大小寫；焊工項目代號以公示平台登記的為準。印章、簽字欄、水印上讀出的字常是錯的，只用來確認「有章」「有簽字」，單位名稱以證面的打印字為準。
- 圖紙的 OCR 常只讀出圖簽和表格：skill 會標出 OCR 讀不全的頁（沒讀出字、只讀出幾個字、識別跑飛、大幅面圖紙），agent 在這些頁上找不到的事實不會寫成「原件沒有」，而是去材料表、管道特性表裡找，仍找不到就交人工確認。同一長行在一頁裡反覆出現也算識別跑飛；二維碼、國徽處服務器偶爾返回的英文說明會換成「[圖塊：識別模型沒讀出字…]」。材料表單元格認錯、整頁讀成別的內容這類問題認不出來。Word 文件裡嵌的圖片（如焊工清單後附的證件照）也會交服務器識別。
- 服務器每次查 OCR 狀態、取結果都要幾秒（它每次整表加載），skill 查得很慢（至少 30 秒一次）。整包幾十份掃描件要 20–60 分鐘：一條 `ocr` 命令默認跑 5 分鐘（`--timeout`，最多 7 分鐘，每個請求都按剩餘時間截斷），到點就停，agent 再跑一次接著傳、接著等，不重傳；agent 會先識別本節點要核的文件。識別失敗的任務當場換新任務重試一次，來不及的留到下次。只有這次新建的任務也返回 `HTTP_401` 這類失敗時，才是服務器那邊 MinerU 的令牌過期或沒配好，要管理員處理，不是你的登錄過期。
- 當前驗證：3 個工程、8 個節點各跑 1 次（用 Sonnet 測的；其他模型未測）。現行的服務器 OCR 版本 2026-10-28 用標準答案重新評測：嚴格分 93.1%–100%（平均 96.3%），0 個嚴重問題；舊版（agent 自己看圖）是 94.4%–100%（平均 97.7%）。評測之後修了它暴露的 4 個 OCR 問題，修後版本 2026-10-28 晚再評一輪：嚴格分 93.1%–100%（平均 97.2%），0 個嚴重問題。這一輪又暴露的 OCR 細節（遺留失敗任務被誤報成令牌壞了、`--timeout` 不是硬上限、整行重複沒標出、Word 內嵌圖片沒識別等）也已修，離線測試全過，這部分沒有再評測。另在生產上用一頁公開的 TSG Z6002 標準頁實測過一次（MinerU，對照人工讀出的 16 項全對）。2026-10-27 在生產上用 P-2026-GDLNG-002 節點 16（3 份整份掃描件、31 頁）跑過完整流程：拉取、服務器 OCR、逐項審計、結果圖（4 頁）、同步預覽都通過；只有這一個節點，未經標準答案打分。標準答案多數未經人工確認；同步只在生產上做過預覽，沒有真實寫入過。結論都要人複核。
- `report` 校驗報告時會核對每條事實的摘錄是否真在所引那一頁的文字裡：符合／不符合項對不上算錯誤，報告交不出去；所以 agent 只能照抄原文，不能改寫。令牌過期時所有命令都返回 `loginRequired`，重新授權一次即可。
- 舊資料包（2026-10-28 之前做的 OCR）是舊排版：照樣能讀；再跑一次 `ocr` 會從服務器上已完成的任務取結果按新排版重排，不重新上傳、不重新識別。已經寫好報告的舊包別重排，不然摘錄會對不上新文字。
- `--out` 指到已有的共享目錄（如 `/tmp`）時，skill 只把它自己新建的目錄設成只有你能進，不改原有目錄的權限。
- 讀資料按頁讀：大文件先 `search`，再用 `text --pages` 只轉命中頁；表格裡橫跨多列的格子每行只寫一次、標「（跨N列）」。節點 16 實測原件文字因此少了六成（約 7.4 萬 → 2.8 萬 token），上百頁的節點也不會把對話撐滿。
