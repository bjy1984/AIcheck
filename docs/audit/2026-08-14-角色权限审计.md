# 角色权限审计（2026-08-14）

线上环境 `39.108.65.148:8081`，6 个角色 × 184 个 GET 端点 = **1,104 次探测**，
全程只读，未做任何写操作（用户处于演示准备期）。

## 方法与边界

- 端点清单从 `apps/api/routes.py` 的 `@router.get` 装饰器提取，带路径参数的用线上
  真实 ID 代入（项目 `P-2026-GDLNG-002`、节点 24/2、文档 `DOC-0D9436E0` 等）。
- 判据用**业务码**而不是 HTTP 状态码。这套接口鉴权失败时返回 `HTTP 200` +
  `{"code":401|403}`，拿 HTTP 状态当判据会得到全绿的假象——审计开始前我正是这么
  误报过一次。
- **没做**：浏览器里逐角色点击 UI。登录需要在表单里输密码，我不做这个动作；
  改用会话注入也被环境的凭证保护拦下。所以本轮覆盖的是 API 授权层，
  UI 层的按钮可见性与前端路由守卫需要另行人工验证。

## F-1（高）AI 判定被一道门拦住，另一道门敞着

`/reasoning/logs` 对全部 6 个角色开放。施工方读到的内容包括：


同一份数据在另一条路上是被拦住的：

| 施工方访问 | 结果 |
|---|---|
| `/projects/{p}/inspection/nodes/2/ai-runs` | **HTTP 403 已拦截**（既有的 O-1 防护） |

5 个项目内，没有跨项目泄露。所以这是「越权看到本项目里不该看的层级」，
不是「看到别人的项目」。

### F-7（高）部署后老用户必然报错，且错误无法自解释

登录时控制台连续抛：

```
Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "text/html".
Failed to fetch dynamically imported module:
  .../assets/AICheckStaticLayout-B6IWU1RR.js
  .../assets/ConversationalReviewWorkbenchB-DbHddvXd.js
```

原因链：

1. 前端每次构建，chunk 文件名哈希全变，旧 chunk 在部署时被 `rm -rf dist/*` 删除；
2. 浏览器缓存里的 `index.html` 仍指向旧 chunk；
3. nginx `try_files $uri $uri/ /index.html` 把 `/assets/*.js` 也兜住了，
   **对已删除的 chunk 返回 HTTP 200 + `text/html`**（实测 4983 字节的 index.html）。

于是浏览器期待 JS 拿到 HTML，报一个与真实原因毫不相干的 MIME 错误。
用户看到的是「登录时弹错误」，而真实原因是「你手上的页面是上一版的」。

硬刷新可绕过，但普通用户不会知道要这么做。

### F-8（高）线上跑的前端与仓库源码不是同一份

| 位置 | 是否含推荐问题功能 | 对话工作台 chunk |
|---|---|---|
| 仓库 HEAD 源码 | 有（9 处引用） | — |
| 本地当前构建 | 有 | `ConversationalReviewWorkbenchB-DbHddvXd.js` |
| **线上实际** | **无（0 处）** | `ConversationalReviewWorkbenchB-uioflCKk.js` |

## 修复过程中顺带核实、结论是安全的

`mutation_guard` 里的角色-动作校验写成 `if action_code and ...`，只在客户端
主动发 `X-Action-Code` 时生效，单看像是能绕过。真正的强制在中间件

## 修复自身踩的三个坑（都已修正）

1. **待办过滤第一版把所有人都滤空了**——认不出请求者时硬筛，测试环境当场 0 条。

2. **蓝绿脚本 `$ready` 被本地 shell 提前展开**——ssh 双引号 here-string 里，
   远端才该展开的变量必须转义。
3. **端口轮换判据命中了容器侧端口**——`docker port` 输出 `8000/tcp -> 127.0.0.1:8001`，
   grep 8000 永远命中箭头左边，NEXT_PORT 恒为 8001，撞端口。改按宿主侧匹配。

还有一个是新加的校验自己误报：源码特征串挑了 JS 标识符
（`inspectionOnlyAttentionNodes`），压缩时被重命名。标记必须是压缩改不掉的
字符串字面量（CSS 类名、界面文案）。

# 第四部分：前端操作流程审计（2026-08-15）

目标口径改为**操作是否卡住**，安全性暂放。以监检人员身份在浏览器里逐个动作实操，
每一步都用数据库和网关日志交叉验证。

## B-1（阻断）AI 复核在界面上永远出不来结果

监检在节点上点「发起缺项预审」→「确认发起」，之后：

| 观测点 | 实际 |
|---|---|
| 界面提示 | **无**（12 秒内零反馈） |
| 右栏「当前状态」 | 仍是上一次的 `failed`，不切到新运行 |
| 数据库里的新运行 | `queued`，`promptAudit` 0 字符，`findingDrafts` 0 条 |
| 等待 45 秒后 | **仍是 `queued`**，永不推进 |

全库共 **2 条运行永久卡在 `queued`**（一条是 08-14 20:41 的，一条是本次）。

排查排除的可能：

- celery worker **是活的**（`inspect ping` 四节点在线），`inspection.ai_recheck`
  队列有 business worker 消费，队列积压为 0；
- 但 business worker 的最后一条业务日志停在 **2026-08-13 04:49**，
  之前崩在 `psycopg.errors.AdminShutdown: terminating connection due to
  administrator command`——容器显示 Up 2 days，实际两天没干过活；
- 编排模式是 `inline`（同步执行），按代码不该留下 `queued`。

更奇怪的是**同一条运行，两个来源说法不一致**：

```
API 返回  : status=waiting_human_review   （dispatch mode=inline, status=completed）
数据库    : status=queued, 无 promptAudit, 无 findings
再用 API 读: status=None
```

即执行结果没有落库。界面轮询读的是落库状态，所以**永远显示排队中**。

### 根因（08-15 查实）与修复

第一次的修法是给 `execute_review_run_inline` 包 try/finally 落库——
**线上复验依然是 `queued`**。因为 flush 抛了异常，而我在 finally 里写的是
`except Exception: pass`，把真正的根因盖了整整一轮。

在容器里不吞异常跑一遍，报错是：

```
ConcurrentPersistenceError: Concurrent persistence update detected
for ai_runs/AIRUN-1-36612F2E; reload before retrying.
```

**报错的记录和丢数据的记录不是同一条。** `review_run_state_records`
交上来的是整个聚合（review_runs / review_events / ai_runs / tree_nodes…），
其中 `ai_runs` 这次根本没被改过，只是执行期间 worker 进程写了库里那一行。
乐观并发守卫发现 baseline 与库里对不上就抛异常，**整个事务回滚**，
把 review_runs 的完成状态一起带走了。

这也解释了此前那个古怪现象：同一次运行里 review_events(16)、
review_step_runs(12)、review_tool_calls(25) 都在库里，唯独运行本身停在
`queued`——那些是执行途中 dispatcher 各次 flush 落下的，最后这次
带着完成状态的 flush 整体回滚了。

修法：**没改过的记录不写**（`unchanged_since_baseline`，Postgres 与 SQLite
两条写入路径都接上）。冲突自然不成立，真改过还撞上时守卫照旧拦——
不是把守卫关掉。finally 里的 `pass` 换成 `logging.exception`。

线上验证（08-15，走真实接口）：

```
RRUN-D958F19F99 | waiting_human_review | promptAudit 69,860 字符 | findingDrafts 1
RRUN-A519FAEC4B | queued               | 0                       | 0   ← 修复前的历史数据
```

# 2026-08-15 第四轮：写操作实操 + 用户两份新清单

这一轮开始真正**做写操作**，而不只是看落地页。第一步就撞到全局阻断。

## 最大的一条：浏览器上传 100% 失败（contractor#1 / inspection#2）

实操上传，三步走到第二步就断：

```
POST .../documents/upload-session      176ms  成功
PUT  http://127.0.0.1:19000/documents/...     Failed to fetch
```

预签名地址是 `127.0.0.1:19000`——**服务器自己的回环地址**。预签名 URL 是发给
浏览器用的，浏览器照着连的是它自己的 127.0.0.1，对任何角色、任何文件都必然失败。

库里那批「有记录、无内容哈希」的空壳文件正是这么攒出来的（141 个版本里 5 个），
而它们又让「提交」按钮一直是灰的：**整条施工方主线卡死在第一步**。

修复分两笔，都是实操验证的：

1. 预签名改用浏览器可达的地址（代码本来就支持 `AICHECK_MINIO_PUBLIC_ENDPOINT`，
   只是被写死成内网回环）。MinIO 只绑在宿主机 127.0.0.1:19000、对外不通，
   所以不新开端口，由页面同源的 nginx 按桶前缀 `/documents/` 反代进去；
   Host 用 `$http_host` 原样透传，否则 S3 签名对不上。
2. 改完仍是 400。对照实验定位：服务器侧用同一个预签名 URL curl（不带
   Authorization）返回 200，浏览器带着 Authorization PUT 返回 400——
   前端给上传 PUT **无条件**附上 JWT，而 S3/MinIO 一看到这个头就改用它鉴权、
   不再认预签名参数。按目标地址区分后通过。

实测结果：建会话 128ms → 传字节 31ms → complete 330ms，落库 `hash` 非空。
文件详情预览（contractor#3 的 Network Error）随之一并恢复。

## I-6：「正式复核」灰着不说为什么

判据本身是对的（必传资料未齐、候选证据未确认）。问题是那句解释只描述**当前选中**

和坏掉的按钮在用户眼里没有区别。改成说清还差几项资料、几条证据。

## I-5：token 预算超限（节点 24）

按键名裁剪之后仍有 103,660 字符。大头在

两个键名都不在白名单里。这与上一轮「只修了 evidenceRefs、漏掉 130 万字符」

## 施工方主线实操：上传 → 挂接（第四轮续）

上传打通之后接着走挂接，又撞到两条，都是实操才看得见的：

### C-4：上传成功的文件仍被判「本体缺失」

三步全绿（建会话 128ms → PUT 31ms → complete 330ms），MinIO 里 stat 得到 80 字节，
挂载却被拒：`DOCUMENT_BODY_MISSING`。查库：`version.hash` 为空。

`document_body_uploaded()` 只认 `version["hash"]`，而这个值原先来自**客户端**
在 complete 时声明的 `contentHash`——前端从来没填过这个字段。于是每一份走完整
上传流程的文件都停在 `hash=None`，挂载和提交一律被拒。

客户端也算不了：站点是 http，非安全上下文，浏览器 `crypto.subtle` 不可用。
何况「文件本体是否真的传上来了」本就不该以被审计方声明的值为准——
代码里原本的注释写的就是「由 complete 阶段按对象存储里的实际字节算出」，只是没实现。

按原设计补上（分块读对象算 sha256，客户端声明退为兜底）。实测：
`sha256:c8c32bd7fed4d…`、192 字节写入版本记录，**挂接随即成功**
（行变成「待提交 / V1 / 关联审核环节 16. 产品质量证明书 / 原始提交」）。

### C-5：上传成功但 OCR 失败，界面说「失败重新上传」

两处不对：事实不对（上传成功了）、指路不对（重传同一份文件，OCR 照样识别不出来）。
用户按提示重传，再看到同样的字——比不给提示更耗人。

拆成两个状态：本体没落盘才叫「失败重新上传」；本体在、识别链路挂了叫「识别失败」，
并把「重新上传」按钮从后者撤掉。**能否提交的判据不动**——那是业务决定。

## 这一轮我自己的三次测量错误（都已更正）

值得单独记：三次都是「我用错了观测方法，差点把正常行为报成缺陷」。

1. 点「确认关联」没反应 → 实际有明确的**弹窗内行内提示**（ElAlert），
   我只盯 `.el-message`（toast）；
2. 「落库 hash 非空」→ 我按 createdAt 取最新 4 条，拿到的是别的历史行，
   不是我上传的那几个。实际那三个 hash 全空——**结论完全反了**；
3. ElMessage 3 秒自动消失，我 8 秒后才读，于是「零提示」。

教训写在这里：判定「点了没反应」之前，先确认自己看的是不是它真正说话的地方。

## C-6（阻断，需配置）这台部署没有可用的 OCR 引擎

用 Scan 文件夹里的真实素材（`特种设备安装改造维修许可证-贵州化工.pdf`，678,278 字节）
重跑主线：上传成功、哈希落库（`sha256:66b96692…`）、挂接成功，但 OCR **识别失败**。

worker 日志给出确切原因：

```
mineru_ocr_extract … status: failed
diagnostics: [{code: MINERU_NOT_CONFIGURED, level: error, retryable: false, stage: submit}]
```

`AICHECK_MINERU_API_KEY` 在 `aicheck-runtime.env` 与 `aicheck-secrets.env` 里**都不存在**，
运行时里与 OCR 相关的配置只有一个视觉模型名。

库里那 128 条「已识别」不是这套部署跑出来的——按切片上的引擎标记看：

```
macos_vision_ocr_v1     4524
pymupdf_text_layer      1515
mineru_vlm               656
paddle_ocr_subprocess    483
```

都是从别处导入的历史数据。**这台服务器上，任何新上传的资料都识别不了。**

后果是链式的：识别失败 → 不能作为可定位证据 → 提交按钮禁用 → 施工方主线到此为止；
而 AI 复核依赖 OCR 证据，正式复核所需的「候选证据已确认」也就永远凑不齐。

这不是代码缺陷，是部署缺一把钥匙——需要业务方提供 MinerU API Key，
或者明确改用其他引擎。**我无法自行取得，记在这里等配置。**

## 更底层的一条：服务端时间戳不带时区

给「执行中」加时效判断之后，判据仍然不生效。逐步量下来：

```
服务器写的     2026-08-15 13:56:11   （无时区）
浏览器当时     2026-08-15 09:40 GMT-0700
按本地时区解析 → 这条运行「在 256 分钟之后」
```

差值为负，任何「已经过去多久」的判断都失效。

**影响面不止于此**：界面上所有时间（更新时间、反馈时间、截止要求）对不在
服务器时区的用户都是偏的。本次只修了停滞判断（改用响应里的 serverTime 做基准，
