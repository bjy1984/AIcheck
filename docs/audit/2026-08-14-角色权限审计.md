# 角色权限审计（2026-08-14）

线上环境 `39.108.65.148:8081`，6 个角色 × 184 个 GET 端点 = **1,104 次探测**，
全程只读，未做任何写操作（用户处于演示准备期）。

## 方法与边界

- 端点清单从 `apps/api/routes.py` 的 `@router.get` 装饰器提取，带路径参数的用线上
  真实 ID 代入（项目 `P-2026-GDLNG-002`、节点 24/2、文档 `DOC-0D9436E0` 等）。
- 判据用**业务码**而不是 HTTP 状态码。这套接口鉴权失败时返回 `HTTP 200` +
  `{"code":401|403}`，拿 HTTP 状态当判据会得到全绿的假象——审计开始前我正是这么
  误报过一次。
- **没做**：浏览器里逐角色点击 UI。登录需要在表单里输密码，我不做这个动作；
  改用会话注入也被环境的凭证保护拦下。所以本轮覆盖的是 API 授权层，
  UI 层的按钮可见性与前端路由守卫需要另行人工验证。

## F-1（高）AI 判定被一道门拦住，另一道门敞着

`/reasoning/logs` 对全部 6 个角色开放。施工方读到的内容包括：

```
节点 2 施工单位许可资质
  AI 判定结果 : 证据不足
  意见草稿    : 当前 OCR 证据不足以支撑模型输出的业务结论，已降级为待人工确认…
  推理过程    : We need answer JSON only. Need produce ReviewFindingDraftList JSON…
```

同一份数据在另一条路上是被拦住的：

| 施工方访问 | 结果 |
|---|---|
| `/projects/{p}/inspection/nodes/2/ai-runs` | **HTTP 403 已拦截**（既有的 O-1 防护） |
| `/reasoning/logs` | **code 0，同样的 suggestion / opinionDraft / reasoningProcess** |

O-1 那条防护的业务意图很清楚：**被检方不该读到监检方的 AI 判定过程**。
`/reasoning/logs` 绕过了它。

缓解因素：内容确实按项目范围过滤了——施工方读到的 50 条全部落在它自己可见的
5 个项目内，没有跨项目泄露。所以这是「越权看到本项目里不该看的层级」，
不是「看到别人的项目」。

复现：以 contractor 身份 `GET /api/reasoning/logs?page=1&pageSize=50`。

## F-2（中高）全量用户目录对所有角色开放

`/users` 对 6 个角色都返回全部 12 个账号，含监检方与管理员。施工方看到的字段：

```
username, name, displayName, role, roleLabel, orgName, orgUnitName,
mobile, status, lastLoginAt, mustChangePassword, id, orgId, roleId, revision, etag
```

实例（施工方读到的监检账号）：

```
username=inspection  displayName=张工  orgName=省特检院一部
role=inspection  status=启用  mobile=（当前为空）
```

`mobile` 当前为空只是因为测试数据没填。**字段在契约里是开放的**——真实部署一旦
录入手机号，被检方就能拿到监检人员的联系方式。`mustChangePassword` 也一并暴露，
它能指出哪些账号还在用初始口令。

复现：以任意非 admin 角色 `GET /api/users`。

## F-3（中）待办完全不按角色过滤

监检方与施工方拿到的是**同一批 20 条待办，ID 逐条相同**：

```
inspection   20 条  样例: TODO-001, TODO-002, TODO-0F5E781B
contractor   20 条  样例: TODO-001, TODO-002, TODO-0F5E781B
```

待办里通常带着「谁该做什么」，这等于把各方的工作安排互相公开。
（`/messages` 也是 6 角色同数，但只有 2 条，样本太小，未下结论。）

复现：分别以两个角色 `GET /api/todos` 比对 ID 集合。

## F-4（中）7 个监检专用节点端点对施工方 / 建设方开放

以下端点路径里带 `/inspection/`，但 contractor 与 owner 均可读（code 0）：

```
/projects/{p}/inspection/nodes/{n}/review-log            监检的复核过程
/projects/{p}/inspection/nodes/{n}/evidence-chain        证据链
/projects/{p}/inspection/nodes/{n}/fact-corrections      监检对 OCR 事实的人工修正
/projects/{p}/inspection/nodes/{n}/live-status
/projects/{p}/inspection/nodes/{n}/date-compare
/projects/{p}/inspection/nodes/{n}/standards
/projects/{p}/inspection/nodes/{n}/rules/current-version
```

其中 `review-log` 与 `fact-corrections` 性质与 F-1 相同：被检方读到监检方的
工作过程。后四个（标准、规则版本、日期比对）可能是有意公开的——**需要业务确认**。

同一节点下的 `ai-runs`、`review-opinions`、`review-workspace`、
`review-sessions/active` 对 contractor/owner 都是 403，说明**拦截规则是逐个端点
写的，不是按前缀统一施加的**——所以新增端点默认是开放的，漏一个就多一个口子。

## F-5（低，待确认）fde 角色多处读到 0 条

`/projects`、`/todos`、`/messages`、`/reasoning/logs` 对 fde 均返回 code 0 但内容为空。
可能是有意隔离（FDE 控制台只看自己的域），也可能是过滤条件写错导致控制台空白。
**需要业务确认预期**。

## F-6（低）两套拒绝机制并存

435 次用业务码 403（HTTP 200 + `{"code":403}`），31 次直接用 HTTP 403。
两者混用在 15 个端点上，前端的错误处理路径不同——一个会显示友好提示，
另一个可能被当成网络异常。不是安全问题，是体验与可维护性问题。

## 确认正常的部分

- **零 5xx**：1,104 次探测没有一次服务端错误。
- **项目范围隔离有效**：inspection 10 个项目 / contractor 5 / ndt 5 / owner 6，
  且推理日志未越出各自项目范围。
- **核心监检端点隔离有效**：`ai-runs`、`review-opinions`、`review-workspace`、
  `review-sessions/*`、`archive`、`reports` 对被检方均已拦截。
- **管理与 FDE 端隔离有效**：`/admin/*`、`/fde/*` 对非对应角色全部 403。
