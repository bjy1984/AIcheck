## 2. 怎么更新远程服务器

只有一条路：`deploy_to_server.sh`。别手工改服务器上的文件。

### 标准命令

```bash
# 只更新后端并重启 API（最常用）
AICHECK_DEPLOY_HOST=aicheck-prod-new bash backend/scripts/deploy_to_server.sh --backend
```

```bash
# 只更新前端静态资源（本地构建后 rsync）
AICHECK_DEPLOY_HOST=aicheck-prod-new bash backend/scripts/deploy_to_server.sh --frontend
```

```bash
# 全量：代码 + 前端
AICHECK_DEPLOY_HOST=aicheck-prod-new bash backend/scripts/deploy_to_server.sh
```

> ⚠️ **第一个坑**
>
> `AICHECK_DEPLOY_HOST` 必须带。脚本默认 `HOST=dev-bjy`，这个名字在本地 ssh 配置里不解析，脚本会「跑完」但其实一台机器都没连上，看着像成功。正确的主机名是 `aicheck-prod-new`。

### 脚本做了什么

- 目标机**没装 git**（无 sudo 装不上），也没有 git-receive-pack，所以不能 push。脚本用 `git archive` 导出 HEAD 的精确树 → 传输 → 服务器侧解包并 commit 进本地 git 仓库，版本仍可追溯、可 diff、可回滚。
- docker hub 与 ghcr 在该网络不可达，镜像走 `docker.m.daocloud.io`。
- 部署后脚本自己跑探针，最后打印 `==> 部署完成（<commit>）`。看到这行且探针全绿才算成功。
- 网络不稳，ssh 偶尔断。断了就重跑，脚本是幂等的。建议包一层重试。

### 凭证与运行时配置

> 🚫 **两条硬规矩**
>
> - 凭证只在服务器上的 `/home/dev-bjy/aicheck-secrets.env`，**不要拷到本地、不要写进仓库、不要贴进对话**。
> - `/home/dev-bjy/aicheck-runtime.env` 是 `backend/deploy/build_runtime_env.py` 生成的，**不要手工编辑**。要改运行时配置就改生成脚本再部署，否则下次部署会被覆盖，而且拓扑漂移检查会报「声明与现实不一致」。

### 回滚

服务器侧有本地 git 仓库，`git log` 能看到历次部署。回滚就是把本地仓库切回目标 commit 再重启容器；或者本地 `git checkout <旧commit>` 后重新跑一次部署脚本（更稳妥，因为镜像与 runtime.env 会一并重建）。

## 3. 怎么跑测试

本机跑不了，用一次性容器；**绝不能**钻进生产容器跑。

> 🚫 **先说不能做的**
>
> 本机装不上 `psycopg` / `temporalio` / `fitz`，任何 python 版本都装不全，`pytest` 直接 collection error。**不要因为图省事就 `docker cp` 把测试拷进正在服务的 `aicheck-api` 容器去跑**——那等于在生产上改文件。这个错我在 2026-09-08 犯过一次，事后只能起一个同镜像的临时容器把原文件 cp 回去、用 root 容器删残留，再用 md5 与 `git show <部署commit>:<path>` 比对确认还原干净。

### 标准命令

```bash
# 全量
AICHECK_DEPLOY_HOST=aicheck-prod-new bash backend/scripts/run_tests_in_container.sh tests
```

```bash
# 单个文件 / 目录，参数直接透传给 pytest
AICHECK_DEPLOY_HOST=aicheck-prod-new bash backend/scripts/run_tests_in_container.sh tests/test_regulatory_tables.py
```

```bash
# lint / import 类改动，先用这个（24 秒暴露全部 ImportError）
AICHECK_DEPLOY_HOST=aicheck-prod-new bash backend/scripts/run_tests_in_container.sh tests --collect-only -q
```

脚本把仓库追踪文件 rsync 到部署主机的 `/tmp/aicheck-ws`，用生产同款镜像起一个 `--rm` 容器跑，跑完即弃，碰不到生产。首次同步约 404 MB，慢链路上要二三十分钟；之后是增量，只传改动。

### 这个环境的固定基线

**2940 通过 / 8 失败 / 65 跳过。** 失败数超过 8 才需要看。那 8 条不是回归：

| 条数 | 测试 | 原因 |
|---|---|---|
| 3 | test_release_manifest | 生产镜像里没有 `git` 可执行文件（镜像不装它是对的） |
| 2 | test_local_startup_script、test_start_local_dev | 镜像里没有 `zsh` |
| 3 | test_import_offline_test_projects ×2、test_contract ×1 | 用到 `test2/` 目录的图纸 PDF，同步时排除了（58 MB） |

> ⚠️ **如果你看到几十条失败**
>
> 先别当回归。**九成是权限。** 容器以 uid 999 往工作区写文件，主机用户删不掉也改不动权限，下一轮就会冒出成片的 `PermissionError: /ws/output/...` 和 `FileNotFoundError`。2026-09-08 这一天我因为它误判了三次（分别看到 96、91、57 条失败）。脚本里已经加了用 root 容器放权的步骤；如果你手工 `docker run`，自己记得先跑下面这条。

```bash
ssh aicheck-prod-new "docker run --rm -u root -v /tmp/aicheck-ws:/ws aicheck-api:local sh -c 'chmod -R a+rwX /ws/output /ws/tmp /ws/backend/data /ws/backend/ocr_eval'"
```

## 4. 必须知道的坑

按踩过的代价排序。前三条会直接让你损坏东西或误判。

### 一、四个再导出枢纽不能盲目 `ruff --fix`

这几个文件里「未使用」的 import 其实是给别处用的再导出，ruff 只看本文件，会全删：

- `libs/review_orchestrator/_shared.py`
- `libs/review_orchestrator/execution.py`
- `libs/review_orchestrator/rule_planners.py`
- `apps/api/routes.py` —— 测试 `from apps.api.routes import EmbeddingClient`，删掉直接 51 个收集错误

更隐蔽的一类：测试用 `monkeypatch.setattr("libs.review_orchestrator.rule_planners.qwen_runtime_client", ...)` 按字符串路径打桩，ruff 完全看不见这种引用。对这四个文件只跑 `ruff check`，改动用精确替换；其它文件可以 `--fix`，但改完必须跑一次 `--collect-only`。

### 二、`业务规则.md` 有两份，必须逐字一致

仓库根目录一份、`rules/` 下一份。`test_business_node_numbering_matches_checklist_everywhere` 校验两份完全相同。只改一份就会红，报错是 `root 业务规则.md is not identical to rules/业务规则.md`。改完记得：

```bash
cp rules/业务规则.md 业务规则.md
```

### 三、审查点 id 的哈希把表格行序算进去了

在资料表中间插一行，会让后面所有审查点 id 整体位移。2026-09-07 已做过一次生产重键迁移把错位的 id 改对（备份在服务器 `/home/dev-bjy/aicheck-backup-mrp-20260907-223645.dump`），但**根因还在**。在修掉根因之前，往资料表中间插行是危险操作；只在表尾追加是安全的。

### 四、生产审查点脚本必须带 `--ids`

`retire` / `align` 这类脚本不带显式 `--ids` 会作用到全量，别在生产上裸跑。

### 五、棘轮不计注释行

`scripts/monolith_baseline` 的行数棘轮不把注释算进去，删注释救不了行数。

### 六、别用无界轮询等后台结果

`until ...; do sleep; done` 跑满 600 秒会被自动转后台然后继续跑，堆成一片假「卡死」。测试用 `ssh <host> "nohup docker run … > /tmp/run_x.txt 2>&1 &"` 在服务器端起，再做**一次**有界检查。这是我今天效率最差的地方。

## 5. 现在有什么问题

按影响排序。第一条是唯一的「红灯」。

### P0 · CI 从 2026-08-14 起一直红，pytest 从未在 CI 跑过

失败点在 `Ruff ratchet` 那一步，`Run backend suite with real PostgreSQL` 根本没开始：

```
✓ Install backend and test dependencies
✓ Verify immutable migration manifest
X Ruff ratchet (no new lint findings)     ← 停在这里
  Run backend suite with real PostgreSQL   ← 从未执行
```

原因：`backend/ruff-baseline.json` 最后一次更新在 2026-08-14，之后进了 329 次提交、加了几十个文件。棘轮的逻辑是「不许新增告警」，当前 **694 条对基线 337 条**，每次推送都被拦。

**我探过的路和结论**（可以直接接着做）：新增 362 条，其中 F401 占 180、I001 占 54、RUF100 占 49，合计 283 条可自动修。分布是 tests 27 个文件、scripts 24、libs 23、apps 5。做法是：

1. 装 CI 同版本 `ruff==0.16.2`（本机默认版本结果不一样）；
2. 对**除四个再导出枢纽以外**的文件跑 `ruff check --select F401,I001,RUF100 --fix`；
3. 跑 `--collect-only`（24 秒）确认没有 ImportError，有就把被删的名字加回并标 `# noqa: F401 - re-export`；
4. 剩下的 BLE001（82 条）、DTZ007、EXE001 等逐条看是真问题还是误报；
5. 最后 `python -m scripts.ruff_baseline --update` 收基线，跑一次全量，推送看 CI。

这一摊我做到第二步时用户叫停了，改动已全部撤销，工作区干净。

### 已修但值得知道 · 一个潜伏三周的 NameError

`apps/worker/tasks.py:2618` 用了 `run.get("storageBucket")`，而 `parse_document` 里根本没有 `run` 这个名字（同函数别处取的是 `version`）。`official_shadow` 开关一开就是 NameError，整条 OCR 任务挂掉。平时跑不到这个分支所以没炸。

**ruff 的 F821 本来能抓，但 CI 红着，没人看见**——这就是上一条的实际代价。已修，并加了用符号表做名字解析的回归测试（验证过修复前红、修复后绿）。

### 数据缺口 · 还没录的标准内容

- GB/T 14976-2025 表 2 化学成分：32 个牌号里 6 个有，其余 26 个待补（力学与热处理已全）
- GB/T 13296-2023 表 3 化学成分未录（力学、硬度、热处理、密度已全）
- NB/T 47014-2023 附录 C~F 未录
- GB/T 9711-2023：业务包里没有任何规则引用它，且手上扫描件 OCR 质量差，**故意不抄**；哪天有规则要用再按几何重建法重做

前三项目前**没有任何判定在用**，优先级低于修 CI。

- **N-21/N-22 型式试验报告平台核验**：公示平台不提供按报告编号的查询接口，只能按制造单位加产品类别检索后人工比对。规则里已写明「检索为空判证据不足，不判不符合」。

## 关于这份文档的诚实说明

2026-09-08 这一天我的效率很差：验证方式选错了——lint 类改动本该用 24 秒的 `--collect-only` 迭代，我却每次都跑 8 分钟的全量；等结果用了无界轮询，堆出一片看着像卡死的后台任务；同一个权限坑踩了三次，每次都要重跑一轮才发现「几十条失败」其实不是回归。技术结论是可靠的、都验证过，但过程绕了很多弯路。这些教训都写进 §3 和 §4 了，接手的人不用重新摸一遍。

文中每条事实都能复核：提交号可 `git show`，测试数字可重跑，CI 状态可 `gh run list --workflow=backend-quality.yml`。
