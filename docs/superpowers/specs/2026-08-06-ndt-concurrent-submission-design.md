# NDT 单文件并发提交修复设计

## 背景

无损检测资料上传后，OCR 在后台异步更新文档状态。当前 NDT 单文件提交接口使用 API 进程内较早加载的文档对象，并在请求结束时执行全状态持久化。若 OCR 已先更新同一文档，提交会触发 `Concurrent persistence update detected`，随后被通用异常处理错误包装为 `EXTERNAL_TOOL_FAILED`。

## 目标

- 提交审批前取得数据库中的最新文档、版本和业务规则关联状态。
- NDT 单文件提交只持久化本次实际修改的记录，不触发无关集合的全状态刷新。
- 并发冲突返回明确、可操作的业务错误：“文件状态已更新，请刷新后重试”。
- OCR 状态继续作为辅助信息，不成为单文件提交门禁。

## 方案

### 最新状态读取

NDT 单文件提交进入业务校验前，针对当前租户重新加载提交所需集合的最新持久化状态，至少覆盖：文档、文档版本、业务规则关联、项目节点、提交记录和待办记录。重新加载后再解析请求中的 `documentId` 与 `bindingIds`，避免使用 OCR 更新前的对象和持久化基线。

刷新范围必须保持在本次提交依赖的集合内，不得刷新知识库向量、OCR 产物等无关大集合。

### 精确范围持久化

NDT 单文件提交成功后，为请求设置精确持久化记录清单，仅包含：

- 被提交的文档；
- 该文档当前全部业务规则关联；
- 本次状态变化涉及的项目节点；
- 新建的 NDT 单文件提交快照；
- 新建的监检待办；
- 本次操作生成的审计记录；
- 当前幂等键记录（如存在）。

上传完成阶段生成的业务规则关联也必须加入上传会话的精确持久化清单，防止刷新后再次出现“尚未关联”。

### 并发冲突响应

持久化层的 `Concurrent persistence update/insert` 异常在 API 层转换为业务冲突响应，HTTP 状态使用 409，错误原因使用专用代码 `RESOURCE_STATE_CHANGED`，用户提示固定为“文件状态已更新，请刷新后重试”。不得再进入兜底的 `EXTERNAL_TOOL_FAILED`。

该转换只处理已识别的并发持久化冲突；未知异常仍保留现有兜底处理与服务端日志。

## 数据流

1. 前端提交单个文件及其全部业务规则关联 ID。
2. 后端刷新该提交所需的最新持久化集合。
3. 后端重新读取并校验文档、版本、关联状态和角色权限。
4. 后端在内存中生成状态变更、提交快照、待办和审计记录。
5. 中间件只写入本次操作的精确记录。
6. 若步骤 2–5 仍检测到并发状态变化，返回明确的 409 业务冲突。

## 测试

- 上传完成的精确持久化记录必须包含新建业务规则关联。
- 模拟 OCR 在提交前更新文档，提交接口重新加载最新状态后仍能成功提交。
- NDT 单文件提交的持久化清单不得包含无关集合。
- 模拟持久化基线冲突，接口返回 `RESOURCE_STATE_CHANGED` 和明确中文提示，不返回 `EXTERNAL_TOOL_FAILED`。
- 现有“无 OCR 门禁、逐文件提交、规则调整后提交”测试继续通过。

## 非目标

- 不修改 OCR 调度、识别算法或识别完成条件。
- 不放宽 NDT 资料类型和业务规则合法性校验。
- 不改变其他业务模块的提交持久化策略。
