# 上传状态、后台处理状态与资料提交解耦设计

日期：2026-08-19

## 背景

施工方和无损检测机构上传工程资料后，文件本体只要已经完整落库，就应当视为上传成功，并允许用户提交。OCR、切片、向量化和后续自动分类属于后台异步处理，不应延长用户的上传流程，也不应成为资料提交的前置条件。

当前实现把两件事混在了一起：

- 前端只有在 OCR、切片、向量化全部完成时才把文件显示为“上传成功”；
- 后端施工方提交接口会再次检查同一处理链路，任一环节未完成或失败都会拒绝提交。

这导致文件本体已经落库、用户也能预览原件时，仍然因为后台处理排队或失败而不能提交。

## 已确认的产品边界

施工方平台和无损检测机构平台继续保留不同的页面、业务说明和资料组织方式。二者可以复用底层状态模型，但不合并成同一套业务界面。

资料类别提醒继续保留，用于告诉不同角色应准备哪些工程资料、当前缺少哪些资料。类别提醒不是上传入口，也不是文件上传或提交的必填条件。

本阶段只完成以下两项：

1. 拆分“上传状态”和“后台处理状态”；
2. 取消 OCR、切片、向量化对资料提交的阻塞。

本阶段不调整施工方或无损检测机构的上传入口，不移除现有资料类别提醒，也不实现 OCR 后自动分类。

## 设计原则

### 文件本体决定上传状态

上传状态只回答“文件字节是否已经完整落库”。后端现有 `document_body_uploaded()` 已经以当前版本的内容哈希为判据：上传完成阶段从对象存储实际内容计算并写入哈希，没有哈希的空壳记录不能视为上传成功。

上传状态定义为：

| 状态 | 判据 | 用户动作 |
| --- | --- | --- |
| 上传中 | 当前页面正在传输文件，尚未调用完成确认 | 等待或取消 |
| 上传成功 | 当前版本有经过完成阶段确认的内容哈希 | 可以预览、关联和提交 |
| 上传失败 | 上传中断、完成确认失败，或台账接口明确返回 `bodyUploaded=false` | 重试上传 |

上传抽屉中的“上传中”由当前上传会话的本地进度表达。文件进入资料台账后，接口必须为每一行返回明确的 `bodyUploaded` 布尔值：`true` 表示上传成功，`false` 表示上传未完成或失败，需要重新上传。第一阶段继续使用这个权威字段，不根据 OCR 状态猜测上传结果。

### OCR、切片和向量化决定后台处理状态

后台处理状态只回答“该文件能否用于自动分类、检索和 AI 审查”，不回答“能否提交”。

聚合状态定义为：

| 状态 | 判据 |
| --- | --- |
| 等待处理 | OCR、切片或向量化尚未开始 |
| 处理中 | 任一后台环节处于排队或执行状态，且没有失败 |
| 处理完成 | OCR 可用、切片完成、向量化完成 |
| 处理异常 | OCR、切片或向量化任一环节失败 |

文件列表可以展示聚合状态；资料详情继续展示 OCR、切片、向量化的具体状态和失败原因，供监检人员、管理员或 FDE 排查。

### 提交只依赖文件本体和业务权限

资料提交只校验：

- 当前版本的文件本体已经完整落库；
- 文件属于当前项目并且当前用户有提交权限；
- 文件或挂载关系处于允许提交、补正或重新提交的业务状态；
- 文件未被重复提交或被不可变审查状态锁定。

以下状态不得阻塞提交：

- OCR 排队中、识别中或识别失败；
- 切片未开始、处理中或失败；
- 向量化未开始、处理中或失败；
- 自动分类尚未开始、处理中或低置信度。

文件本体没有落库仍然必须拒绝提交，避免只创建了目录记录的空壳资料进入监检流程。

## 前端设计

### 状态模型

`frontend/src/utils/documentPipelineStatus.ts` 不再用一个 `DocumentBusinessStatus` 同时表达上传和后台处理。

拆分为两个独立派生函数：

- `documentUploadStatus(file)`：台账数据只根据 `bodyUploaded` 返回上传成功或上传失败，上传抽屉继续用自己的传输进度表达上传中；
- `documentProcessingStatus(file)`：根据 `currentOcrStatus`、`sliceStatus`、`vectorStatus` 返回等待处理、处理中、处理完成或处理异常。

`canSubmitDocument(file)` 只依赖 `documentUploadStatus(file) === '上传成功'`。

`bodyUploaded` 缺失时显示“上传状态未知”并禁用提交，不在前端根据 OCR 状态猜测。施工方和无损检测机构使用的项目文件接口必须继续为每一行返回明确的 `bodyUploaded` 布尔值。

### 施工方界面

施工方页面保留“资料分类与上传指引”、缺项提醒和需补正提醒。

资料台账分别展示：

- 上传状态：上传中、上传成功、上传失败；
- 后台处理：等待处理、处理中、处理完成、处理异常；
- 业务状态：未关联、待提交、已提交、需补正、已通过。

上传成功后提交按钮立即可用。后台处理异常时，文件仍可提交；状态提示说明“文件已上传，可正常提交；自动识别暂不可用”，不得提示用户重新上传同一文件。

### 无损检测机构界面

无损检测机构继续使用自己的检测任务、底片、检测记录、报告和补正界面。资料类别提醒和适用业务规则提醒继续存在。

普通工程文件或无损检测资料的提交不再等待 OCR、切片或向量化。底片登记、检测记录完整性、报告与底片关联等结构化业务校验不属于后台文档处理状态，本阶段不取消这些业务校验。

换言之：取消的是 AI 技术处理前置，不是无损检测业务数据自身的必填和一致性要求。

## 后端设计

### 施工方提交

`POST /projects/{project_id}/submissions` 的项目资料池提交和节点资料提交，不再调用 `blocked_pipeline_documents()` 拒绝施工方提交。

接口继续调用现有文件本体校验，确保当前版本有完整内容。接口返回、提交快照、待办创建、幂等和并发控制保持不变。

### 无损检测资料提交

无损检测工程文件的提交入口同样移除 OCR、切片和向量化完成校验。

无损检测报告提交中与报告记录、底片、检测记录和授权节点相关的业务就绪校验继续保留。现有 `ndt_report_readiness()` 中的 `NDT_REPORT_OCR_NOT_COMPLETE` 和 `NDT_REPORT_FIELDS_MISSING` 改成非阻塞后台处理提示；人工填写或已有报告记录中的报告编号、检测方法等业务字段仍按原规则校验。

### 后台处理

上传完成后仍然正常派发 OCR、切片和向量化任务。取消提交阻塞不能取消后台任务、失败重试、可观测性或告警。

资料可以在后台处理完成前进入监检资料池。AI 自动审查必须继续等待自身所需的 OCR、切片和向量化产物；“允许提交”不等于“立即启动 AI 审查”。后台处理完成后，由既有调度或后续自动分类阶段继续触发 AI 能力。

## 错误处理

| 场景 | 用户可否提交 | 界面提示 |
| --- | --- | --- |
| 文件本体未落库 | 否 | 上传失败，请重试 |
| OCR 排队或识别中 | 是 | 文件已上传，后台处理中 |
| OCR 失败 | 是 | 文件已上传，可提交；自动识别异常 |
| 切片或向量化失败 | 是 | 文件已上传，可提交；AI 处理异常 |
| 业务状态不允许重复提交 | 否 | 文件已提交或当前状态不可提交 |
| 无损检测结构化业务数据缺失 | 视具体业务动作而定 | 明确指出缺失的报告、底片或检测记录字段 |

批量提交保持现有原子语义：批次中只要存在文件本体未落库的条目，整批拒绝并列出对应文件；OCR、切片或向量化异常不得进入这份阻塞清单。

## 数据与审计

本阶段不修改提交快照结构，不迁移已有分类字段。

后台处理状态变化不修改提交时间、提交人或提交文件版本。提交后发生 OCR 重试、向量重建或处理状态变化，应继续写入任务和审计记录，但不得生成新的业务提交记录。

## 测试策略

### 前端单元测试

- `bodyUploaded=true` 且 OCR 排队时，上传状态为“上传成功”，后台处理为“处理中”，允许提交；
- `bodyUploaded=true` 且 OCR、切片或向量化失败时，上传状态仍为“上传成功”，后台处理为“处理异常”，允许提交；
- `bodyUploaded=false` 时上传失败且不可提交；
- OCR、切片、向量化全部完成时后台处理为“处理完成”；
- 施工方资料类别提醒仍然存在；
- 无损检测机构原有角色页面和结构化业务入口仍然存在。

### 后端契约与集成测试

- 施工方可以提交 OCR 排队中的已上传文件；
- 施工方可以提交 OCR、切片或向量化失败的已上传文件；
- 文件本体没有落库时仍返回 `DOCUMENT_BODY_MISSING`；
- 项目资料池提交和节点绑定提交都遵守相同口径；
- 无损检测工程文件不被 OCR 或向量化状态阻塞；
- 无损检测报告、底片、检测记录的结构化业务校验仍然生效；
- 提交不影响后台任务继续执行；
- 幂等重放不会重复创建提交记录或待办。

## 验收标准

1. 文件上传完成确认成功后，施工方和无损检测机构都能立即提交该文件；
2. OCR、切片、向量化排队或失败不会导致提交接口拒绝；
3. 空壳文件仍然不能提交；
4. 页面能同时看到独立的上传状态、后台处理状态和业务提交状态；
5. 施工方与无损检测机构界面保持区分，资料类别提醒保持存在；
6. 无损检测结构化业务规则没有因为本次解耦被绕过；
7. 后台处理完成后仍可继续用于分类、检索和 AI 审查。

## 后续阶段

本阶段通过后，再分别设计施工方和无损检测机构各自的集中上传入口。两个入口可以复用上传组件和后台分类能力，但保留不同的角色说明、资料类别提醒和业务操作。

OCR 后自动分类、低置信度待确认、节点推荐和人工纠正属于后续独立规格，不纳入本次实施。
