# 工程资料上传、提交与后台校验解耦设计

日期：2026-08-19

## 1. 目标

施工方和无损检测机构上传工程资料后，只要文件本体完整落库，就表示上传成功，用户可以立即提交。OCR、切片、向量化、自动分类和资料内容完整性校验全部在后台继续执行，不得成为首次文件提交的前置条件。

本设计解决四个当前问题：

1. 前端把 OCR、切片、向量化全部完成才显示为“上传成功”；
2. 后端使用同一技术处理链路阻塞施工方和无损检测机构提交；
3. 无损检测提交把资料类别、资料类型和 OCR 产物当成必填条件；
4. 报告、底片、检测记录的内容完整性校验和文件提交动作混在一起。

## 2. 已确认的产品边界

### 2.1 两个平台保持区分

施工方平台和无损检测机构平台继续保留不同的页面结构、角色说明、业务提醒和资料台账。二者复用底层上传组件、状态模型和提交校验内核，但不合并成相同的业务界面。

### 2.2 资料类别是提醒和后台结果

资料类别提醒继续存在，用于说明该角色通常应准备哪些资料、当前可能缺少哪些资料。资料类别不是上传文件的必填项，也不是文件提交的必填项。

单个文件没有类别时显示“待识别”，不得根据文件名在前端显示“推测类别”。后台完成 OCR 和自动分类后再补充类别；人工确认结果优先于后续自动分类。

### 2.3 首次文件提交不等于业务内容完整

用户提交的是已经落库的原始文件版本。报告编号、检测比例、合格级别、底片关联、检测记录字段等属于提交后的业务完整性检查结果。

即使资料内容不完整，文件仍然可以提交给监检；系统随后形成“待补充项”或“风险提示”，由提交方补充或监检人员审查。

## 3. 四层状态模型

文件状态拆成四个相互独立的维度，任何界面不得再用一个“处理状态”同时表达四件事。

### 3.1 上传状态

只回答“文件字节是否完整落库”。

| 状态 | 判据 | 是否可提交 |
| --- | --- | --- |
| 上传中 | 当前上传会话仍在传输或等待完成确认 | 否 |
| 上传成功 | 当前版本有完成阶段从实际存储内容确认的哈希 | 是 |
| 上传失败 | 上传中断、完成确认失败或接口返回 `bodyUploaded=false` | 否 |
| 状态未知 | 台账接口没有返回明确的 `bodyUploaded` | 否，刷新后重试 |

后端现有 `document_body_uploaded()` 继续作为权威判据。不得用 `fileStatus`、OCR 状态或文件记录是否存在代替文件本体校验。

### 3.2 提交状态

只回答“文件是否已经进入监检业务流程”。

| 状态 | 含义 |
| --- | --- |
| 未提交 | 文件已上传但尚未提交 |
| 已提交 | 已生成提交快照并进入监检资料池 |
| 审查中 | 监检人员或 AI 正在处理 |
| 需补正 | 监检人员要求补充或替换资料 |
| 已通过 | 当前提交版本已通过 |

### 3.3 后台处理状态

只回答“系统自动能力处理到哪里”，不控制用户能否提交。

| 状态 | 判据 |
| --- | --- |
| 等待处理 | OCR、切片或向量化尚未开始 |
| 处理中 | 任一环节排队或执行中，且没有失败 |
| 处理完成 | OCR 可用、切片完成、向量化完成 |
| 处理异常 | OCR、切片或向量化任一环节失败 |

处理异常时提示“文件已上传，可正常提交；自动识别暂不可用”，不得提示用户重新上传同一文件。

### 3.4 业务完整性状态

只回答“系统目前发现资料内容是否满足业务规则”，不控制首次文件提交。

| 状态 | 含义 |
| --- | --- |
| 待检查 | OCR 或自动分类尚未提供足够信息 |
| 检查中 | 正在执行规则和字段比对 |
| 完整 | 当前没有发现缺项 |
| 待补充 | 已发现明确缺失字段、关联或材料 |
| 待人工确认 | 识别置信度不足或规则无法自动判断 |

业务完整性结果包含规则编码、提示内容、证据来源、严重程度、检查时间和规则版本。结果变化不修改原始文件和提交快照。

## 4. 首次提交的唯一阻塞条件

施工方和无损检测机构的首次文件提交使用同一组底层阻塞条件：

- 当前文件版本的文件本体没有完整落库；
- 文件不属于当前项目或当前租户；
- 当前用户没有项目或提交权限；
- 文件版本、挂载关系或业务状态不允许提交；
- 文件已经提交且当前动作不是补正或重新提交；
- 幂等键、版本或并发校验冲突。

以下信息全部不得阻塞首次文件提交：

- 资料类别为空、待识别或低置信度；
- 资料类型为空或仍是通用类型；
- 尚未关联审核节点或业务规则；
- OCR 排队、识别中或识别失败；
- 切片、向量化未完成或失败；
- OCR 结构化字段为空；
- OCR 字段没有 bbox；
- 报告、底片、影像或检测记录的业务字段不完整。

批量提交保持原子语义：批次中存在文件本体未落库、越权或状态冲突的文件时，整批拒绝并列出具体文件。后台处理或业务完整性问题不进入这份阻塞清单。

## 5. 角色界面设计

### 5.1 施工方平台

保留“资料分类与上传指引”、缺项提醒和需补正提醒。分类表只承担准备说明、缺项统计和筛选作用，不再提供按类别上传的必经路径。

施工资料台账显示：

- 文件名和版本；
- 上传状态；
- 提交状态；
- 后台处理状态；
- 系统分类：待识别、系统分类、待确认、人工确认；
- 业务完整性：待检查、完整、待补充、待人工确认；
- 上传人、来源单位和更新时间；
- 预览、提交、替换、删除、查看问题等操作。

上传成功后“提交”立即可用。文件没有类别时仍可提交，提交后在监检资料池显示“分类处理中”。

### 5.2 无损检测机构平台

保留无损检测机构自己的检测任务摘要、资料类别提醒、底片、检测记录、报告和补正区域，不与施工方页面合并。

无损检测资料台账使用与施工方一致的四层状态，但增加“业务问题”入口。点击后按报告、底片、检测记录分组展示缺项，例如：

- 报告缺少报告编号或检测方法；
- RT 报告缺少检测比例或合格级别；
- RT 报告没有关联底片或数字影像；
- 底片缺少底片编号、焊口编号或检测方法；
- 检测记录缺少记录编号、焊口编号、检测方法、检测日期或评定人员。

这些问题提供“补充报告信息”“关联底片”“完善检测记录”等后续动作，但不禁用首次文件提交。

### 5.3 提交确认

提交确认只说明文件数量、文件版本和提交后的不可变规则，不要求用户选择资料类别。

如果后台已经发现业务问题，确认框可以展示“当前发现 N 项待补充，仍可提交”，但主操作仍为“确认提交”。尚未完成后台检查时显示“资料将在提交后继续识别和检查”。

## 6. 当前无损检测规则的重新归位

当前规则继续运行，但从“提交门禁”调整为“提交后完整性检查”。

| 当前规则 | 新位置 | 是否阻塞首次文件提交 |
| --- | --- | --- |
| `materialCategory=无损检测资料` | 后台分类结果 | 否 |
| `materialTypeCode` 非空且非通用 | 后台资料类型识别 | 否 |
| 适用节点 35–42 | 后台节点推荐或人工绑定 | 否 |
| OCR 完成 | 后台处理状态 | 否 |
| OCR 结构化字段存在 | 后台处理质量提示 | 否 |
| OCR 字段存在 bbox | 后台证据定位质量提示 | 否 |
| 报告关联原始文件 | 文件完整性和可追溯检查 | 否；原始文件未落库才阻塞 |
| 报告编号、检测方法 | 报告完整性待补充项 | 否 |
| RT 检测比例 | RT 报告完整性待补充项 | 否 |
| RT 合格级别或底片质量等级 | RT 报告完整性待补充项 | 否 |
| RT 底片或影像关联 | RT 关联完整性待补充项 | 否 |
| 底片编号、焊口编号、检测方法 | 底片完整性待补充项 | 否 |
| 记录编号、焊口编号、检测方法 | 检测记录完整性待补充项 | 否 |
| 检测日期、评定人员 | 检测记录质量待补充项 | 否 |
| 项目、租户、角色和节点权限 | 安全与授权门禁 | 是 |
| 文件已提交或挂载状态不允许 | 业务状态门禁 | 是 |

规则引擎可以在 OCR 完成、人工补充字段、底片关联变化或资料重新分类后重复执行。重复执行只更新完整性结果，不生成新的文件提交。

## 7. 后端设计

### 7.1 共享文件提交校验内核

提取共享的文件提交校验函数，供以下入口复用：

- 施工方项目资料池提交；
- 施工方节点资料提交；
- 无损检测普通工程资料提交；
- 无损检测报告、底片或检测记录相关文件提交；
- 补正和重新提交。

共享校验只处理文件本体、项目归属、权限、版本、状态、重复提交、幂等和并发，不读取资料类别、资料类型、OCR、切片、向量化或业务完整性结果。

### 7.2 施工方接口

`POST /projects/{project_id}/submissions` 的项目资料池提交和节点提交移除 `blocked_pipeline_documents()` 门禁，保留现有文件本体校验、权限、状态、快照、待办、幂等和并发控制。

文件没有类别、资料类型或节点绑定时，可以提交到项目资料池，等待后台分类和监检处理。

### 7.3 无损检测普通资料接口

`POST /projects/{project_id}/ndt/material-submissions` 移除以下门禁：

- `materialCategory` 必须等于“无损检测资料”；
- `materialTypeCode` 必须非空、非通用；
- `blocked_pipeline_documents()`；
- 必须已经关联全部适用业务规则。

接口补充显式的 `document_body_uploaded()` 校验。没有节点绑定时提交到无损检测资料池；已有合法绑定时可以随提交一并进入对应节点。非法、越权或属于历史版本的绑定仍然拒绝。

### 7.4 无损检测报告接口

无损检测文件的首次提交统一走 7.3 的普通资料接口。`POST /projects/{project_id}/ndt/submissions` 降为可选的“报告、底片和检测记录业务包确认”接口，不再决定原始文件有没有提交成功。

业务包确认接口只校验所引用的报告、底片和检测记录对象是否存在、属于当前项目、当前用户可见且状态允许确认，不再因为以下内容拒绝：

- OCR 未完成；
- OCR 结构化字段为空；
- bbox 缺失；
- 报告编号或检测方法缺失；
- RT 检测比例、合格级别或底片关联缺失。

尚未生成报告、底片或检测记录对象时，不影响原始文件首次提交；待 OCR、自动分类或人工补充生成这些对象后再确认业务包。已有但字段不完整的对象可以进入业务包快照，并明确标记 `completenessStatus` 和问题列表。

### 7.5 后台业务完整性检查

现有 `ndt_report_readiness()` 调整为非阻塞的 `ndt_business_completeness()`。返回结构区分：

- `processingIssues`：OCR、字段抽取、bbox、切片、向量化等技术问题；
- `businessIssues`：报告、底片、影像和检测记录内容缺失；
- `manualChecks`：系统无法可靠判断、需要人工确认的事项。

提交接口把当前检查结果作为提示写入提交快照，但不得根据 `passed=false` 拒绝首次提交。

### 7.6 后台任务和 AI 审查

上传完成后继续派发 OCR、切片、向量化和自动分类任务。允许提交不能取消任务派发、失败重试、可观测性或告警。

资料可以先进入监检资料池。AI 自动审查只有在自身依赖的处理产物就绪后才运行；处理异常时保留人工审查入口。业务内容不完整时，AI 可以输出缺项结论，不要求提交方重新提交同一原始文件。

## 8. 数据与审计

提交快照继续锁定文件版本、提交人和提交时间。提交后的 OCR、分类、字段补充和完整性检查不得修改这三个事实。

每份文件对外提供：

- `bodyUploaded`；
- `uploadStatus`；
- `submissionStatus`；
- `processingStatus`；
- `classificationStatus`；
- `businessCompletenessStatus`；
- `businessIssueCount`；
- `processingIssueCount`。

人工补充报告字段、关联底片或修改系统分类必须记录操作人、修改前后值、时间和原因。人工确认的分类不得被后台重跑覆盖。

## 9. 错误和异常处理

| 场景 | 是否可提交 | 用户提示 |
| --- | --- | --- |
| 文件本体未落库 | 否 | 上传失败，请重试 |
| 文件越权或不属于项目 | 否 | 无权提交该文件 |
| 文件已经提交 | 否 | 文件已提交，不能重复提交 |
| OCR 排队或处理中 | 是 | 文件已上传，后台处理中 |
| OCR、切片或向量化失败 | 是 | 文件已上传，可提交；自动处理异常 |
| 资料类别为空 | 是 | 待系统识别 |
| 报告字段缺失 | 是 | 已提交，报告信息待补充 |
| RT 缺少底片关联 | 是 | 已提交，待关联底片或影像 |
| 检测记录字段缺失 | 是 | 已提交，检测记录待完善 |

## 10. 测试策略

### 10.1 前端状态测试

- `bodyUploaded=true` 且 OCR 排队时，上传状态为“上传成功”、后台处理为“处理中”，提交按钮可用；
- `bodyUploaded=true` 且 OCR、切片或向量化失败时，上传状态仍为“上传成功”，提交按钮可用；
- `bodyUploaded=false` 时不可提交；
- 类别为空时显示“待识别”，不显示文件名推测类别；
- 业务问题显示在独立完整性列或详情中，不禁用提交；
- 施工方资料类别提醒继续存在；
- 无损检测机构角色页面和类别提醒继续存在。

### 10.2 后端提交测试

- 施工方可以提交 OCR 排队、识别失败、切片失败或向量化失败的已上传文件；
- 施工方可以提交没有资料类别、资料类型和节点绑定的已上传文件；
- 无损检测机构可以提交没有资料类别或资料类型的已上传文件；
- 无损检测机构可以提交 OCR 未完成或处理失败的已上传文件；
- 无损检测报告缺少报告编号、RT 比例、合格级别或底片关联时仍可首次提交；
- 上述缺项进入业务完整性问题列表；
- 空壳文件仍返回 `DOCUMENT_BODY_MISSING`；
- 越权、历史版本、重复提交和状态冲突仍然拒绝；
- 幂等重放不重复创建提交记录或待办；
- 提交后后台任务继续执行，并可更新分类和完整性结果。

### 10.3 无损检测完整性规则测试

- 报告编号、检测方法缺失生成报告完整性问题；
- RT 检测比例、合格级别、底片关联缺失分别生成明确问题；
- 底片编号、焊口编号、检测方法缺失生成底片完整性问题；
- 检测记录编号、焊口编号、检测方法、检测日期、评定人员缺失生成检测记录问题；
- OCR、结构化字段和 bbox 异常归入技术处理问题，不归入提交门禁；
- 人工补充后重新检查可以关闭对应问题，且不生成新的提交。

## 11. 验收标准

1. 文件完成落库后，施工方和无损检测机构均可立即提交；
2. 资料类别、资料类型、节点绑定、OCR、切片、向量化和内容完整性均不阻塞首次文件提交；
3. 空壳文件、越权文件、重复提交和非法状态仍然被拒绝；
4. 页面独立展示上传、提交、后台处理和业务完整性四层状态；
5. 施工方与无损检测机构界面保持区分，资料类别提醒保持存在；
6. 无损检测现有报告、底片和检测记录规则转化为可追踪的提交后问题；
7. 人工补充可以关闭问题，不需要重复上传或重新提交原始文件；
8. 后台处理完成后继续支持自动分类、检索和 AI 审查。

## 12. 实施分期

### 第一阶段：提交解耦

- 拆分上传、提交、后台处理和业务完整性状态；
- 移除类别、资料类型、节点、OCR、切片、向量化和内容完整性门禁；
- 所有文件提交入口改用共享文件本体与权限校验；
- 将现有无损检测就绪规则改为非阻塞问题列表；
- 保留两个角色现有页面和资料类别提醒。

### 第二阶段：分别改造上传入口

- 施工方平台设置自己的集中上传入口；
- 无损检测机构平台设置自己的集中上传入口；
