# 管理员新建项目全流程加固设计

## 背景

管理员在“项目立项向导”中可以完成基本信息和参建单位选择，但历史用户数据存在 `orgId` 为空或组织名称与可选单位不一致的情况。向导第 2 步只检查是否选择了单位，没有检查该单位下是否存在可授权的启用用户，因此问题直到第 3 步才暴露，并最终阻止创建项目。

同一流程还存在创建响应携带重复业务包快照、详情展示不友好，以及本地运行时 Redis 配置不明确的问题。

## 目标

1. 在第 2 步提前发现所选参建单位没有可用初始成员，并给出可操作的错误信息。
2. 保持组织授权边界：只允许选择真实隶属于所选组织且角色匹配的启用用户。
3. 缩小 `POST /api/admin/projects` 响应，不再重复返回完整 `businessPackSnapshot`。
4. 改善项目详情中的空区域、参建类型和节点范围显示。
5. 让本地开发环境在非严格模式下不依赖 Redis，同时维持严格生产模式的 Redis 强制要求。
6. 通过自动化测试和本地浏览器管理员全流程验证证明修改有效。

## 非目标

- 不根据用户角色猜测组织并自动迁移历史用户。
- 不允许跨组织兜底选择初始成员。
- 不删除或裁剪数据库中保存的 `businessPackSnapshot`。
- 不改变严格生产模式的故障关闭策略。
- 不重构与项目立项无关的管理后台页面。

## 方案

### 1. 组织与用户一致性

候选成员继续使用已有的组织 ID 优先匹配规则：当用户和所选单位都具有组织 ID 时，仅比较 ID；只有缺少 ID 时才使用规范化后的组织名称兼容历史数据。候选人还必须同时满足用户启用和角色匹配条件。

系统不自动把 `orgId=null` 且组织名称不匹配的用户分配到任意可选单位，因为这种推断可能产生跨组织越权。此类历史数据应由管理员显式修正。新增和修改用户时继续执行既有组织类型与角色约束。

### 2. 第 2 步前置校验

管理员点击第 2 步“下一步”时，除检查必需参建单位是否已选择外，还逐个检查业务类型要求角色的候选成员数。任何所选单位没有启用且角色匹配的用户时：

- 保持在第 2 步；
- 阻止进入初始授权；
- 提示具体角色和单位，例如“施工单位「施工测试」暂无启用的施工方用户，请先在组织用户中配置”；
- 不清除已填写的其他向导数据。

第 3 步和后端创建接口仍保留成员必选校验，作为纵深防御，避免绕过前端直接调用接口。

### 3. 创建响应瘦身

项目仍以完整 `businessPackSnapshot` 持久化。创建成功响应中的顶层 `project` 和 `detail.project` 改用不含 `businessPackSnapshot` 的项目摘要，保留项目 ID、版本、业务包标识、业务包版本与哈希等前端实际需要的字段。

业务包摘要继续通过现有 `businessPack` 字段返回；完整快照继续由专用快照能力读取。只调整创建接口的响应形态，避免扩大对其他详情接口消费者的影响。

### 4. 详情显示

- 区域为空、仅含空白或缺失时显示 `-`。
- 参建单位类型使用现有角色中文映射，例如 `owner` 显示“建设单位”、`contractor` 显示“施工方”、`ndt` 显示“无损检测机构”。
- 节点范围按连续区间压缩，并附节点数：`1,2,...,69` 显示为 `1–69（69 个节点）`；非连续范围显示为 `1–4、8、10–12（8 个节点）`；空范围显示 `-`。

节点范围格式化实现为独立纯函数，便于单元测试并避免模板逻辑膨胀。

### 5. Redis 与本地运行

安全边界保持不变：

- 严格生产模式：Redis 不可用时后端启动或安全会话操作失败，并返回明确的服务不可用语义；不得静默降级到内存会话。
- 本地开发模式：显式使用 `AICHECK_STRICT_PRODUCTION=false`，允许现有内存会话回退，不要求开发者先启动 Redis。

仓库提供明确的本地启动方式或配置示例，避免开发机器继承严格模式。前端登录错误映射对安全后端不可用的 `503` 给出“请启动 Redis 或使用本地开发模式”的可操作提示；其他未知错误仍使用通用错误信息。

## 数据流

1. 管理员填写基本信息并选择参建单位。
2. 前端按所选单位、角色和启用状态计算候选成员。
3. 点击下一步时，前端验证每个要求角色至少有一名候选成员。
4. 校验通过后进入初始授权；管理员为每个角色选择成员。
5. 后端再次验证成员、组织、角色和节点授权关系。
6. 后端保存包含完整业务包快照的项目，但返回不含快照的创建结果。
7. 前端打开项目详情并使用中文类型、空值占位和压缩节点范围展示。

## 错误处理

- 参建单位无候选成员：第 2 步就地提示，不调用创建接口。
- 初始成员未选择：第 3 步继续阻止提交。
- 成员组织或角色不匹配：后端拒绝请求并返回业务校验错误。
- 本地非严格模式 Redis 不可用：使用内存会话继续开发。
- 严格生产模式 Redis 不可用：返回明确服务不可用错误，不降级。

## 测试策略

### 前端单元测试

- 所选组织没有启用的匹配角色用户时，第 2 步校验失败并包含角色和组织名称。
- 正确 `orgId` 下的启用用户允许进入第 3 步。
- 跨组织、禁用或角色不匹配的用户不计入候选人。
- 节点范围连续、离散和空值格式化正确。
- 区域空值和参建类型中文映射正确。
- 安全服务 `503` 显示可操作的 Redis/本地模式提示。

### 后端测试

- 创建项目仍保存完整 `businessPackSnapshot`。
- 创建响应的 `project` 与 `detail.project` 均不含 `businessPackSnapshot`。
- 响应仍包含前端需要的业务包版本、哈希和创建节点数量。
- 成员组织或角色不匹配时创建请求被拒绝。
- 非严格模式允许 Redis 缺失；严格模式保持故障关闭。

### 浏览器验收

使用管理员账号在本地浏览器完成以下路径：

1. 区域留空进入下一步。
2. 选择无可用用户的单位时在第 2 步收到明确提示。
3. 选择具有启用成员的建设、施工、无损检测和监检单位。
4. 在第 3 步为所有要求角色选择初始成员。
5. 成功创建项目并打开详情。
6. 确认空区域显示 `-`、参建类型中文化、69 个节点显示为压缩范围。
7. 检查创建请求响应中不存在完整快照且响应体显著缩小。

## 验收标准

- 管理员不会在进入第 3 步后才首次发现所选单位无人可选。
- 系统不会跨组织自动配人或扩大授权范围。
- 合法数据可完成立项，区域保持选填。
- 创建响应不含重复完整快照，项目持久化快照不受影响。
- 项目详情三个展示问题全部修正。
- 本地非严格模式可在 Redis 未运行时登录；严格生产模式仍强制 Redis。
- 相关前后端测试通过，且本地浏览器全流程通过。
