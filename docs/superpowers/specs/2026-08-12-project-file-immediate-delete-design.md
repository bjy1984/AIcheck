# 项目文件即时删除设计

## 问题

项目文件删除接口在服务器数据量较大时需要较长时间完成持久化。前端在接口返回后还会
重新加载整个工作台，并且在此之前保留原有 `projectFiles`，因此用户确认删除后仍会在
列表中看到该文件一段时间。

## 设计

前端采用可回滚的乐观删除：用户确认后，立即从当前节点包的 `projectFiles` 中移除目标
文件并保存其原始位置。接口成功时保持移除状态，提示成功，并在后台静默重新加载当前
节点包以校准文件数据与统计；接口失败或返回空响应时，将文件恢复到原位置并展示错误。
取消确认不改变本地状态。

后端保持现有级联删除范围和审计语义不变，但为删除请求设置精确的
`flush_state_keys`。持久化只扫描删除函数实际可能修改的集合以及 `audit_logs`，不再扫描
整个内存状态库。幂等结果仍由现有中间件持久化。

不采用以下方案：

- 等接口成功后再移除列表行：仍会暴露服务器响应延迟。
- 删除成功后重新加载完整工作台：会继续请求上下文、树、报告和审计等无关数据。
- 只做前端优化：界面虽即时响应，但后台接口仍长期占用请求和持久化资源。
- 改为物理数据库级联：改动范围过大，并会绕过现有内存状态、审计和幂等机制。

## 错误处理

- 接口抛错或返回空响应时恢复原文件，恢复操作去重，避免重复插入。
- 后台静默校准失败不重新显示已由服务器确认删除的文件，也不覆盖页面级错误状态；用户
  后续刷新仍可取得权威数据。
- 后端删除权限、已提交文件冲突校验、存储对象清理和关联记录清理保持原样。

## 验证

- 前端纯函数单元测试覆盖立即移除、保持顺序、目标不存在和失败恢复去重。
- 后端路由测试确认删除请求只向持久化层传递预期状态集合，并继续验证所有关联记录删除。
- 运行前端全部单元测试、类型检查和生产构建。
- 运行后端定向契约测试，并在提交前运行相关回归测试。
- 发布后通过跳板机验证删除接口、前端静态资源版本与服务健康状态。
