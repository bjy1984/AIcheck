# 项目立项成员组织关联修复设计

## 背景

项目立项向导第二步选择参建单位，第三步按角色和单位筛选初始成员。当前前端仅使用 `user.orgName === selectedOrgName` 判断用户是否属于所选单位，后端创建项目时也使用相同的名称字符串校验。单位改名、历史导入或测试数据名称不一致时，即使用户的 `orgId` 仍正确，施工方和无损检测人员也会被错误排除。

## 目标

- 所选参建单位与用户均有 `orgId` 时，使用 `orgId` 判断组织归属。
- 任一侧缺少 `orgId` 的旧数据，继续按规范化后的单位名称兼容。
- 前端显示为可选的成员必须能够通过后端立项校验。
- 不改变业务类型、角色、启用状态和节点授权规则。

## 方案

### 前端候选人筛选

向导仍保存现有单位名称字段，以保持创建项目接口兼容。筛选候选人时先通过单位名称找到当前启用的组织记录：

1. 用户角色必须与向导角色一致。
2. 用户状态必须为“启用”。
3. 用户和组织都有 `orgId` 时比较 ID。
4. 缺少 ID 时比较去除首尾空白后的单位名称。

切换参建单位时使用同一归属判断清除不再属于该单位的已选用户，避免展示和清理逻辑不一致。

### 后端立项校验

后端根据请求中的参建单位名称解析组织记录。校验初始成员时：

1. 保留用户存在、启用状态和角色一致性检查。
2. 用户与所选组织都有 ID 时比较 ID。
3. 缺少 ID 时回退到规范化后的名称比较。
4. 不匹配时继续返回现有成员组织不一致错误。

### 数据投影

管理员用户投影在能够通过 `orgId` 找到组织时，以组织当前名称作为规范显示名称；找不到组织时保留用户记录中的旧名称。这减少单位改名后继续输出旧名称的概率，同时兼容孤立历史记录。

## 测试

- 后端回归测试：构造用户 `orgId` 正确但 `orgName` 为旧名称，项目立项应成功。
- 后端负向测试：用户 `orgId` 指向其他组织，即使名称相同或旧名称相近也必须拒绝。
- 前端回归测试：同角色启用用户 `orgId` 与所选组织一致时应出现在候选列表；不同组织用户不得出现。
- 运行目标后端测试、前端类型检查和相关端到端测试。

## 非目标

- 不修改立项向导步骤、字段布局或节点范围。
- 不批量改写已有项目和成员记录。
- 不放宽角色或启用状态要求。
