# 监检端已提交资料视图与提交生命周期修复设计

## 背景

监检工作平台当前直接读取节点资料包中的整个项目文件库。文件完成上传后，即使尚未提交审查，也会进入监检端列表；页面同时使用文件版本上传时间或文档更新时间作为“上传时间”，不能表达正式提交审查的时间。普通施工资料提交到项目资料池后，文档本身仍可能保持“已上传”，又会造成已提交资料状态显示错误。

系统内同时存在施工方项目资料池提交、施工方节点资料提交和无损检测机构单文件提交三条路径。三条路径的提交状态和时间分别存放在文档、挂载及提交记录中，监检端缺少统一的正式提交资料读模型。此外，系统仍保留提交方撤回已提交资料的接口和界面入口，与“一旦提交审查不得撤回，只能由监检人员退回后重新提交”的业务规则冲突。

## 目标

- 只有正式提交审查的施工方和无损检测机构资料才能进入监检工作平台。
- 上传、OCR 处理和正式提交是相互独立的生命周期；OCR 更新不得改变监检可见性或提交时间。
- 监检端统一展示提交状态和提交审查时间，不展示仅上传状态和上传时间。
- 提交方提交后不得撤回；只有监检人员可以退回补正。
- 退回后允许提交方修改资料并重新提交，每次提交形成独立、可追溯的提交记录。
- 同一文件只暴露已经提交的业务规则或节点范围，不泄露同文件上的草稿挂载。

## 业务规则

### 上传与可见性

文件上传完成后保存为提交方草稿。`fileStatus = 已上传`、`poolSubmissionStatus = 未提交` 或仅有 `bindingStatus = 草稿挂载` 的文件不得出现在监检端接口、列表数量、搜索结果或分页结果中。

监检端可见资料必须至少满足下列一个条件：

- 施工方项目资料池：存在有效的项目级 submission，且文档 `poolSubmissionStatus = 已提交`；
- 施工方节点资料：至少一个挂载属于有效 submission，且挂载状态为 `已提交`、`需补正` 或 `已通过`；
- 无损检测单文件资料：存在有效的 `ndt-material` submission，文档 `fileStatus = 已提交审批`，且至少一个提交范围内的挂载状态为 `已提交`、`需补正` 或 `已通过`。

资料有多个挂载时，监检读模型只返回已提交范围内的挂载。未提交的业务规则和节点挂载仍只对提交方可见。

### 提交状态与时间

监检端使用统一字段 `reviewStatus`，不直接展示底层 `fileStatus`：

- `待审查`：最新有效提交尚未形成监检结论；
- `需补正`：监检人员已退回，等待提交方重新提交；
- `已重新提交`：退回后产生了新的有效提交；
- `已通过`：提交范围内的审查已通过；
- `部分待审`：同一文件的已提交挂载处于不同审查状态。

统一字段 `submittedAt` 必须来自正式 submission：

- 项目资料池提交使用项目级 submission 的 `submittedAt`，并与 `poolSubmittedAt` 保持一致；
- 节点资料提交根据 submission 的 `bindingIds` 关联文档，使用该有效提交的 `submittedAt`；
- NDT 单文件提交使用 `ndt-material` submission 的 `submittedAt`，并与文档 `submittedAt` 保持一致。

文件版本的 `uploadTime` 和文档 `updatedAt` 不得作为提交审查时间。重新提交后，列表展示最新有效提交时间；历史提交时间保留在提交历史中。

### 禁止提交方撤回

提交方界面移除“撤回未提交”入口及相关交互。已有撤回 API 不再改变任何文档、挂载或提交记录，统一返回 HTTP 409 和业务错误 `SUBMISSION_WITHDRAW_NOT_ALLOWED`，提示“资料已提交审查，不能撤回；如需修改，请联系监检人员退回后重新提交。”

权限动作中不再向施工方或无损检测机构下发 `submission:withdraw`。删除未提交文件仍然允许；正式提交后的文件继续禁止直接删除。

### 监检退回与重新提交

监检人员退回补正时必须选择本次退回涉及的已提交挂载，填写退回原因，并在一次事务中完成：

- 创建补正记录并保存 `returnedAt`、原因、监检人员及原 `submissionId`；
- 将选中挂载更新为 `需补正`；
- 将相关节点更新为 `需补正`；
- 创建提交方待办；
- 保留原 submission 和原提交时间，不覆盖历史。

退回后，提交方只能对 `需补正` 范围调整文件或规则挂载并重新提交。重新提交创建新的 submission，通过 `previousSubmissionId` 和 `rectificationId` 关联原提交及退回记录；新 submission 使用新的 `submittedAt`。监检端继续显示该资料，但状态从“需补正”更新为“已重新提交”。

项目资料池文件如果尚未挂载到具体审查节点，不提供节点退回操作；监检人员完成资料归类或挂载后，按对应节点退回。不得通过提交方撤回接口改变项目资料池状态。

## 架构方案

### 监检专用读模型

新增监检专用查询接口，不再由监检总览直接消费共享节点资料包中的 `projectFiles`：

`GET /api/projects/{projectId}/inspection/submitted-documents`

接口仅允许 inspection 角色访问，服务端完成可见性过滤、提交记录关联、状态归一化、搜索、排序和分页。建议响应结构：

```json
{
  "items": [
    {
      "documentId": "DOC-001",
      "submissionId": "SUB-001",
      "submissionType": "node",
      "fileName": "施工组织设计.pdf",
      "fileType": "application/pdf",
      "materialCategory": "施工组织设计",
      "sourceOrgName": "施工单位",
      "submitterName": "李工",
      "reviewStatus": "待审查",
      "submittedAt": "2026-08-06T15:40:50Z",
      "submittedBindings": [],
      "currentOcrStatus": "已识别",
      "ocrReadiness": {}
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

查询服务按 submission `submittedAt` 倒序处理最新有效提交，并通过 submission 的 `documentIds` 或 `bindingIds` 解析文档。项目级 submission 直接使用 `documentIds`；节点提交通过 `bindingIds` 解析文档；NDT submission 同时校验 `documentIds` 与 `bindingIds`。接口不得仅依赖易受 OCR 更新影响的文档更新时间。

### 写模型一致性

三条提交路径都以 submission 为提交事实来源。写入提交记录、文档或挂载状态、提交时间、待办和审计日志必须使用同一个服务端时间值。项目资料池的 `poolSubmittedAt` 和 NDT 文档的 `submittedAt` 作为便捷索引保留，但读模型会校验其与最新有效 submission 的一致性。

后续如检测到旧数据只有提交状态而缺少 submission，接口不推断上传时间为提交时间。该资料不进入正式监检列表，并记录数据完整性告警，避免伪造提交时间。

### 前端展示

监检总览将“施工方/无损检测机构上传文件列表”改为“已提交审查资料”，说明文案明确仅展示已经提交监检审查的资料。搜索条件改为文件名、提交单位、提交人、资料类别和审查状态。

表格调整为：文件名、来源、提交人、资料类别、审查/OCR 状态、提交审查时间、操作。状态标签使用 `reviewStatus`，时间使用接口 `submittedAt`。空状态使用“暂无已提交审查资料”。

施工方提交批次界面、操作栏和提交历史中移除撤回按钮、撤回表单和重试撤回逻辑。历史数据中已有撤回记录仍可只读展示，确保审计追溯不丢失。

## 错误处理

- 未提交资料请求监检详情时返回 404，避免确认其存在。
- 非 inspection 角色调用监检资料接口返回 403。
- 提交方调用撤回接口返回 409 `SUBMISSION_WITHDRAW_NOT_ALLOWED`，不得产生部分状态更新。
- 监检退回未选择挂载、挂载不属于当前有效提交或已通过/归档时，返回明确的 409 业务错误。
- OCR 排队、失败或结果不完整仅作为辅助状态展示，不阻断正式提交、监检可见性或退回补正。
- 提交、退回和重新提交发生并发冲突时，返回 `RESOURCE_STATE_CHANGED`，提示刷新后重试。

## 兼容与数据迁移

- 保留文档现有上传时间和更新时间字段，仅停止在监检端将其解释为提交时间。
- 保留历史 submission、withdrawal 和审计记录，旧撤回数据只读展示。
- 对已有数据执行一致性扫描：提交状态存在但找不到 submission、submission 找不到文档或挂载、提交时间不一致的记录输出审计报告，不自动用上传时间补齐。
- 共享节点资料包继续服务施工方草稿管理，不在该接口中做监检角色专用裁剪，避免破坏上传方工作台。

## 测试策略

### 后端契约测试

- 施工方仅上传的项目资料不出现在监检查询结果。
- 施工方项目资料池提交后出现，时间等于项目级 submission `submittedAt`。
- 施工方节点资料提交后出现，时间通过 submission `bindingIds` 正确解析。
- NDT 单文件提交后出现，时间等于 `ndt-material` submission `submittedAt`。
- 同一文件混合已提交和草稿挂载时，只返回已提交挂载。
- OCR 在上传后或提交后更新 `updatedAt`，提交审查时间保持不变。
- 提交方撤回接口返回 409，所有状态保持不变。
- 监检退回将目标挂载更新为 `需补正` 并生成补正记录和待办。
- 退回后重新提交生成新 submission，保留原提交和退回历史。
- 非 inspection 角色不能调用监检资料接口。
- 搜索、分页、总数只计算正式提交资料。

### 前端测试

- 监检表格只消费专用接口，不读取 `nodePackage.projectFiles`。
- 表头和文案使用“已提交审查资料”“提交审查时间”。
- 时间严格展示 `submittedAt`，缺失时显示异常状态而不是回退到上传时间。
- 页面不显示“已上传”作为监检审查状态。
- 施工方操作栏和提交弹窗不再出现撤回入口。
- 历史撤回记录仍能只读展示。

### 回归验证

- 施工方仍可上传、保存草稿、绑定节点和提交。
- NDT 仍可逐文件保存草稿、调整适用业务规则并提交。
- OCR 仍在上传后异步运行，失败不阻断单文件提交。
- 监检人员仍可查看原文、OCR 证据、保存审查意见、退回补正和审查通过。

## 非目标

- 不修改 OCR 引擎、识别算法或证据完整性判断。
- 不把项目资料池提交强制改为节点提交。
- 不删除历史撤回数据或审计日志。
- 不对其他非监检业务模块重构文件上传流程。
