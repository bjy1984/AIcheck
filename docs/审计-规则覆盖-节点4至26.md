# 审计：现有审查规则对节点 4/5/6/7/8/9/12/13/16/24/25/26 审查内容的覆盖度

日期：2026-09-06　依据：业务包 `engineering_inspection_v1`（rules / atomic_checks / atomic_check_tool_bindings / nodes / materials）、各工具实现（`libs/review_tools/*.py`、`review_orchestrator/*.py`）、《研究-焊接材料设计节点审查原则》§5.2 判定清单、《规则测试》反馈。
方法：对每个节点，把业务口径（rules.yaml 的 criteria / checkMethod）和研究报告的判定清单拆成审查要点，逐条对照现有原子检查的 instruction、绑定的工具、工具实际执行的分支、事实来源与试点开关，判断"能不能跑出结论"。

## 0. 结论

**不满足。12 个节点里没有一个能对其审查内容形成完整的自动判定；4 个节点（5、8、9、26）在正式审查里实际上跑不出任何确定性结论。**

| 节点 | 审查内容 | 覆盖度 | 一句话 |
|---|---|---|---|
| 4 设计文件的批准程序 | 齐全性 + 三级/四级签字 | 部分 | 齐全性与签字角色能判；"目录 vs 上传"对照没实现；四级触发用工程级参数不看逐管线；**不在试点规则表，正式审查不跑工具** |
| 5 施工图审查手续 | 审查见证材料 | 不满足 | 没有判定口径、没有事实构建器、绑定缺 requiredDocumentTypes 参数，工具必返回证据不足；不在试点表 |
| 6 计算书审批手续 | 覆盖管线 + 设计条件一致 + 签字级别 | 部分 | 签字能判；"计算书 vs 设计条件"需要 parameterComparisons 事实，没人产出，一致性检查永远证据不足 |
| 7 设计变更书面批准 | 设计许可章 + 三/四级签字 + 原设计单位批准 | 部分 | 框架最完整；但 hasDesignChanges / 印章原件 / 原设计单位 等事实来源未闭环，版本连续性不查 |
| 8 标准版本有效 | 所采用标准现行有效 | 基本不满足 | 只有在线查询且强制人工确认；无本地版本时间线；签发日期与版本矛盾不判；不在试点表 |
| 9 设计对 NDT/防腐/试验的规定 | 设计说明有具体要求且符合标准 | 不满足 | 工具零内置知识，全靠冻结规则包 `designSpecialRequirementRules`，而规则包里**没有这一节**，一律证据不足；节点资料要求错配（要求泄漏试验报告、仪表证书） |
| 12 元件制造单位许可 | 许可证号平台核实 + 范围覆盖工程元件 | 部分 | 范围覆盖表可用；平台核实来自 `manualRegistryVerifications`（人工填），未接 `search_cnse_organizations` |
| 13 监检证书 / 型式试验 | 证书齐全 + 覆盖材料表元件 | 较好 | 分类表、覆盖、批次追溯齐；缺平台型式试验报告查询；分类表 5 类元件留 None |
| 16 产品质量证明文件 | 逐批核验形式、内容、一致性、数值、追溯 | 部分 | 形式/内容/一致性/追溯能跑；**数值限值从未提供**，结果核验形同虚设；只冻结 8 个标准；无版本时间线、牌号-标准合法性、逐行成分、PMI/复验 |
| 24 焊工资格 | 人证相符 + 作业内容在证书范围 | 部分 | 2010 版覆盖逻辑可跑；2026 版门禁未验证，2026-08-01 后一律证据不足；平台查询未绑定；无清单/证书/平台三方比对 |
| 25 焊接工艺文件 | WPS/PQR 审批对应 + 参数与实际生产条件覆盖 | 部分 | 四个数值参数 + 方法/材料三重相等；无 NB/T 47014-2023 类别组别/厚度/重要因素覆盖；无 WPS 11 项；无评定标准版本判断 |
| 26 焊材质量证明 | MTC 含成分力学 + 与实物批号对应 + 牌号规格符合设计 + 有效期 | 基本不满足 | 限值档案缺失 → `product_standard_limit_profile_missing` 一律证据不足；无型号解析与母材匹配；有效期按不存在的 `stockValidUntil` 判 |

四个横向原因决定了以上大部分"部分"和"不满足"：

1. **试点开关**：`atomic_check_tool_bindings.yaml` 的 `pilotRules` 不含 R04、R05、R08；绑定集 lifecycle 仍是 draft，正式审查对这三条规则直接抛错、不跑任何确定性工具。
2. **没有逐管线事实**：只有 R14 从管道特性表抽出 `pipelineCharacteristics`（管线号、级别、P、T、材质）；R04/R06/R07 的四级触发用的是工程级 `project.pipelineGrade` 和设计参数合成的一条假管线。
3. **冻结数据表是空的**：R09 的领域规则、R16 的验收限值、R26 的焊材限值、R24 的 2026 覆盖表、R25 的类别组别表都设计成"由冻结档案提供、工具不猜"，但档案从未录入。
4. **外部核验靠人工**：R12 的许可证平台核实、R08 的标准状态、R24 的焊工平台查询、R13 的型式试验报告查询都没有接入自动查询，或接入了但强制人工确认。

## 2. 需要新增的规则、工具与数据（按节点）

编号 N-xx 为本审计建议项；"数据"指冻结档案 / YAML，"工具"指确定性函数，"规则"指原子检查。

### 横向前置（不做这些，下面的节点项大多跑不出来）

## 4. 附：本次核实的两个平台事实（2026-09-06 晚更正）
- **平台是返回多证的，我们的客户端只取了第一条。** 公示平台网页流程：`remotePubQuery.json`（只回一条记录，用途是取身份证号）→ 跳转 `/pub/perResult?sfzh=…&moveLength=…`（页面里藏 `validCode`）→ `/pub/getPerInfoBySfzh.json?sfzh=…&validCode=…` 返回 `licList` 全部证书。`libs/integrations/cnse_client.py` 停在第一步。实测：李卫伍 7 条（起重机指挥 2 条、焊工 5 条，其中 3 条现行：GTAW-FeⅡ-6FG-12/19-FefS-02/11/12、GTAW-FeⅣ-6G-5/57-FefS-02/10/12、SMAW-FeⅡ-6FG-12/19-Fef3J，2028-10-31 到期，与焊工清单逐字一致）；姜军 4 条（现行焊工证 1 条、起重机指挥 2 条、2024-12 已到期的旧焊工证 1 条）。此前"平台一人只回一条、不能按类别筛选"的结论撤回；对 `remotePubQuery.json` 加类别参数无效、分页 403 的观察仍然成立，但已不重要。
- **`validFlag` 不等于现行**：已到期记录（yxrqz 2024-10、2024-12）的 validFlag 仍是 1，有效性必须按 yxrqz 与施焊日期计算。
- 系统内部的"一人多证"：`check_certificate_validity` 与 `check_welder_work_coverage` 按证书列表逐张判；`certificate_facts` 的旧命名镜像只取第一张证（影响旧绑定）；焊工证抽取器按"一份文件一张证"，多人合订扫描件只抽到第一人。
