# 生產伺服器上的 Jev 插件 A/B 評估（2026-09-25）

## 結論

**這批資料上，Jev 沒有帶來可量化的提升，也沒有造成傷害。評估後已關閉兩個項目的 Jev 開關，暫不再測。**

- 8 個正式複核節點、23 個原子項，Jev 開與關的判定**完全相同**，逐條 processChecks 也 0 差異。
- Jev 逐項建議（PRIMARY_DECISION）被問到 **0 題**：這些節點的原子項全部由規則工具判定，沒有需要閱讀判斷的題。
- Jev 事實核對（FACT_CHECK）只在 2 個節點跑到，核對 **5 條事實，全部確認正確**（把握值 0.95–1.0），可疑 **0 條**。
- 耗時沒有差別：兩組合計 2,577 秒對 2,465 秒，差距在模型生成的正常波動內。

這不是「Jev 沒有能力」的判決。Jev 的強項是核對原文是否寫明某個抽取值（見 [2026-09-23 能力邊界](2026-09-23-jev-boundary-suite.md)：抽取值核對 32/32）。但這次能跑正式複核的節點剛好都由規則判定，Jev 沒有施力點。

## 為什麼 Jev 沒有施力點

1. **逐項建議只問規則管不到的題。** Jev 只回答需要閱讀判斷的原子項；這 8 個節點（設計文件、材料追溯、設計許可等）的原子項全部由規則工具負責，所以都是 `no_semantic_checks`。
2. **事實核對只核證書、設計、焊工與施工記錄事實。** 這 8 個節點裡只有 R01、R09 帶這類事實，其餘都是 `no_certificate_facts`。
3. **Jev 最有價值的節點在正式模式跑不到：**
   - 證書類（R02、R03、R24、R38）：多張證書合訂，最容易讀錯；
   - 語義類（R19）；
   - 記錄類（R44–R68）。

   前兩類在這兩個項目資料不齊，不能發起正式複核；記錄類不在 pilot 名單，只能跑缺項預審，而 Jev 只在正式模式執行。
4. **這次灰度實際遇到的抽取錯誤已由規則修掉：**
   - 證書起止日期讀反（#49）；
   - OCR 在空白格編出管線行（#58）。
