# 第 3 層接進管線：agent 的產出當證據存，不在事實構建裡調模型（2026-09-10）

## 要解決的架構問題

第 3 層（agent 讀正文填布林）最直覺的接法，是在 fact builder 裡直接調模型。**這樣
會毀掉驗收重放。**

`replay_review_acceptance` 的前提是「同樣的輸入必得同樣的輸出」，靠的是
`OFFLINE_TOOLS` 那批工具不碰網路。事實構建一旦調模型：

- 同一份 fixture 每跑一次就重新問一次模型，兩次結論可能不同
- 驗收契約要求的「不得用人工拼造的通過 JSON 代替執行結果」失去意義——結果不再可
  重現，也就無從核對
- 每次重放都要再花一次錢

## 接法

agent 的產出被當作**證據**記進 state 的新集合 `domain_judgments`：它和 OCR 的表格
一樣，是一次性產生、此後只被讀取的資料。凍結進 fixture 之後，重放讀的是當時記下
的那一份，不會再花錢，也不會飄。

事實構建（`installation_domain_facts._build`）只多做一件事：按五個定位欄位去
`domain_judgments` 找對應記錄，找到就把值併進 domain row。**整條路徑仍然離線。**

## 三條規矩，都有測試釘住

1. **五項全等才算數**：projectId / nodeId / domain / objectId / recordVersionId。
   少比一項就可能把甲管線的結論安到乙管線頭上。命中兩條視為來源含糊，**一條都不
   給**。
2. **表格裡已有的值優先。** agent 讀的是正文，表格是結構化原件；兩者衝突以原件為
   準。一次模型調用不能悄悄改寫 OCR 抽出來的數字。
3. **被拒的路徑留在 row 上**（`judgmentRejections`）。模型答了但引用對不上，必須
   看得見，不能只留在日誌裡——那和模型老實留空是兩回事。

寫入端（`run_domain_judgment.py --persist`）用五個定位欄位算一個穩定 id，重跑**替
換**而不是並存；並存會讓 `judgment_for` 判成來源含糊、一條都不給，等於把那次調用
的錢白花。

## 現在的狀態

程式與測試都完成，端到端測試證明「表格值 + agent 判斷」能合成完整的 domain row 走
到 R43。**但真實運行仍未發生**——生產的兩個模型供應商一個密鑰無效、一個賬戶沒
錢，詳見[同日記錄](2026-09-10-llm-key-invalid-in-production.md)。

密鑰恢復後要跑的就一條命令，不需要再改程式。
