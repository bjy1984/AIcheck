# 離線重放覆蓋：3 → 26 條（2026-09-10）

## 量出來的數

驗收契約要求每條規則四種情境都有**真實執行結果**，而重放是把結果變成可核對證據的
唯一機制。所以「有多少條能離線重放」是第 8 項的先決條件，先量一次：

| | 條數 |
|---|---|
| 規則總數 | 69 |
| **可離線重放** | **26** |
| 沒有事實構建器 | 43 |
| 計劃缺失／工具未註冊 | 0 |
| 卡在非離線工具 | **0** |

修之前只有 3 條（R35 / R36 / R37）。

## 兩次修的是同一個病

`OFFLINE_TOOLS` 是一份**手寫**名單。而「註冊一個新工具」和「更新這份名單」是兩個
動作——中間必然有人只做前一個。

- 第一次：26 個 frozen-domain 工具接進來時名單沒跟上，R43 以後全部卡在
  `replay_nonlocal_or_unsupported_tools`，69 條掉到只剩 3 條能重放。
- 第二次：補完之後量出來 24 條，R39／R40 仍卡著。查它們的十個工具——只對傳進來的
  arguments 計算，導入閉包裡沒有任何網路或資料庫客戶端，和那 26 個是同一類。**它們
  缺席只是名單沒跟上，不是判定上有差別。** 補進去，26 條，零阻塞。

追依賴時有個坑：`business_tools.py` 是總登記本，導入全部工具，拿它當閉包起點會把
`cnse_client` / `std_samr_client` 那些無關的 httpx 客戶端也算進來，看起來像是 R39
會連網。要從工具自己的模組起算才對。

## 所以加了測試，而不是指望下一個人記得

`tests/test_offline_replay_coverage.py`：

1. **每條有事實構建器的規則都必須能離線重放。** 下次再有人加工具忘了更新名單，
   這裡會紅，而不是讓那些規則悄悄變成不可核驗。
2. **名單裡不得有已刪除的工具名。** 留著會讓人以為某條路是通的。

## 還差什麼

剩下 43 條卡在**沒有事實構建器**——那是另一個缺口，不是名單問題。事實構建器目前覆
蓋 27 個節點。

要注意：能重放不等於能產出驗收證據。重放的前提是有 fixture，而真實運行要能導出成
fixture，還需要凍結的文件範圍（生產目前 0 筆有）和真實素材（見同日的
[缺口盤點](2026-09-10-criteria-producer-gap-audit.md)）。**26 這個數字是上限，不是
現況。**
