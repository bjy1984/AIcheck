# 判據的生產側：第 1、2 層接通（2026-09-10）

## 背景

同日的[缺口盤點](2026-09-10-criteria-producer-gap-audit.md)結論：凍結判據層只有
消費者沒有生產者。缺三層——表結構分類、欄位對映、布林產生。第 3 層要接 LLM 跑真
實文件、要花錢，未獲批准；第 1、2 層不花錢且可離線測，先做這兩層。

## 做了什麼

**宣告面**：`business_packs/engineering_inspection_v1/table_schema_signatures.yaml`
——和它餵的判據放在同一個目錄。每條簽名寫：怎麼認這張表（必需表頭 + 至少幾個備選
表頭）、對象識別欄、以及表頭到判據 `actualPath` 的對映。每條都必須填 `evidence`
說明表頭出自哪份真實資料。

**機制面**：`libs/table_schema_mapping.py`，純函式，不碰網路和資料庫。

**接線**：`read_ndt_tables` 在 OCR 沒給 `businessSchema` 時用簽名再認一次。**在讀
取時機補認，既有文件不必重跑 OCR**——生產庫那 1004 列現成資料立刻可用。既有分類
優先，簽名只補空缺，不覆蓋。

## 三條「不猜」的規矩

判據那邊「該寫沒寫」判不符合、「取不到值」判證據不足；兩種結果都比塞一個猜的值進
去好。所以：

1. **同時符合兩條簽名就不貼標籤。** 貼錯的表會被當成真證據讀，比沒有這張表更難查。
2. **對映不上的欄位不寫。** 判據看到缺項報缺證據，那是正確的結果。
3. **`检测比例` 只收乾淨的「10%」。**「约10%」「10~20%」一律拒收——R36 的工具要
   的是數，約數和範圍不是數。

`applicable` 也只有簽名裡明寫 `applicableWhen: table_present` 才給 True，並在
YAML 裡註明「這是一個宣告的判斷，不是從資料讀出來的」，可被覆核。

## 在真實生產資料上驗過

不是只跑自己寫的 fixture。把生產庫全部 166 張解析表撈下來，逐張過分類器：

| | 張數 |
|---|---|
| 原本無 schema，仍認不出 | 119 |
| 原本有 schema（不動） | 31 |
| **原本無 schema，新認出 `material_certificate_domains`** | **3** |
| **與既有分類衝突** | **0** |

那 3 張是同一張真表——`0常用管道元件核查记录-施工单位填写.doc` 裡的一張 MinerU
解析表（7 列、6 個相異證明書編號），因為同一份文件掛在三個專案下而出現三次。

真實的一列跑出來長這樣（值全是真的）：

```json
{"projectId": "...", "objectType": "material_certificate",
 "objectId": "20260213951", "recordVersionId": "...",
 "domain": "materialCertificate", "applicable": true,
 "certificate": {"documentNo": "20260213951", "materialGrade": "S30408"}}
```

`材质:S30408标准:GB/T14976-2025` 被按標籤切開了——整串塞進 `materialGrade` 會讓
牌號裡混進標準號。

## 撤掉一條簽名：它的來源是種子資料

我一開始還寫了 `ndt_plan_items`，表頭取自「介质 | 公称直径 | 检测比例 | 管道号」，
生產庫裡出現 13 次，當時記成「真實表頭」。逐張追來源之後撤掉了：

- 13 張的 `tableId` 全是 `TABLE-PARSE-FDE-*`；真實 OCR 的表是 `MINERU-*`（共 150 張）
- 13 張的內容**逐字相同**：PL8301 / PL8302、天然气、DN100、10%
- 它們被掛在**焊工資格證、焊工名冊、RT 檢測報告**這些不相干的文件底下

也就是有人把同一張示範表複製到那個專案的每份文件上。依它寫的簽名，等於拿別人捏
的樣本當真實表頭——正是這份檔開頭那條規矩要防的事。撤掉，等真的拿到無損檢測委託
／比例表再按真實表頭補回來。

**所以真實覆蓋是 1 條簽名、1 張真表，不是我先前說的 16 張。**

## 現在到哪、還差什麼

端到端測試（`tests/test_real_table_reaches_the_rules.py`）證明：**一張生產庫裡真
實的、沒有 businessSchema 的表，現在能一路走到 R43 的 fact builder，帶著真實
的 `documentNo` 和 `materialGrade`。** 這條鏈之前是斷的。

但 R43 的結果**仍然是 evidence_insufficient**，因為三個判斷布林還是空的：

- `certificate.certificatesAndMarksReviewed`
- `certificate.gradeMatchesSpecification`
- `certificate.requiredProcessingAndTestsEvidenced`

這是預期的，不是遺漏，並且有一條測試專門釘住它們必須缺席。差別是：從「什麼都沒
有」變成「差三個明確的判斷」。

**目前只有 1 條簽名**（R43），涵蓋 73 個表結構名裡的 1 個。其餘 71 條要
真實表頭才能寫——憑印象寫的簽名會在真實素材上默默配錯表，那比沒有更糟。生產庫裡
還有 119 張認不出的表，是下一批簽名的來源。

## 下一步

1. 從那 119 張表繼續抽表頭，補簽名（不花錢、可離線測、可在真實資料上驗證覆蓋率）。
2. 第 3 層仍待批准：接 agent 讀正文產生判斷布林，或人工填。

## 補充：為什麼只寫得出 2 條簽名

我原本以為剩下 119 張認不出的表是下一批簽名的來源。逐張看過表頭之後，發現不是。
它們大多是：

| 張數 | 內容 |
|---|---|
| 13 | `发证机关(章)`——整張表只有一格，表頭沒認出來 |
| 11 | `内容 \| 项目`——通用鍵值對 |
| 10 | `许可项目 \| 许可子项目 \| 许可参数`——資質許可 |
| 8 | `1. 注册详细信息可自中国特种设备检验协会网站...`——腳註被當成表 |
| 4 | 工商登記變更事項 |
| 3 | 查詢號／回執號 |

也就是**資質類文件和 OCR 誤判**，不是施工記錄。

再查語料本身（121 份文件的檔名與物料類型），三個真實工程交的是：設計文件、許可
證、資格證、產品質量證明書、無損檢測報告、焊接工藝評定、施工組織設計、施工方案。

**沒有任何一份防腐施工記錄、陰極保護測試記錄、支吊架安裝記錄、驗收表。**

所以：

| 規則群 | 需要的文件 | 語料裡有嗎 |
|---|---|---|
| R43 材料證明 | 產品質量證明書 | **有**（5 份） |
| R36 無損檢測方案 | 無損檢測報告／委託 | **有**（8 份） |
| R44 / R46 / R47 / R49 / R50 / R52 / R53 / R54 / R55 / R68 等施工類 | 施工記錄、測試記錄、驗收表 | **一份都沒有** |

我寫得出的兩條簽名，正好就是語料裡有對應文件的那兩條——不是巧合，是我從真實資料
往回挑的。

這也解釋了那 352 個判斷布林為什麼補不上：抽樣顯示約七成是現場觀察（陽極回填無空
隙、通電前電纜已連接、四點測厚），而**記錄這些觀察的文件根本不在語料裡**。不是
OCR 認不出，不是 agent 讀不懂，是紙沒交上來。

## 修正一個我先前的判斷

我在缺口盤點裡建議「從那 119 張表繼續抽表頭，補簽名」。**這條建議是錯的**——那
119 張表裡沒有施工記錄。要推進那 25 條施工類規則，缺的第一件事不是程式，是**向工
程方索取施工記錄類資料**。
