# 待辦跨程序驗收，與交接跨程序測試的既有脆弱性

## 補上的驗收：待辦彙總接口跨 HTTP 程序

清單第 5 項要求「工位待辦彙總接口的完整跨 HTTP 程序驗收；**不能拿交接詳情的測試直接代替**」。

新增 `backend/tests/test_todos_http_postgres.py`：起兩個真實 uvicorn 程序共用一個 PostgreSQL，釘住兩件事——

1. 兩個程序給出的待辦集合與總數一致
2. 程序 0 完成的待辦，程序 1 看得到新狀態

第 2 條**先直接查庫斷言**完成動作已落庫，再驗另一個程序讀得到。分開驗的理由：失敗時能立刻分辨問題在寫入端還是讀取端；只斷言「另一個程序看得見」的話，兩種原因會混成同一個現象。

## 我在這條上犯的錯（方向完全反了）

初版挑「列表裡第一條待辦」作為目標，不同執行順序會挑到不同記錄，於是單跑過、全量掛。

**我把這個測試不穩定當成了產品缺陷**，照 `review_handoff_routes` 的樣子給 `/todos` 兩個讀路徑加了 `refresh_collections_incrementally({"todos"})`。加完之後變成**穩定失敗**——我當時以為是「終於復現了」。

撤掉改動後測試 XPASS，才看清真相：**是那個刷新造成讀不到的**。顯式增量刷新會把水位線推進到 `safe_watermark`，若晚於後續寫入的 `updated_at`，之後的 `updated_at > watermark` 就永遠跳過那一行。**原始程式碼本來是對的，我親手造出了自己要測的 bug。**

教訓：測試不穩定時，先把測試本身確定下來（固定目標記錄），再判斷被測物。順序反了就會去「修」一個沒有問題的東西。這段已寫進用例的文檔字串。

## 查出的既有問題：交接跨程序測試

`tests/test_review_handoff_http_postgres.py::test_two_http_processes_reject_stale_verification_and_refresh_source` 的表現：

| 情形 | 結果 |
|---|---|
| 單獨跑 | 通過 |
| 與**任何**另一個測試檔一起（換成不相干的 `test_review_workstations.py` 同樣復現） | **失敗 40906** |
| 反序（另一檔先跑） | 通過 |
| 幾千個測試的全量跑 | 通過 |

失敗點在第 142 行 `assert revised['code'] == 0`，回的是 `RESOURCE_STATE_CHANGED`（40906，「數據狀態已更新，請刷新後重試」）——樂觀鎖判定程序 1 的寫入基準已過期。

**加一次「刷新後重試」無效**：40906 持續出現。也就是說在這個情形下，程序 1 重讀之後寫入基準**仍然是舊的**，不是抖動一下就好。

這正落在清單第 5 項問的那件事上——「交接依賴、結果和『需重驗』狀態，在上述情況下是否一致」。**建議由該測試與交接寫入路徑的擁有者接手查**：讀路徑有 `_refresh_dependency_state`，但寫入時的 `assert_persistence_baseline` 用的基準似乎不隨之更新。

我沒有改那條測試。放寬它的斷言、或加一個實測無效的重試，都只是把問題蓋住。
