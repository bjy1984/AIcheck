## 1. 為甚麼要調整

原分支的做法是 Qwen 根據節點模板和 OCR 出題，Jev 選答案，然後**用 Jev 的答案覆寫原子項結果**。評估時發現三個問題：

- **Jev 答了它答不了的題。**194 個原子項中，除 67 個證據定位項外，其餘 127 項都會被 Jev 覆寫，包括 13 項證書／許可／平台核驗和 15 項日期、數值計算。Jev 只讀 OCR，查不了公示平台；算術也應由程式算。
- **低把握也會生效，而且會流進下游。**R09-01 上 Jev 以 0.28 選「通過」，照樣成為該項結果；結果又被寫回 `context["ruleResults"]`，審查草稿、依據校驗和逐項輸出都用它。
- **出錯時會蓋掉規則結論。**不在白名單的工程、出題失敗或 Jev 不可用時，所有原子項會被改成「需人工」，連規則已明確判出的「不符合」也被蓋掉。

Jev 沒有通過或拒絕理由，在監檢語境裡「不符合，0.87」只是一個提示，不是結論。9 月 22 日的[研究](research/2026-09-22-jev-vs-current-verdict-layer.md)已得出「能做，但不該做成裁決層」，原分支後來偏離了這個判斷。

## 2. Jev 用在哪裡、不能用在哪裡

判斷標準只有一條：**Jev 回答「原文是否寫明某事」很可靠，但它不給理由，也不會算。**所以它只用來核對事實、提示分歧，不用來下結論。這條規則已寫成 [jev_usage_policy.py](../../backend/libs/review_orchestrator/jev_usage_policy.py)，並由程式強制執行。

## 5. 新提案評估：RAG 選條款 → Jev 判適用 → Qwen 出題 → Jev 判

新提案的流程是：節點審計 → 掛載的審計材料 → Qwen 從 RAG 選出候選條款 → Jev 判斷哪些條款適用 → Qwen 出題 → Jev 判斷。它想解決的問題是真的：R06-03 暴露出「適用性」判錯，固定模板也可能沒覆蓋材料中的特殊情況。**但作為主線不建議，原因如下：**

1. **與已定的固定條款綁定相反。**[節點與固定標準條款綁定方案](../业务节点与固定标准条款绑定方案.md)已把 69 個節點綁到經原文核對的條款，列明版本、頁碼、核驗狀態，並寫明「運行時不再讓 LLM 檢索、選擇或猜測條款」。這是因為 TSG 31-2025、NB/T 47014-2023 等剛換版，檢索很容易取到舊版條款。
2. **漏審是靜默的，而且誤差會相乘。**選條款、判適用、出題、判題四段都帶隨機性。假設每段有九成正確，連乘後只剩約三分之二；被 RAG 漏掉或被判成「不適用」的條款根本不會出現在介面上，監檢員看不到自己沒審到甚麼。
3. **Jev 判「不適用」等於用一個沒有理由的答案刪掉一條要求。**這正是會讓結論變寬鬆的決定，和「Jev 只作加強」矛盾。適用性多由 GC 等級、設計壓力、溫度、材料決定，這些已經抽取出來了，應由確定性規則判。
4. **Jev 又回到裁決位置。**最後一步仍是由 Jev 判題，而 Jev 沒有理由。
5. **更難評測。**除了題目的真值，還要條款選擇的真值（應審哪些條款），目前兩者都是零。

**建議改用 C′，分兩步做：**先離線把 RAG 跑在歷史工程上，找出「經常相關卻不在固定條款包內」的條款，由監檢員審核後補進條款包；線上只顯示「可能遺漏的條款」清單，不刪必審項、不產生結論。前提是先量測 RAG 對條款的召回率，並確保只檢索現行版本。
