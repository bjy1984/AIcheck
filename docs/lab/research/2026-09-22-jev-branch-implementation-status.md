   `/home/dev-bjy/aicheck-secrets.env`。正式 Jev 开关仍保持关闭。
2. **33 题监检标注与阈值校准**。16 道分歧和 17 道 Jev 判通过的原始候选表未在本
   工作树中找到；`scratchpad/shadow/` 也不存在。只有研究报告，不能重造题目或宣称
   0.68／0.72 已经校准。标注后才能设置校准、拒绝和 UI 开关。
3. **上游两个生产缺陷**。GC2 覆盖结论冲突仍待按法规来源修正；本分支只阻止冲突
   结果进入 Jev state。节点 3 的已知「单位名称被抽成评价句」已加窄范围守卫，见下文；
   尚未重放原生产 OCR，不能记为实机修复完成。
4. **实机验收**。需要原始七项目影子产物或获准后的受控回放，核对 R25/29/32 的
   71 条假事实、219 格方向对照、逐句抓错率、R19 八项语义题及大文件分拆。
   单份超过 40,000 字的文件目前会跳过 Jev；不能宣称两格超长已补跑。
5. **费用优化与正式队列**。当前 Qwen 仍对所有进入原流程的节点生成发现；“只给人工
   队列生成解释”的省费改造尚未实施。R19 仍按现有语义路径裁决，Jev 暂不替换它。
6. **清单模式**。`AICHECK_REVIEW_PROMPT_MODE=checklist` 的清单结论受独立的条件一致性
   契约保护；本分支的逐句核对只针对自由发现模式。清单模式会明确记录
   `unsupported_checklist_mode`，不会擅自改写固定条件判定。

## 开关与验收顺序

先验收不出境的规则/表格回退测试；获得出境结论并轮换密钥后，先只开三项基础开关
跑影子数据。33 题经监检标注后，确定并记录拒绝阈值、人工队列进出阈值，再考虑设置：

```text
AICHECK_JEV_CALIBRATION_APPROVED=true
AICHECK_JEV_CLAIM_GATE_ENABLED=true
AICHECK_JEV_CLAIM_REJECT_CONFIDENCE=<经标注确认的值>
AICHECK_JEV_SECOND_OPINION_UI_ENABLED=true
AICHECK_JEV_QUEUE_ENTER_CONFIDENCE=<经标注确认的值>
AICHECK_JEV_QUEUE_EXIT_CONFIDENCE=<经标注确认且高于进入阈值的值>
```

研究计划中的 0.68/0.72 只是待校准候选。支持页只有 Jev 的定位建议，不能替代
现有 `evidenceRefs`。所有代码变更目前只在该分支，未部署。

## 文件归属的下一批开发（仍为影子模式）

- OCR 后的异步分类任务完成并落库后，可另外派发 Jev 文件归属任务。新任务只在
  `AICHECK_JEV_DOCUMENT_ROUTING_ENABLED=true`、Jev 总开关、资料出境许可、新密钥及
  Celery 派发同时满足时运行；inline／派发不可用时不会在上传请求里同步访问 Jev。
- 每份文件以本工程、当前版本的完整 OCR 为输入，按当前业务包启用的审查点汇总成
  节点选择题。输出每节点三态与把握值、输入指纹、现有归属及分歧；人工拒绝的节点
  不进入建议名单。结果保存在文件的 `jevRoutingShadow`，不改资料类型、绑定、证据链
  或审查结论。旧版本、跨工程、无 OCR、单文件超长、请求整体超长和模板超长均显式
  跳过或标为部分结果。当前默认审查点资产共有 168 项、覆盖 68 个节点；本地预检中
  问题模板收紧后，本地预检 `test2/` 共 20 份中 19 份可发起、1 份（`test2-006`）
  因原文超过 40,000 字被跳过；19 份合计需 66 次完整原文请求，其中 `test2-010`
  最多需 10 次。单文件超过 10 次请求会明确返回预算超限。这里仅计算请求尺寸，
  未实际发送这批文件归属题，也未测准确率与费用。
- 所有调用仍走同一个 `ask_jev`。兼容相同请求／响应契约的 API 可配置
  `AICHECK_JEV_API_URL`；切换域名须另设 `AICHECK_JEV_APPROVED_HOSTS`，且只接受 HTTPS。
  统一客户端按完整请求包（原文加题目）限制 40,000 字，并自动分批、校验每批回答；
  单题仍超限则显式失败。模型仍固定 `jev-1.13.0`，不同协议或模型须重新适配及校准。
- 文件归属的多批请求可能长于普通任务；只给这个任务的 PostgreSQL 锁设 180 秒空闲
  超时，普通任务仍为 60 秒，避免请求未结束时锁先失效，同时保留孤儿锁自动清理。
- 这一批用伪造 Jev 响应验证了整份 OCR、人工否决、输入变化重跑、异步派发、版本
  竞态及故障回退；统一客户端、任务锁和离线容量预检加入后相关后端回归 **106 项通过**。**尚未用七项目真值集衡量归属准确率**，不得把影子建议接入自动
  挂载。正式资料出境许可和密钥轮换的发布前置条件维持不变。

## 节点 3 的错误单位名称守卫

- 单位许可证 OCR 若把「被评定为 A 级机构。」之类明显的评价句填入单位名称，事实
  构建不再把它当主体身份；同份 OCR 有另一条正常单位名称字段时优先用正常字段。
  单位许可证也不再把正文的个人「姓名」回退成持证单位。
- 对被拒的字段记录 `holder_field_rejected`；按许可证号查到平台登记后，保留平台
  查询结果，但不据此冒充主体一致或报主体不一致，也不引入平台证据，判定为证据不足
  交人工核对。真正的正常名称不一致仍保留 `verified_mismatch`。
- 证书事实、平台核对、规则输出相关 **48 项测试通过**。这只覆盖已知错误形态，
  尚未拿节点 3 原生产 OCR 重放，不能推论所有单位名称抽取都已修好。
