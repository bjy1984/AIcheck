# 条款结构化渲染与索引路径融合方案

承接 `标准规范MinerU重识别与语义结构化方案.md`（Track 1 / Track 2 已完成）。
本方案解决两件遗留事项：工作台还渲染不了公式与表格；标准库与普通上传的索引
路径看上去是两套。

两件事有一个共同的前提：**Track 2 的结构字段目前只有标准库有，普通上传的表格
根本进不了切片链**。所以渲染方案不能只按标准库设计，融合方案也不只是"整理代码"。

## 一、问题一：工作台的公式与表格渲染

### 1.1 现状

| 项 | 现状 |
|---|---|
| 条款正文渲染方式 | 全部是 Vue 文本插值 `{{ }}` |
| 全仓库 `v-html` 用法 | **0 处** |
| katex / mathjax / markdown-it / marked / dompurify / sanitize-html | **一个都没装** |
| UI 框架 | Element Plus 2.11.9 |

### 1.1.1 关键校正：只有一个地方真的在渲染条款正文

初查列出了三个"条款展示位"，逐个追下来发现**其中两个根本不含条款正文**：

| 展示位置 | 渲染字段 | 这个字段实际是什么 |
|---|---|---|
| AI 审查 · 适用标准条款卡片 | `basis.summary` | ❌ **是 YAML 里人工写的 `purpose`**（"直接监检依据" / "专业执行条款"），见 `routes.py:4386` `"summary": purpose` |
| 侧栏 · 标准依据 | `standard.summary` | ❌ 同一条数据源（`fixed_standard_references_for_node`） |
| **打开条款原文弹窗** | `chunk.text` | ✅ **真·条款正文**，按 (文件, 页码) 拉回 `KnowledgeChunk[]` |

`basis_card` 展示的是固定引用的元数据（标准号、条款号、用途）加一个跳转到 PDF
第 N 页的预览链接，**它没有条款正文可渲染**。往这里接 KaTeX 是接错了地方。

真正的接入点是 `EvidenceLocatorDialog.vue`：

```177:182:frontend/src/views/AICheck/components/EvidenceLocatorDialog.vue
const clauseOcrText = computed(() =>
  clauseChunks.value
    .map((chunk) => String(chunk.text || '').trim())
    .filter(Boolean)
    .join('\n')
)
```

它把该页所有 chunk 的 `text` 拼成一个字符串塞进 `<pre>`（359 行）。公式和表格
就在这些 chunk 里，只是被当成纯文本拼掉了。

**另一个好消息**：这个弹窗调的 `/api/knowledge/files/{fileId}/chunks` 返回的是
**完整 chunk payload**，没有字段裁剪：

```27801:27801:backend/apps/api/routes.py
    chunks = [repo.clone(item) for item in repo.state.get("knowledge_chunks", []) if item.get("fileId") == file_id]
```

也就是说 `blockType` / `latex` / `tableHtml` **已经在往前端传了**，前端只是没用。
后端在这条链上不需要新增字段，只需要把 `tableHtml` 换成结构化行。

### 1.2 一处必须先纠正的设计：`tableHtml` 不该进接口

这个仓库有一条**明确写在注释里的既定约定**：后端不向前端下发引擎产出的 HTML。

```288:288:frontend/src/api/aicheck/index.ts
/** OCR 抽出的表格。后端不下发引擎 html（XSS 面），只给结构化行。 */
```

```780:781:frontend/src/views/AICheck/components/FileDetailDialog.vue
                      <!-- 用 normalizedRows 自己画表，不渲染引擎产出的 html（XSS 面） -->
                      <div v-if="table.normalizedRows.length" class="ocr-table-scroll">
```

OCR 表格因此走的是结构化行（`OcrStructuredTable`：`columnNames` / `normalizedRows`
/ `cells`），前端手工画 `<table>`，全程 `{{ }}` 插值。

**我在 Track 2 里把 `tableHtml` 直接放进了检索接口返回，与这条约定冲突。**
按现在的字段设计，前端要么渲染不了表格，要么被迫引入 `v-html` + 消毒库，把这条
守了很久的边界破掉。这是要改的，且改在后端比改在前端便宜得多。

好消息是转换器现成：

```3007:3050:backend/apps/ocr_service/engines.py
def html_table_to_structure(html: str) -> dict[str, Any]:
    ...
    return {
        "rows": max(max_row, len(parser.rows)),
        "columns": max_col,
        "cells": cells,
        "normalizedRows": normalized_rows_from_cells(cells),
    }
```

`libs/mineru_ocr.py:15` 已经在 import 它，MinerU 的 OCR 表格就是这么转的。
标准库条款只要复用同一个函数，产出的形状与 `OcrStructuredTable` 完全一致，
前端连渲染逻辑都能直接复用。

### 1.3 设计决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 表格怎么给前端 | **结构化行，不给 HTML** | 与既有约定一致；转换器现成；前端可复用已有渲染 |
| `tableHtml` 是否保留 | 保留在 chunk 存储层，**不进 API 响应** | 留作溯源与排查，但不进入渲染路径 |
| 公式怎么渲染 | **客户端 KaTeX**，`trust: false` + `throwOnError: false` | KaTeX 解析 LaTeX 后自建 DOM，不是 HTML 注入；`trust:false` 会禁掉 `\href` 等能造 URL 的命令 |
| 公式是否服务端预渲染 | **否** | 服务端渲染出的还是 HTML 字符串，等于把刚挡住的注入面重新打开 |
| 公式渲染失败怎么办 | 降级显示原始 LaTeX 文本 | 标准里的公式识别不可能 100% 正确，不能让一个坏公式把整张卡片打空 |

### 1.4 改动清单

**后端**（先做，前端依赖它）

1. `libs/knowledge_indexing.py`：`structure_fields_for_unit` 在拿到 `tableHtml`
   时，顺带调 `html_table_to_structure` 产出 `tableColumns` / `tableRows` /
   `tableCells` 写进 chunk。
2. `libs/knowledge_retrieval.py`：`normalize_clause` 的结构字段白名单里，
   把 `tableHtml` 换成 `tableColumns` / `tableRows`；`latex` / `blockType` /
   `caption` 保留。
3. 存量数据：写一个**只补字段**的 backfill 脚本，给现有 1253 条 table chunk /
   clause 就地补上结构化行。
   **不要走重灌**——重灌会删向量，代价是十分钟的重新嵌入，而这次改动完全不影响
   `text`，嵌入结果一个字都不会变。

**前端**

4. 装 `katex`（含 CSS）。这是本方案唯一的新依赖，**不装 dompurify**——因为不再
   有 HTML 要消毒。
5. 新建 `StructuredTable.vue`：把 `FileDetailDialog.vue` 782–795 的手工画表逻辑
   提成公共组件，OCR 表格与条款表格共用一套。
6. 新建 `ClauseChunkContent.vue`：按 `blockType` 分支——`equation` 走 KaTeX，
   `table` 走 `StructuredTable`，其余原样 `{{ }}` 插值。
7. 接入 `EvidenceLocatorDialog.vue`：把 `<pre>{{ clauseOcrText }}` 换成按 chunk
   逐条渲染 `ClauseChunkContent`。**这是唯一必须改的渲染点。**
8. 顺带接入 `KnowledgeOverview.vue` 5108–5111 的切片预览（同样在显示裸 chunk
   text），让知识管理页也能看到公式与表格。
9. 类型扩展：`KnowledgeChunk`（`api/aicheck/index.ts` 1028–1035）加结构字段。
   **不改** `ReviewBBasisItem` / `StandardReference`——见 1.1.1，它们不含正文。

### 1.5 风险

- **KaTeX 体积**：约 270KB JS 加字体文件。工作台是内部系统，可接受；若在意，
  按路由懒加载条款渲染组件。
- **MinerU 的 LaTeX 带脏尾巴**：实测公式里有 `\tag{……(1}` 这种残缺标记
  （中文省略号 + 不配对括号），KaTeX 会报错。必须 `throwOnError: false` 并做
  降级，这也是上面那条决策的由来。
- ~~`summary` 未必等于条款正文~~ **已核实**：见 1.1.1，`basis.summary` 是人工
  写的用途说明，不含正文。接入点已改为条款原文弹窗。

## 二、问题二：两条索引路径的关系与融合

### 2.1 结论：不是两套，是"前半段两套、后半段一套"

后半段**早就是共用的**：

```
                路径 A（普通上传）              路径 B（标准库）
                dispatch_knowledge_             reocr_standards_
                file_index_pipeline             with_mineru.py
                        │                              │
        ┌───────────────┴──────────┐                   │
   取文本三选一                      │            读 MinerU sidecar
   ocr_parse_results.fragments      │            content_list.json
   / 本地文件直读                    │                  │
   / extracted_fields 兜底           │                  │
        └───────────────┬──────────┘                   │
                        └──────────┬───────────────────┘
                                   ▼
                    ★ 以下全部共用 ★
                    build_chunks_for_file
                    clause_from_chunk
                    embedding_text_for_chunk
                    embedding_batches_for_chunks
                    build_vector_rows
                    → embed_knowledge → pgvector
```

分叉只有两处：**从文档拿到"文本单元"的方式**，和**落库机制**。

### 2.2 差异清单

| 维度 | 路径 A | 路径 B |
|---|---|---|
| 文本来源 | DB 里的 `ocr_parse_results.fragments` | 磁盘上的 MinerU sidecar |
| 分块粒度 | `chunk_text` 按句读切，上限 1800 字符 | 正文按页合并；公式/表格独立成块 |
| 落库 | `repo.apply_slice_result` + `flush_state` | **直连 SQL** DELETE + INSERT |
| page_index 节点 | ✅ 生成 | ❌ 不生成 |
| knowledge_clauses | 由 `sync_standard_page_index_for_source` 批量生成 | 脚本内直接写 |
| 任务记录 | 建 slice / vector 两条 `knowledge_tasks` | 不建 |

### 2.3 三个真实缺陷

**缺陷一：普通上传的表格结构停在 OCR 结果层，进不了知识索引层。**

先说清楚三层，因为这里很容易被误读成"MinerU 没存结构化信息"——**存了**：

| 层 | 载体 | 表格结构 | 公式 |
|---|---|---|---|
| ① OCR 结果层 | `ocr_parse_results` | ✅ `tables[]` 带 `cells` / `normalizedRows` / `html`；`layoutBlocks[]` 带 `blockType` | ✅ `fragments[]` 带 `blockType` / `latex` |
| ② 文件详情展示 | 文档详情接口的 `ocrStructured` | ✅ 前端 `FileDetailDialog.vue` 已经在画 | — |
| ③ 知识索引层 | `knowledge_chunks` / `clauses` / `vectors` | ❌ **丢失** | ✅ Track 2 已打通 |

普通上传默认就走 MinerU：`AICHECK_OCR_DEFAULT_PROVIDER` 未设时硬编码回退
`"mineru"`（`backend/apps/worker/tasks.py:1714`），本地 `.env` 也显式设成了
`mineru`。落库是全量原样存，没有裁剪（`repository.py:2826-2835`）。

断点在①→③：MinerU 归一化时，`table` 块写进 `tables` 数组后就 `continue` 了，
**从不进入 `fragments`**：

```415:434:backend/libs/mineru_ocr.py
            tables.append(table)
            ...
            continue
```

而知识切片 `knowledge_slice_fragments_from_ocr` **只读 `fragments`**。
于是公式（在 fragments 里）能一路透传到 chunk，表格（只在 tables 里）到此为止。

标准库之所以有 1253 条表格块，正是因为路径 B 绕过了这一层、直接从 sidecar 的
`content_list.json` 自己拆的。

**影响**：普通上传文件的表格，在文件详情里看得见，但检索不到、也不能作为条款
引用——而工程资料里的关键参数（材质、规格、验收指标）大量就在表格里。

这是两条路径能力不对等的根源，也是本方案里唯一"修了立刻有用户价值"的一项。

> 顺带澄清一个容易误判的点：普通上传（无业务 profile）会被设上
> `enableTables: False`（`tasks.py:1754`），但 `libs/mineru_ocr.py` **从不读这个
> 选项**，MinerU 该解析的表格照样解析、照样落库。这个开关只对 local 引擎路径
> 生效，不是表格丢失的原因。

**缺陷二：标准库的 page_index 是陈旧的。**

`sync_standard_page_index_for_source`（`repository.py:3185`）只在路径 A 里被调，
路径 B 从来不碰它。而 Track 1、Track 2 两轮重建把 `CHK-*` ID 全换过。
所以库里那些 page_index 节点的 `linkedClauseIds` 指向的是**已经不存在的分块**。

后果：检索路由选中 `pageindex_tree_search` 时（`knowledge_retrieval.py:805`），
它算出的 `linkedClauseIds` 匹配不上任何现存条款，那条路由的加权等于白给。
**不报错，只是这条检索路径对标准库静默失效。**

> 代码层面可以确定路径 B 从不写 page_index；库里节点具体陈旧到什么程度，
> 需要等 Postgres 起来后查一次 `knowledge_page_index_nodes` 确认。写方案时
> 本地 Docker 已停，没能取到实测数字。

**缺陷三：路径 B 手写 SQL 绕开了持久化基线校验。**

`persist()` 之所以直连 SQL，是因为同 ID「先删后写」会触发
`ConcurrentPersistenceError`（`repository.py` 的 `assert_persistence_baseline`）。
这是绕过症状而不是解决病因，代价是路径 B 同时也绕过了并发保护和 `flush_state`
的全部副作用（page_index 缺失就是副作用之一）。

### 2.4 融合的红线

**护栏挡的是粒度策略，不是管线身份。**

```821:840:backend/libs/knowledge_indexing.py
def reject_if_dedicated_ingestion(file: dict[str, Any]) -> None:
    """标准条款库不许走通用重建管线（dispatch_knowledge_file_index_pipeline）。
    ...
    0819 拿它给标准库换向量模型，结果 31 份标准的分块直接归零，另 29 份被切成
    完全不同的粒度（13594 个碎块），靠迁移前的备份才救回来。
```

融合**不等于**"标准库从此走通用切片器"。粒度差异是有意为之，必须在合并后以
一个显式命名的参数活下来。如果合并的做法是"把两段代码并成一段、让标准库走
默认分支"，那就是在重演 0819。

### 2.5 分阶段融合

**P0 · 让 MinerU 表格进 fragments（独立价值，不依赖后续阶段）**

改 `libs/mineru_ocr.py`：table 块在写入 `tables` 的同时，也向 `fragments` 追加
一条带 `blockType="table"` / `tableHtml` / `caption` 的 fragment。
下游（Track 2 已改好的透传链）无需再动。

收益：普通上传文件的表格立刻能进知识分块与检索，与标准库能力拉平。
风险：`fragments` 数量增加，需确认 `tables` 数组的消费方没有"fragments 里
一定没有表格"的隐含假设——`tests/test_mineru_ocr.py:284` 是分开统计两者的，
该断言要一并核对。

**P1 · 补齐路径 B 的缺失副作用**

1. 路径 B 重建后调用 `sync_standard_page_index_for_source("KS-STANDARD-RULES")`，
   让 page_index 与新分块对齐。
2. 给 `repo` 增加一个正当的「就地重建」入口，替掉手写 SQL —— 让
   `assert_persistence_baseline` 认识"同 ID 先删后写"这种合法模式，而不是
   靠绕开它。
3. 基线断言里加一条：page_index 节点的 `linkedClauseIds` 必须能解析到现存条款
   （这正是缺陷二那种静默失效的检测器）。

**P2 · 统一"文本单元"这一层**

把"从某个来源得到 units"抽成一个适配器接口，三个实现：
`ocr_parse_results` / `mineru_sidecar` / `local_file`；
再把"units → chunks → clauses → 落库 → 派发向量化"收敛成一个函数，
两个入口都调它。

**粒度策略作为显式参数传入**，取值如 `generic_by_length` 与
`page_merged_with_structured_blocks`，默认值必须是安全的那个，且标准库的取值
要有测试锁死。护栏保持不动。

### 2.6 建议执行顺序

P0 独立且收益最直接，可以先做。P1 修的是已经在发生的静默失效，优先级高于 P2。
P2 是结构性重构，投入最大、直接用户价值最小，建议等 P0/P1 稳定后再评估是否值得。

问题一的后端改动（1.4 的 1–3 项）与 P0 互不影响，可以并行。
