**术语（全文只用这几个词）**
- **不符合**：确定性工具给出 failed，或通过守卫的发现 severity 为 critical/high。改变节点结论。
- **预警**：通过守卫的发现 severity 为 medium/low，或法规过渡期内的作废引用。不改变节点结论，要求书面确认或补充资料。
- **证据不足**：判定所需的数据缺失或 OCR 不可用（groundingStatus = insufficient_evidence，或工具返回 evidence_insufficient）。
- **需人工确认**：系统能力之外的事项（印章真伪、签字本人、纠错后的代号），必须由监检人员核对原件。
- **口径待确认**：业务方尚未答复的判定口径，系统按 2.5 的默认分支执行并在发现里打标。
- **[待核]**：法规或标准中的具体数值尚未对照原文核实，录入前不得用于判"不符合"。

### 6.2 判定 `evaluate_welding_process` v2
- 四链闭合矩阵：每焊口输出 closed / broken / conflict。四条链的接口固定如下，构建器只负责把焊口事实喂给各工具、收集结果，不重复实现判定：

| 链 | 调用 | 输入（来自焊口联合表） | 输出字段 | closed 的条件 |
|---|---|---|---|---|
| 焊工链 | `check_welder_work_coverage`（P1 v2） | `workItems[]`：焊口号、方法（按层）、母材牌号、外径、壁厚、焊缝金属厚度、位置、衬垫、背面保护气、焊材类型；`certificates[]`：该焊口焊工代号对应的证书 | `checks[]`（维度、条款、pass/fail/insufficient）、`covered: bool` | 该焊口每一层的方法都有一名持证焊工 covered=True |
| 工艺链 | `check_wps_pqr_coverage`（P2 v2） | `workItems[]` 同上 + `wpsNo`；`wpsItems[]`、`pqrItems[]` | `coverage[]`（维度、pass/fail/insufficient）、`covered: bool` | 焊口引用的 WPS 存在、已批准、PQR 链接闭环且覆盖该焊口 |
| 焊材链 | `evaluate_welding_consumable`（P3 v2）+ `evaluate_welding_consumable_control` | 焊口用焊材型号/规格/批号；`qualityCertificates[]`、`physicalItems[]`、领用/烘干记录 | `status`（passed/failed/evidence_insufficient）、`batchTrace: bool` | 批号在证书与领用台账里都能找到，且证书 passed |
| 管材链 | `evaluate_r16_batch_traceability`（R16）+ 标志移植记录（R21） | 焊口所在管线的管材炉批号、`qualityCertificates[]`、`physicalMark` | `status`、`traceMatched: bool` | 炉批号在质量证明与标志移植记录里一致 |

- 状态规则：四链都 closed → closed；任一链 fail 或 failed → conflict；其余（有 insufficient）→ broken，并列出缺哪一类资料。
- 施焊参数在 WPS 范围内（电流、电压、速度、道间温度、线能量）；焊缝标识/焊工标记存在（TSG 31-2025 4.2.2）。
- 汇总：覆盖率（有持证焊工覆盖的焊口比例）、断链清单、冲突清单。

## 11. P8 审查 harness 与模型分层

依据：《审计-低参数模型适配》（2026-09-06，六模型生产数据离线实测）。审计结论是：小模型直接替换 review / projectReview 行不通，但小模型失败里的大头是 harness 缺陷（参数 400、JSON 信封走样、守卫误杀、单次输入 55k token），这些缺陷对大模型同样在浪费 token 和时间。本阶段的目标不是"让小模型追平大模型"，而是**把审查链路做成与模型大小弱相关**：判定进代码，模型只做读和写；格式和参数问题在运行时兜住；守卫只杀真幻觉。做完后再用同一套基准决定哪些角色能降配。

### 11.1 目标与度量

固定基准样本：测试项目4 节点 24（1 片）、测试项目3 节点 2（多片）、测试项目4 一键分析批次 1/2/16/24。每次改动跑六个模型（qwen3.8-max、qwen3.7-plus、qwen-plus、qwen-flash、qwen3-30b、qwen3-8b），记录五个数：通过守卫的诊断条数、失败分片数、信封/JSON 错误数、计费输入输出 token、耗时。

| 指标 | 审计基线 | P8 目标 |
|---|---|---|
| qwen3.7-plus 两节点通过守卫条数 | 3 / 13 | ≥ 8 / 13 |
| qwen-plus 节点 2 信封错误分片 | 6 / 9 | 0（含修复重试） |
| 节点 2 单次审查计费输入 token | 51.7 万 | ≤ 15 万 |
| 节点 2 单次审查耗时（qwen3.7-plus） | 721 s | ≤ 180 s |
| 默认配置下 HTTP 400 的模型 | 4 / 6 | 0 |
| 一键分析节点 24 抓到"证书代号与工艺卡不一致" | 仅 qwen3.8-max | 全部模型（由 P1 工具产出，模型只复述） |

### 11.3 H0 基准固化
- 脚本来源：审计时用的 `pa_model_exp.py`（同一请求多模型）与 `review_model_exp.py`（克隆 AiRun、用 `attach_review_evidence_package_to_ai_run` 重建分片并把分片置回 pending、落库函数置空、走完整 `execute_review_run_inline`）。两处坑必须保留在脚本注释里：克隆会继承 evidenceManifestId/evidenceShardIds，已 completed 的分片会直接复用旧草稿而零模型调用；`create_review_run_from_ai_run` 不重建分片。
- 输出：`experiments/out/<date>/<model>-<project>-<node>.json`（rec + drafts）与一张汇总表；汇总表直接贴进本节 11.1 的度量表。
- 运行方式：只在生产容器里手动跑（`docker exec -w /app -e PYTHONPATH=/app -e AICHECK_LLM_MODEL_REVIEW=<model>`），不进 cron；费用约每轮 ¥10（六模型，按系统单价折算，真实账单以阿里云为准）。频次：每个子阶段合并前一轮、P7 灰度期间每天一轮，一周约 ¥70，由项目负责人批。

### 11.4 H1 运行时模型能力表
- 在 `qwen_runtime` 加一张按模型名前缀匹配的能力表：`maxOutputTokens`（qwen-plus/qwen-flash/qwen3-30b 32,768；qwen3.7-plus/qwen3.8-max 48,000+；qwen3-8b 8,192 待核）、`needsThinkingOff`（qwen3-* 开源系列非流式）、`supportsTools`、`contextTokens`。
- `chat_sync` 在发请求前钳 max_tokens 到表值并写一条 `llmMetadata.clamped` 记录；对 needsThinkingOff 的模型注入 `enable_thinking=false`（流式除外）。现有四处手写的 `enable_thinking=False` 改为依赖运行时。
- 计价：`model_cost_cny` 按模型名查单价表（环境变量 `AICHECK_MODEL_PRICING_JSON` 或表），priceVersion 升到 `per-model-pricing-2026-09`；未命中的模型回退全局单价并在 usage 里标 `priceSource=default`。
- 测试：对每个模型名断言钳制后的参数；对 qwen3-8b 断言注入了 enable_thinking。

### 11.5 H2 分片估算与证据预算
- `_estimated_tokens`：CJK 字符按 1 token、其他按 1/4 估算（审计实测：估算 5,849 → 计费 26,756，比例 4.6）。改完后 AICHECK_REVIEW_SHARD_TARGET_TOKENS 的语义才等于真实 token，目标值重定为 12,000 真实 token 的证据 + 约 8k 固定提示词。
- 证据裁剪（总量才是成本主因，估算修正只让单片诚实）：按节点 requirements 的 materialTypeCode 与证据链 targeting 只装本节点相关的资料版本；人工挂载与 evidenceLinks 永远保留；同一表格的 rows/cellsSummary 别名已在提示词层去重，分片层也去；置信度全 0 且无表格匹配的整页只保留一条"该页 OCR 不可用"的摘要而不是全文。
- 验收：节点 2 从 9 片 / 51.7 万 token 降到 ≤ 15 万；节点 24 单片不变。守卫通过条数不得下降（裁剪掉了必要证据会立刻在基准里显现）。

### 11.6 H3 守卫语料补齐
- `_supplied_identifiers` 增加：规则包里出现的法规/标准号（`rules.yaml` criteria 与 clause package 的编号，例如 TSG Z6002-2026、NB/T 47014-2023）；工程元数据（施工单位、设计单位、监检单位、管道级别、施工起止）；日期变体（`2026-12-25` ↔ `2026年12月25日` ↔ `2026.12.25`，月末规则同证书核验）；编号变体（去连字符、去空格）。
- 原则不变：只补标识符，不补规则正文里的结论词；"覆盖 GC2"仍按肯定结论从严。
- 回归用例直接取审计里被误杀的四类：`Z6002-2010` / `D7006-2020`、`2026年12月25日`、`中石化安装有限公司`、`3832`。

### 11.7 H4 信封修复与分片级重试
- `normalize_llm_findings` 遇到 LLM_OUTPUT_INVALID_ENVELOPE / INVALID_JSON：先用同一模型发一次短修复请求（把原输出发回，要求只输出 `{"findings":[...]}`，max_tokens 4,000）；仍失败则该分片用升级模型（review 的升级链固定为 qwen3.8-max）重试一次；两次都失败才标 failed。
- `generate_sharded_finding_drafts`：失败分片不再让整次审查 review_incomplete，而是完成其余分片、把失败分片列进 `qualityGate.failedShards`，节点状态仍进 waiting_human_review 并在 UI 标"部分分片未完成"。
- 每次修复/升级都记 model_call_attempts（stage=envelope_repair / shard_escalation），基准脚本据此统计。

### 11.8 H5 清单填表模式
- 从 `rules.yaml` 的原子检查项与 `node_requirements` 生成清单：每项 `{itemId, question, ruleCode, expectedEvidence}`。提示词要求模型对每项只填 `{itemId, verdict ∈ 符合|不符合|证据不足|需人工确认, evidenceRefs, note}`，外加最多 3 条 `extraFindings`。
- 代码组装 findings：标题来自清单项，严重度来自规则，肯定结论词只出现在代码生成的标题里，守卫只对 note 和 extraFindings 做断言核对。这样小模型不再需要"想出"审查结构，大模型也少写被丢弃的长描述。
- 用开关 `AICHECK_REVIEW_PROMPT_MODE=checklist|freeform` 灰度；基准同时跑两种模式比较，清单模式的 extraFindings 命中率用来判断它是否漏掉了自由模式能发现的问题。

### 11.9 H6 判定进代码
- 焊接节点的所有覆盖/比对/一致性判定由 P1–P4 的确定性工具产出，模型只解释与补充证据（P6 提示词已有此约束）。审计里"只有 qwen3.8-max 抓到证书代号与工艺卡不一致"这类差距，在工具产出后对所有模型消失。
- 跨文档一致性通用工具（证书号 vs 核验文本、持证人 vs 名册、发证机关 vs 印章）归到 P1 的三方比对里，不在 P8 重复建。

### 11.10 H7 模型分层与 A/B
- documentClassifier：用 ≥200 份已人工确认分类的文件跑 qwen-plus 与 qwen-flash 对照，一致率 ≥97% 才切；切换只改 `build_runtime_env.py` 的 AICHECK_LLM_MODEL_DOCUMENT_CLASSIFIER。
- 材料齐全性预检："某某未提供"由 `build_node_evidence_readiness` 直接生成发现，不再经过模型。
- review 角色 A/B：一周内每天用基准跑一次 qwen3.7-plus 与 qwen3.8-max，另在生产挑 5 个真实节点各跑两次 AiRun 对比通过守卫条数、耗时、费用；qwen3.8-max 全面占优即切换。
- 备胎：AICHECK_LLM_FALLBACK_MODEL_REVIEW 由 deepseek-v4-pro 改为 DashScope 内的另一模型（或给 DeepSeek 充值），否则主供应商故障时无兜底。

### 11.11 风险
- **证据裁剪裁掉必要证据**：以守卫通过条数不降为硬门槛，人工挂载与证据链永不裁。
- **清单模式漏掉清单外问题**：保留 extraFindings，基准里与自由模式对照；清单本身随 rules.yaml 演进。
- **守卫放宽引入幻觉**：只加标识符不加结论词，回归用例锁住。

### 12.3 结论卡与发现的契约（前后端共用）

**状态映射表**（全文唯一词表，P6 卡片、结论卡、发现分组、颜色都按此表）：

| 来源 | 取值 | 术语 | 结论卡分组 | 颜色 |
|---|---|---|---|---|
| 确定性工具结果 | failed | 不符合 | 需处理 | 红 |
| 通过守卫的发现 severity | critical / high | 不符合 | 需处理 | 红 |
| 通过守卫的发现 severity | medium / low | 预警 | 待确认 | 橙 |
| 确定性工具结果 | evidence_insufficient；或发现 groundingStatus = insufficient_evidence | 证据不足 | 证据不足（折叠组） | 灰 |
| 发现 suggestedAction = human_confirm 且原因属系统能力之外（印章真伪、签字本人、纠错代号） | — | 需人工确认 | 待确认 | 蓝 |
| 发现带 `policyPending: true` | — | 口径待确认 | 待确认 | 蓝，附口径名 |
| 确定性 passed 且无 critical/high 发现 | — | 未见问题 | 未见问题 | 绿 |

**结论推导决策表**（按行从上到下第一条命中即为结论）：

| 序 | 条件 | 结论 |
|---|---|---|
| 1 | 任一确定性工具 failed，或任一通过守卫的发现 severity ∈ {critical, high} | 需处理 |
| 2 | 无第 1 条，且存在通过守卫的 medium/low 发现，或存在需人工确认 / 口径待确认 项 | 待确认 |
| 3 | 无第 1、2 条，且存在证据不足项（含所有发现都被守卫降级的情形） | 证据不足 |
| 4 | 确定性工具全部 passed 或 not_applicable，且无任何发现 | 未见问题 |

- **结论**四选一：需处理 / 待确认 / 证据不足 / 未见问题，只由上表推导，不由模型自由发挥。
- **一句话** ≤40 字，说这个节点现在卡在哪。
- **三个数字**：需处理 N、待确认 N、证据不足 N（合并后）。
- **关键事实** ≤3 条，每条 ≤40 字并带一个证据位置（文件 + 页）。
- **建议动作** 1 条，枚举：发联络单 / 要求补资料 / 现场核对原件 / 平台核验 / 人工确认。
- **发现三组**：需处理（通过守卫且 severity ≥ high）→ 待确认（通过守卫其余）→ 证据不足（折叠一组，展开为去重待核对项，模型原文可再展开）。
- **单条发现**：标题 ≤30 字只说差距；正文 ≤120 字，固定"查到什么 → 差在哪 → 怎么做"；证据 / 规则 / 动作 chips；超长默认收起三行。
- **工程级**：节点优先级表（结论、最高严重度、需处理条数）+ 共性风险 ≤3。

### 14.1 N-03 TSG 时间线同步脚本 `scripts/sync_tsg_catalog.py`（依据《研究-TSG规范在线核验源》）

**三段抓取**
1. 目录：特种设备局“安全技术规范”栏目分页接口（GET，`paramJson={"pageNo":N,"pageSize":10}`，共 111 条），解析标题、TSG 编号、发布日期、详情页、PDF 链接。解析不出编号的（修改单公告、试行文件）单独列出，不进时间线。编号解析规则：

```
TSG\s*([A-Z]{0,2}\d{2,4})[—\-－–](\d{4})
```

2. 公告：按编号在总局“政府信息公开 › 特种设备 公告”与“特种设备局 › 通知公告”两个栏目检索，解析固定措辞“对《X》（TSG …）进行了修订/整合修订 … 自 YYYY 年 M 月 D 日起施行”，得到 实施日期 与 被修订编号列表；办公厅通知（如 市监特设发〔2026〕85 号）解析过渡条款。
3. 附则：下载 PDF，从目录页取“附则”页码，只 OCR 附则 1–2 页，抽“自 … 起施行 … 同时废止：(1)…(2)…”得到 正式废止列表；与公告的被修订列表比对，不一致的标“待人工核对”。

**时间线字段**：编号、名称、发布日期、实施日期、替代编号、被替代编号、废止日期、过渡期截止、来源 URL（目录/公告/PDF 三个）、抽取方式（规则/OCR）、核对人、核对日期。写入 `business_packs/engineering_inspection_v1/standard_version_timeline.yaml`，GB/NB 条目由 `lookup_standard_status` 的结果同表落地。

**R08 判定**（AC-R08-01 改）：设计文件引用的 TSG 编号 → 时间线：现行 → 通过；已被替代且设计签发日期在新版实施日之后 → 过渡期内预警（要求书面确认）/ 过渡期外不符合；未收录 → 在线查询 + 人工确认；OCR 抽取且未核对的条目 → 只给预警不给不符合。

**运行方式**：手动或每月一次 cron，输出变更清单（新增、实施日期变化、废止关系变化），变化必须人工核对后才合并到 YAML；不在审查请求路径上实时抓取。

**验收**：111 条目录全量解析成功率 ≥ 95%（解析失败条目列表可读）；三份样本（TSG 31-2025、Z6002-2026、08-2026）的实施日期与废止关系与人工核对一致；节点 8 对测试项目3/4 的 6 处作废引用输出“过渡期预警”并附来源 URL。

## 17. P12 审计反馈飞轮（依据《研究-审计agent自我迭代》）

目标：让审计量与人工纠正量变成下一版资产的输入。迭代对象是四层可版本化资产（数据表、守卫语料、提示词与清单模板、案例库与回归用例），不训练模型权重；迭代方式是"离线回放 → 指标不降 → 影子运行 → 灰度 → 全量"，任何自动调整不得改变已出具的结论。

### 17.1 现状（2026-09-06 生产核实）

- 生成侧没有任何代码读取人工纠正。

### 17.4 规则
- 单人纠正只进回归用例，不改数据表与守卫语料；合并要求 ≥2 名审查人、≥2 个项目一致。
- canUseForEval 与 canUseForTraining 分开；被后续纠正推翻的纠正降级为“争议样本”，不进基准。
- 迭代只影响新审查；历史 AiRun 保持原样，回放结果单独存。
- 资产发版前必须通过回放：§17.3 指标不降，且人工已确认的结论零翻转。

### 17.5 验收
- F1：测试项目3 节点 2 上完成一次“人工结论 ≠ AI 建议”的提交，review_opinions 与 ai_feedback 各有一条可按 aiRunId 关联的记录；证据链驳回一次，manualComment 为选定原因而非常量；退回补正一次，rectifications 带 finding id。
- F2：117 次历史 AiRun 回填后，基准脚本输出 §17.3 全部指标，triage 页能按七类筛选。
- F3：制造一条守卫误杀（法规号 Z6002-2010）→ 三人两项目标“其实有依据”→ 候选 → 回放降级率下降 → 合并；制造一条限值纠正 → 候选行 → 核对 → 合并；制造一条改写 → 案例库 → 下一次同规则审查的提示词里检索到该案例。
- F4：盲审任务连续两周产出橡皮图章指数；影子运行对同一节点产出新旧版本对比表；业务包快照哈希随语料版本变化。

### 17.6 风险
- **没有燃料**：监检人员不在系统里提交结论，一切为零。F1 之后把采集覆盖率放进 P7 探针，低于 80% 报警。
- **飞轮固化错误**：靠 F4 盲审与 ≥2 人 ≥2 项目的合并门槛；单条纠正永不直接改规则。
- **纠正数据的合规**：canUseForTraining 默认 false，只做评估与检索，不做训练；dataSensitivity 按 FDE triage 现有字段。
- **案例库过时**：案例带版本与失效日期，规则文本变更自动下架。
