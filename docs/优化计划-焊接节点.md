# 焊接节点（24–29）优化计划

> 日期：2026-09-06。依据：《研究-焊接材料设计节点审查原则》（法规/标准事实与代码差距）与《规则测试-焊接材料设计节点-测试项目3与4》（真实资料判定与规则反馈）。范围：节点 24 焊工资格、25 焊接工艺文件、26 焊材质量证明、27 焊材管理、28 管道组对、29 施焊参数/记录/焊缝标识，以及它们与设计（5–9）、管材（16/21）节点的联动。本文只做计划，不含代码。

## 0. 目标与验收口径

**目标**：让六条原则在焊接节点上变成可自动执行、可解释、可回溯到原件位置的判定，而不是模型自由发挥。

**验收口径**（用测试项目3/4 作回归样本，期望结论已在规则测试报告中给出）：
1. 节点 24 对 测试项目4 姜军 给出"GTAW、SMAW 两项均覆盖 20# Φ108×8 6G"，引用证书代号、工艺卡参数与 TSG Z6002-2026 表 A-6/A-7/A-8 的具体条目；对 测试项目3 给出"按 WPS 无背面保护气无人覆盖；赵相军/席俊杰 若现场充氩则覆盖；姜军 FeⅡ 不覆盖 FeⅣ；李卫伍 平台未返回焊接项目需人工核查"。
2. 节点 25 对 测试项目4 PQR HP/P-2023-01 给出"母材 Fe-1-1、T=7 覆盖 1.5~14、GTAW 焊缝金属 pWPS 写 ≤6 超出 2t=4（预警）、PQR 未按 2023 版复核（预警）"；对 测试项目3 给出"Fe-8-1 T=6 覆盖 3mm；位置 1G 为次要因素；背面保护气与焊工证书冲突"。
3. 节点 26 对 测试项目4 判"焊材证明书缺失，不符合"；对 测试项目3 判"证书缺熔敷金属力学/执行标准/生产日期，证据不足；JQ.TG304 与 WPS H06Cr19Ni10 需型号等效确认"。
4. 节点 29 在缺施焊记录时明确输出"焊口联合表无法构建，四链闭合失败"，并列出缺哪一类资料。
5. 每条发现都带 evidenceRefs（页码/bbox/原文）与规则条款号，正式审查可引用。
6. 单元测试覆盖覆盖表的每一行；测试项目3/4 的 OCR 快照作为端到端回归数据。

## 3. P1 节点 24 焊工资格

### 3.1 数据层：`business_packs/engineering_inspection_v1/welder_qualification.yaml`
- `editions`: `tsg_z6002_2010`（施焊日期 < 2026-08-01）、`tsg_z6002_2026`（≥ 2026-08-01；证书有效期内旧证按新表）。
- `methods`: SMAW/GTAW/GMAW/FCAW/SAW/PAW/OFW…，别名表（氩弧焊→GTAW，药芯气保焊→FCAW）。
- `materialCategories`: FeⅠ~FeⅣ 牌号清单（表 A-2 全量）+ NB/T 47014 类别→TSG 类别映射（Fe-1/3/4/5A→FeⅠ/Ⅱ，Fe-5B/6/7→FeⅢ，Fe-8/10→FeⅣ）；覆盖矩阵两版各一份。
- `positions`: 表 A-6 覆盖矩阵（含 5GX/6GX、板试件用于管件 D≥76、角焊缝/管板）。
- `thickness`: 表 A-7（T<12→2t；≥12→不限）、气焊、堆焊表 A-12。
- `diameter`: 表 A-8/A-10（<25→≥D；25~76→≥25；≥76→≥76；向下焊 ≥300→≥76）。
- `filler`: 表 A-3 覆盖链（Fef1/2/3/3J/4/4J/FefS）+ 焊材型号→Fef 类别映射（E4303→Fef3、E4315/E5015→Fef3J、E308-16→Fef4、E308-15→Fef4J、焊丝→FefS）。
- `processFactors`: 01/02/03/10/11/12/13/14/23/24 参与比较；`11→10 allowed`；FeⅢ 的 10 豁免；机动焊因素表。
- `backing`: 无(K) 覆盖有(K)；带(K) 只覆盖带衬垫/双面焊/角焊缝/不焊透接头；"后焊方法视为带衬垫"。

### 3.2 代号解析 `decode_welder_code` v2
- 模糊纠错表：`CTAF/CTAV/GTAV→GTAW`、`SHAV/SHAW/SMAY→SMAW`、`PTAV→GTAW?`（标记低置信）、`FetS/Fe1S/FefS`、`Fef3J/FefBJ/Fe13J`、`Fef4J/Fe14J`、`6C→6G`、`5FC/6FG`、`63/57→6G-3/57`；全角/罗马数字规范化；每段带 `confidence` 与 `rawSegment`。
- 结构校验：六段 + 工艺因素；板/管判别（有 `/` 为管）；(K) 提取；组合考试（"和"连接）拆成多项。
- 输出 `parseStatus: parsed | corrected | unsupported`，corrected 时在发现里提示"代号 OCR 已纠错，请核对原件"。

### 3.3 覆盖判定 `check_welder_work_coverage` v2
- 输入：焊口/管线事实（方法、母材牌号→类别、外径、壁厚、焊缝金属厚度按方法拆分、位置、是否向下焊、衬垫/打底、背面保护气、填充金属类型/焊材型号、极性）来自 WPS/工艺卡 + 管道特性表 + 施焊记录。
- 逐维度输出 `checks[]`（每项含规则条款：如 `TSG Z6002-2026 表 A-8`），任一 fail 即不覆盖；`evidence_insufficient` 只在关键输入缺失时。
- **WPS 联动**：工艺因素与衬垫取自 WPS/工艺卡而非证书自身；工艺卡"持证项目"文本与参数表矛盾 → 单独 `process_card_inconsistent` 预警。
- 组合工艺：GTAW 打底 + SMAW 盖面分别判定；后焊方法自动视为带衬垫；焊缝金属厚度按各方法层厚（工艺卡"层/道"表）估算，缺失时按"打底 ≤3mm、其余为壁厚减打底"保守估算并标注。
- 版本：按施焊日期选表；证书批准日期 < 2026-08-01 的旧证在 2026-08-01 后按新表。

### 3.4 三方比对与真实性
- 输入源优先级：平台记录 > 证书原件 OCR > 焊工清单；任何不一致生成 `roster_certificate_platform_mismatch` 发现（列三方值）。
- `check_certificate_validity` 保留（有效期覆盖施焊期）；新增"连续中断 6 个月能力验证"提示（需用人单位记录，缺失 → 需人工确认）。
- 平台"聘用单位"与施工单位不一致 → 预警级发现（待你决定是否升级）。
- 无效证据识别：非中文/测试用文件（如"AICheck Upload Verification"）→ `invalid_evidence`。

### 3.5 输出与展示
- 节点 24 卡片：每位焊工一行（姓名、证号、平台状态、项目代号、有效期）+ 每个焊口/管线一列的覆盖矩阵（✓/✗/?），点击展开逐维度依据。
- 发现模板：`焊工{姓名} {代号} 对 {管线} {方法} 覆盖/不覆盖：{维度} {实际} vs {证书范围}（{条款}）`。

### 3.6 测试
- 覆盖表逐行单测（2010/2026 各一套）；OCR 纠错单测（本次真实 OCR 串）；测试项目3/4 快照端到端；边界：D=25/76、t=12、5GX、FeⅢ 因素 10 豁免、组合考试拆分。

## 5. P3 节点 26/27 焊材

### 5.1 数据层：`welding_consumables.yaml`
- 型号解析规则：E/ER/S/F/TS 前缀语法、强度级别、药皮/成分代号、后缀（-B2、-G、H5）；商品牌号→型号对照（J422/J427/J506/J507/R307/R317/A102/A022/A132/A137/A302/A062/H08A/H08MnA/H10Mn2/H08Mn2SiA/TIG-J50/TIG-R40/H13CrMoA/H08CrMoVA/H0Cr21Ni10/H00Cr19Ni12Mo2/JQ.TG304→ER308…），带来源与置信度；未知牌号 → 需人工确认。
- 母材→焊材推荐/等强表（第 3.3 节）：按母材牌号或 NB/T 47014 组别给允许型号集合与最低强度级别；异种钢规则；耐热钢 Cr/Mo/V 匹配；不锈钢按成分族（308/316L/309L）。
- 熔敷金属限值档案（第 3.5 节，待核后固化）：按型号索引成分与力学范围。
- 保管规则：湿度 ≤60%，库存期限以证明书/说明书为准（无则按 `defaultShelfLifeMonths` 配置并标"默认值"），烘干参数按类型默认表（待核）。

### 5.2 抽取
- OCR profile `welding_material_certificate_v1`：型号/牌号/规格/批号/生产日期/执行标准/成分表/力学表/扩散氢/检验章；支持金桥式"要求-实测"两列表格。

### 5.3 判定

- 发现模板：`焊材 {型号/牌号} 批 {批号}：{缺项/超限/不匹配/超期}（{标准条款}）`。

## 6. P4 焊口联合表（节点 29 为核心）

### 6.1 数据结构 `weld_joint_ledger`
- 主键：焊口号（施焊记录）；字段：管线号、规格、材质→类别、位置、方法（按层）、焊工代号/证号、焊材型号/规格/批号（按层）、WPS 号、PQR 号、管材炉批号（来自标志移植/管材证）、日期、电参数、道间温度、背面保护气、NDT 结果引用。

## 11. P8 审查 harness 与模型分层

依据：《审计-低参数模型适配》（2026-09-06，六模型生产数据离线实测）。审计结论是：小模型直接替换 review / projectReview 行不通，但小模型失败里的大头是 harness 缺陷（参数 400、JSON 信封走样、守卫误杀、单次输入 55k token），这些缺陷对大模型同样在浪费 token 和时间。本阶段的目标不是"让小模型追平大模型"，而是**把审查链路做成与模型大小弱相关**：判定进代码，模型只做读和写；格式和参数问题在运行时兜住；守卫只杀真幻觉。做完后再用同一套基准决定哪些角色能降配。

### 11.1 目标与度量

固定基准样本：测试项目4 节点 24（1 片）、测试项目3 节点 2（多片）、测试项目4 一键分析批次 1/2/16/24。每次改动跑六个模型（qwen3.8-max、qwen3.7-plus、qwen-plus、qwen-flash、qwen3-30b、qwen3-8b），记录五个数：通过守卫的诊断条数、失败分片数、信封/JSON 错误数、计费输入输出 token、耗时。

| 指标 | 审计基线 | P8 目标 |
|---|---|---|
| qwen3.7-plus 两节点通过守卫条数 | 3 / 13 | ≥ 8 / 13 |
| qwen-plus 节点 2 信封错误分片 | 6 / 9 | 0（含修复重试） |
| 节点 2 单次审查计费输入 token | 51.7 万 | ≤ 15 万 |
| 节点 2 单次审查耗时（qwen3.7-plus） | 721 s | ≤ 180 s |
| 默认配置下 HTTP 400 的模型 | 4 / 6 | 0 |
| 一键分析节点 24 抓到"证书代号与工艺卡不一致" | 仅 qwen3.8-max | 全部模型（由 P1 工具产出，模型只复述） |

### 11.3 H0 基准固化
- 脚本来源：审计时用的 `pa_model_exp.py`（同一请求多模型）与 `review_model_exp.py`（克隆 AiRun、用 `attach_review_evidence_package_to_ai_run` 重建分片并把分片置回 pending、落库函数置空、走完整 `execute_review_run_inline`）。两处坑必须保留在脚本注释里：克隆会继承 evidenceManifestId/evidenceShardIds，已 completed 的分片会直接复用旧草稿而零模型调用；`create_review_run_from_ai_run` 不重建分片。
- 输出：`experiments/out/<date>/<model>-<project>-<node>.json`（rec + drafts）与一张汇总表；汇总表直接贴进本节 11.1 的度量表。
- 运行方式：只在生产容器里手动跑（`docker exec -w /app -e PYTHONPATH=/app -e AICHECK_LLM_MODEL_REVIEW=<model>`），不进 cron；费用约每轮 ¥10（六模型）。

### 11.4 H1 运行时模型能力表
- 在 `qwen_runtime` 加一张按模型名前缀匹配的能力表：`maxOutputTokens`（qwen-plus/qwen-flash/qwen3-30b 32,768；qwen3.7-plus/qwen3.8-max 48,000+；qwen3-8b 8,192 待核）、`needsThinkingOff`（qwen3-* 开源系列非流式）、`supportsTools`、`contextTokens`。
- `chat_sync` 在发请求前钳 max_tokens 到表值并写一条 `llmMetadata.clamped` 记录；对 needsThinkingOff 的模型注入 `enable_thinking=false`（流式除外）。现有四处手写的 `enable_thinking=False` 改为依赖运行时。
- 计价：`model_cost_cny` 按模型名查单价表（环境变量 `AICHECK_MODEL_PRICING_JSON` 或表），priceVersion 升到 `per-model-pricing-2026-09`；未命中的模型回退全局单价并在 usage 里标 `priceSource=default`。
- 测试：对每个模型名断言钳制后的参数；对 qwen3-8b 断言注入了 enable_thinking。

### 11.5 H2 分片估算与证据预算
- `_estimated_tokens`：CJK 字符按 1 token、其他按 1/4 估算（审计实测：估算 5,849 → 计费 26,756，比例 4.6）。改完后 AICHECK_REVIEW_SHARD_TARGET_TOKENS 的语义才等于真实 token，目标值重定为 12,000 真实 token 的证据 + 约 8k 固定提示词。
- 证据裁剪（总量才是成本主因，估算修正只让单片诚实）：按节点 requirements 的 materialTypeCode 与证据链 targeting 只装本节点相关的资料版本；人工挂载与 evidenceLinks 永远保留；同一表格的 rows/cellsSummary 别名已在提示词层去重，分片层也去；置信度全 0 且无表格匹配的整页只保留一条"该页 OCR 不可用"的摘要而不是全文。
- 验收：节点 2 从 9 片 / 51.7 万 token 降到 ≤ 15 万；节点 24 单片不变。守卫通过条数不得下降（裁剪掉了必要证据会立刻在基准里显现）。

### 11.6 H3 守卫语料补齐
- `_supplied_identifiers` 增加：规则包里出现的法规/标准号（`rules.yaml` criteria 与 clause package 的编号，例如 TSG Z6002-2026、NB/T 47014-2023）；工程元数据（施工单位、设计单位、监检单位、管道级别、施工起止）；日期变体（`2026-12-25` ↔ `2026年12月25日` ↔ `2026.12.25`，月末规则同证书核验）；编号变体（去连字符、去空格）。
- 原则不变：只补标识符，不补规则正文里的结论词；"覆盖 GC2"仍按肯定结论从严。
- 回归用例直接取审计里被误杀的四类：`Z6002-2010` / `D7006-2020`、`2026年12月25日`、`中石化安装有限公司`、`3832`。

### 11.7 H4 信封修复与分片级重试
- `normalize_llm_findings` 遇到 LLM_OUTPUT_INVALID_ENVELOPE / INVALID_JSON：先用同一模型发一次短修复请求（把原输出发回，要求只输出 `{"findings":[...]}`，max_tokens 4,000）；仍失败则该分片用升级模型（review 的升级链固定为 qwen3.8-max）重试一次；两次都失败才标 failed。
- `generate_sharded_finding_drafts`：失败分片不再让整次审查 review_incomplete，而是完成其余分片、把失败分片列进 `qualityGate.failedShards`，节点状态仍进 waiting_human_review 并在 UI 标"部分分片未完成"。
- 每次修复/升级都记 model_call_attempts（stage=envelope_repair / shard_escalation），基准脚本据此统计。

### 11.8 H5 清单填表模式
- 从 `rules.yaml` 的原子检查项与 `node_requirements` 生成清单：每项 `{itemId, question, ruleCode, expectedEvidence}`。提示词要求模型对每项只填 `{itemId, verdict ∈ 符合|不符合|证据不足|需人工确认, evidenceRefs, note}`，外加最多 3 条 `extraFindings`。
- 代码组装 findings：标题来自清单项，严重度来自规则，肯定结论词只出现在代码生成的标题里，守卫只对 note 和 extraFindings 做断言核对。这样小模型不再需要"想出"审查结构，大模型也少写被丢弃的长描述。
- 用开关 `AICHECK_REVIEW_PROMPT_MODE=checklist|freeform` 灰度；基准同时跑两种模式比较，清单模式的 extraFindings 命中率用来判断它是否漏掉了自由模式能发现的问题。

### 11.9 H6 判定进代码
- 焊接节点的所有覆盖/比对/一致性判定由 P1–P4 的确定性工具产出，模型只解释与补充证据（P6 提示词已有此约束）。审计里"只有 qwen3.8-max 抓到证书代号与工艺卡不一致"这类差距，在工具产出后对所有模型消失。
- 跨文档一致性通用工具（证书号 vs 核验文本、持证人 vs 名册、发证机关 vs 印章）归到 P1 的三方比对里，不在 P8 重复建。

### 11.10 H7 模型分层与 A/B
- documentClassifier：用 ≥200 份已人工确认分类的文件跑 qwen-plus 与 qwen-flash 对照，一致率 ≥97% 才切；切换只改 `build_runtime_env.py` 的 AICHECK_LLM_MODEL_DOCUMENT_CLASSIFIER。
- 材料齐全性预检："某某未提供"由 `build_node_evidence_readiness` 直接生成发现，不再经过模型。
- review 角色 A/B：一周内每天用基准跑一次 qwen3.7-plus 与 qwen3.8-max，另在生产挑 5 个真实节点各跑两次 AiRun 对比通过守卫条数、耗时、费用；qwen3.8-max 全面占优即切换。
- 备胎：AICHECK_LLM_FALLBACK_MODEL_REVIEW 由 deepseek-v4-pro 改为 DashScope 内的另一模型（或给 DeepSeek 充值），否则主供应商故障时无兜底。

### 11.11 风险
- **证据裁剪裁掉必要证据**：以守卫通过条数不降为硬门槛，人工挂载与证据链永不裁。
- **清单模式漏掉清单外问题**：保留 extraFindings，基准里与自由模式对照；清单本身随 rules.yaml 演进。
- **守卫放宽引入幻觉**：只加标识符不加结论词，回归用例锁住。
- **升级重试的费用**：只在分片失败时触发，基准统计升级次数；若某模型升级率 >30%，说明该模型不适合该角色，直接不用。
- **基准样本单一**：两个节点一批四节点只够看方向，P7 回归集扩到 3–5 个典型工程后再下"能降配"的结论。
