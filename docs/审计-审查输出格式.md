# 审计：审查输出的内容格式（监检人员抓不到重点的原因与改法）

日期：2026-09-06　范围：节点级 AI 审查发现、AI 建议（opinionDraft）、一键分析结果的呈现
方法：读生产库最近 25 次有发现的 AiRun（106 条发现），逐条统计文本形态；读后端接地守卫与分片合并代码；读前端三处渲染路径。配套网页含"现状 vs 改后"的对照样张。

## 0. 结论先行

监检人员看不到重点，不是因为模型写得长，而是因为**系统把最没有信息量的一句话复制了最多遍，又把最有信息量的字段藏起来了**。

| 现象 | 数据（最近 25 次 AiRun，106 条发现） |
| --- | --- |
| 标题就是模板句"证据不足，需人工确认" | 71 / 106（67%） |
| 同一次审查里标题重复 | 46 / 106（43%）；测试项目3 节点 2 最近一次 13 条里 10 条一模一样 |
| 正文长度中位数 | 94 字，正好等于那句模板的长度 |
| 正文最长 | 884 字，内容是一段原始 JSON 被当正文渲染 |
| 顶部"AI 建议"（opinionDraft）就是那句模板 | 20 / 25 次 |
| 前端渲染 unsupportedClaims（模板句里让读者"见本条的 unsupportedClaims"） | 0 处 |
| 前端渲染 suggestedAction / findingType | 0 处（监检面板） |
| 前端排序、分组、折叠 | 无；按后端顺序平铺，正文不截断 |
| 后端已有的工程级优先级摘要（priorityReviewNodeIds / commonRisks） | 有 API，无任何页面渲染 |
| **节点级 AI 复核的发现列表在监检面板上根本不渲染** | 登录实测测试项目3 节点 2：库里 13 条发现，页面 0 张卡；面板从运行的自由文本 outputText 解析发现，忽略已存的 findings 数组；67 次完成的节点运行里只有 20 次有可解析的文本 |

所以监检人员打开一个节点看到的是：顶部一句"模型给出的业务结论缺少证据支持……"，标题栏"13 条 · 均需人工确认"，正文再来一句"当前节点形成 13 条审查发现，所有结果均需人工确认"，然后 10 张一模一样的卡，真正有内容的 3 张混在中间，且没有任何一处告诉他"先看哪条、去查哪份、该做什么"。

改法分三层，前端一层就能解决大半（在此之前还有一个半天的 R0：节点级运行的发现目前根本没渲染，先让它显示出来）：
1. **前端（1–2 天）**：结论先行；按"需处理 / 待确认 / 证据不足"分组排序；证据不足的合并成一组折叠；把 unsupportedClaims 翻成人话显示；正文默认三行；渲染现成的工程级优先级摘要。
2. **守卫与合并（0.5–1 天）**：无据断言分支不再销毁模型原文；合并时按"断言集合"去重；opinionDraft 永远不取模板句。
3. **输出契约（1–2 天，并入 harness 计划 H5）**：发现增加 摘要 / 关键事实 / 差距 / 动作 四个短字段，长度在校验层强制。

## 1. 现状：一条发现是怎么变成那句模板的

### 1.0 登录实测：节点级运行的发现根本没显示
用 inspection 账号打开测试项目3 节点 2 的「AI 复核」：面板只有一行结论标签"证据不足"、一句模板正文、一张证照核验卡，然后是历史三次运行各一句同样的模板；下方「人工审查」区的「总体意见」也是同一句模板。DOM 里 `ai-finding` 卡片数为 0。

原因在 `Workbench.vue`：传给面板的 `nodeFindings` 来自 `parseAiFindings(aiRecheckDisplay.outputText)`，即把运行的自由文本当 JSON 解析；这次运行的 llmResultText / outputText 都是空的，于是 13 条已落库的 findings 一条都没进面板。67 次状态为完成的节点运行里只有 20 次的文本以 `{` 开头可解析，其余 47 次监检人员看到的都是"零发现 + 一句模板"。就算解析成功，这条路径也把 evidenceRefs / ruleRefs 强制置空，证据链接不会出现。

也就是说，目前节点级 AI 审查对监检人员可见的全部内容，就是 opinionDraft 那一句话。而 opinionDraft 在 25 次里 20 次是模板。

### 1.1 模型端没有任何篇幅或结构约束
- 节点审查系统提示词只有一句话（`libs/db/seed.py` PTPL-review-202606）："只输出有证据支撑的审查建议。不得对最终业务状态作出批准。"输出 schema 里 title / description 都是自由字符串，没有长度、没有"先说什么后说什么"。
- 一键分析同样：schema 只有 findingType / severity / title / description / evidenceRefs。
- 结果是模型按自己的习惯写：大模型一条正文 150–300 字，小模型一句话；同一节点 9 个分片各自为政。

### 1.2 守卫把"有内容"改写成"没内容"
`libs/review_grounding.apply_grounding_guardrails` 有两条降级分支：
- **分片证据不可定位 / 正式模式无引用**：标题改成"证据不足，需人工确认"，正文 = 警示句 + 模型原文（保留 modelTitle / modelDescription）。这一支还能让人知道去查哪份。
- **含无据断言（unsupported claims）**：标题改成"证据不足，需人工确认"，正文替换成固定的 94 字模板，**模型原文整条丢弃**，只在 unsupportedClaims 里留下被判无据的 token（如"许可证"、"2026-12-25"、"江苏三江机电工程有限公司"）。代码注释写明"这里不能带出原文，原文本身就是问题"。

第二支是 71 条模板标题的来源。而 unsupportedClaims 里的 token 恰恰是监检人员最需要的线索（哪家单位、哪个日期、哪个编号需要核对），前端却没有渲染它。

### 1.3 合并层不合并
9 个分片各产出一条"证据不足"，`shard_execution._finding_key` 用 (findingType, title, description, severity, suggestedAction) 去重。模板句的 title/description 完全相同，但 severity 不同（high/medium/low 随模型心情）就成了不同的 key，于是 10 条模板并排。`node_finding_aggregates.conflicts` 里其实已经把它们标成了同标题冲突组，前端也没用。

### 1.4 顶部摘要取错了字段
`execution.py` 把 `findingDrafts[0].description` 直接当作 `suggestion.opinionDraft`。第一条常常就是降级过的模板句，于是 25 次里 20 次的"AI 建议"是"模型给出的业务结论缺少证据支持……"。另有一条旧的本地降级路径把整段 JSON 塞进 description（AIRUN-11-05E2F6F5，884 字），监检人员看到的是花括号。

### 1.5 前端：平铺、不排、不折、丢字段
`WorkbenchAiReviewPanel.vue` + `workbenchReviewPresentation.ts`：
- 发现按后端顺序平铺，无排序、无分组、无去重、正文无行数限制；唯一被截断的是证据引文（短的那部分）。
- 每条只渲染 title / description / severity / confidence / evidenceRefs / ruleRefs；`typeLabel` 算了但没渲染；`suggestedAction`、`groundingStatus`、`unsupportedClaims`、`kbRefs`、`manualConfirmItems` 在监检面板不存在。
- "均需人工确认"在标题栏、摘要句、每张卡上各说一遍，却没有一处说"哪条要紧"。
- 严重度词表有两套（提示/一般/重要/严重 vs 高/中/低），B 工作台直接渲染英文 `medium`。
- 一键分析没有结果页，只能逐节点看；后端 `ProjectReviewSummary`（nodeSummaries / commonRisks / priorityReviewNodeIds）没有任何页面使用。

## 2. 监检人员真正需要的阅读顺序

对一个节点，读者要在一屏内回答三个问题：**要不要管、去查哪份、做什么**。据此定义输出契约：

**节点结论卡（永远在最上面）**
- 结论：需处理 / 待确认 / 证据不足 / 未见问题（四选一，由确定性结果 + 通过守卫的最高严重度决定，不由模型自由发挥）。
- 一句话（≤40 字）：这个节点现在卡在哪。
- 三个数字：需处理 N、待确认 N、证据不足 N。
- 关键事实 ≤3 条（每条 ≤40 字，每条带一个证据位置）。
- 建议动作 1 条（枚举：发联络单 / 要求补资料 / 现场核对原件 / 平台核验 / 人工确认）。

**发现列表（分三组，组内按严重度）**
1. 需处理：通过守卫且 severity ≥ high。
2. 待确认：通过守卫的其余。
3. 证据不足（折叠为一组）：一行"N 条结论未经证据核实"，展开后是去重的"待核对项"清单（由 unsupportedClaims 翻译成"核对 持证单位『江苏三江机电工程有限公司』与项目施工单位是否一致"这样的句子），模型原文可再展开。

**每条发现的固定结构**
- 标题 ≤30 字，只说差距，不说过程。
- 正文 ≤120 字，固定三段：查到什么 → 差在哪 → 怎么做。
- 证据 chips（文件 + 页），规则条款 chip，动作 chip。
- 超出长度的正文默认收起三行。

**工程级（一键分析）**
- 先给节点优先级表：节点、结论、最高严重度、需处理条数，按优先级排序；再给"跨节点共性风险"三条以内。这两个字段后端已经算好（`autoReview.ts` ProjectReviewSummary），只缺页面。

## 3. 改法与工作量

### R0 先把发现显示出来（半天，前端）
- `Workbench.vue` 的 `nodeAiPresentationFindings` 改为直接读 `aiRun.findings`（后端 `nodes/{id}/package` 的 aiRuns 已带全量 findings），保留 evidenceRefs / ruleRefs / groundingStatus / unsupportedClaims / suggestedAction；文本解析只作为没有 findings 数组时的回退。
- 验收：测试项目3 节点 2 页面出现 13 张卡（改完 R1 后变成 1 张结论卡 + 3 条 + 1 组）。

### R1 前端（1–2 天，不改后端即可上线）
- `workbenchReviewPresentation.ts`：新增 `groupWorkbenchFindings`（分组 + 排序 + 证据不足合并 + 按 unsupportedClaims 集合去重）；新增 `humanizeUnsupportedClaims`（token → 待核对句）；结论卡由现有字段推导（deterministicResult、最高严重度、通过守卫条数）。
- `WorkbenchAiReviewPanel.vue`：结论卡置顶；三组渲染；证据不足组默认折叠；正文 `line-clamp: 3` + 展开；渲染 suggestedAction 与 typeLabel；统一严重度词表。
- 一键分析：新增 `ProjectAnalysisSummaryPanel.vue`，渲染 ProjectReviewSummary 的优先级表与共性风险。
- 验收：测试项目3 节点 2 最近一次运行（13 条）在改后应显示为 1 张结论卡 + 3 条待确认 + 1 个折叠组（10 条合并，去重后待核对项约 6 项）。

### R2 守卫与合并（0.5–1 天）
- `review_grounding`：无据断言分支同样保留 modelTitle / modelDescription（标记 `unverified: true`，前端默认不展示、可展开）；模板句只作 description 的前缀而不是全部。
- `shard_execution._finding_key`：对降级条目改用 (title, sorted(unsupportedClaims)) 作 key，severity 不参与；合并时严重度取最高。
- `execution.py` opinionDraft：取第一条通过守卫的发现的标题，没有则取确定性结果的说明；永远不取模板句。删掉把 JSON 当正文的本地降级路径。
- 验收：重跑测试项目3 节点 2，opinionDraft 不再是模板；模板标题条数从 10 降到 ≤3 组。

### R3 输出契约（1–2 天，并入 harness 计划 H5 清单模式）
- finding schema 增加 `summary`(≤40)、`facts[≤3]{text≤40, evidenceRef}`、`gap`(≤60)、`action`(枚举)；`description` ≤150。
- `validate_project_analysis_output` 与 `normalize_llm_findings` 强制长度：超长截断并记 `validationFailures: TEXT_TOO_LONG`；每节点发现 ≤8 条，多出的归并进"其他"。
- 提示词加一段格式约束（先差距后过程、动作用枚举、不复述规则原文）。
- 验收：基准样本上 95% 的正文 ≤150 字；结论卡字段填充率 100%。

### R4 一键分析结果页（1 天）
- 工程级页面：优先级表 + 共性风险 + 每节点一行结论；点节点进入 R1 的节点视图。

## 4. 与其他计划的关系
- 焊接节点计划 P6"覆盖判定卡片、四链矩阵卡片"是节点结论卡的焊接特化，应复用 R1 的结论卡骨架。
- harness 计划 H3（守卫语料补齐）会直接减少 71 条模板标题的来源；H5（清单填表）与 R3 是同一件事的两端：清单项就是"关键事实"，代码组装就能保证长度和结构。
- R1 不依赖任何后端改动，建议最先做；它解决的是"看不到重点"，而 H3/R2 解决的是"重点被丢了"。
